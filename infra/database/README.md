# Разделение ролей PostgreSQL: изолированный стенд

Это первая часть SP-E1-06. `grant-isolated-runtime.sql` — **только испытательный bootstrap**, а не скрипт обновления существующей базы. Он намеренно отказывает, если текущая база не совпадает с явно заданной и не называется `souzpir_test_*`, если подключение выполнено не от не-суперпользователя — владельца базы, если runtime обладает опасными атрибутами, членством или объектами, либо если в `public` смешаны владельцы таблиц. В существующих базах применение и перенос объектов требуют отдельного решения и проверки интегратором.

Сначала выделите отдельный worktree с собственной физической копией `vendor`, отдельный временный PostgreSQL-кластер, порт, базу и две роли без `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION`, `BYPASSRLS` и членства в других ролях. Владельцем тестовой базы и создаваемых миграциями объектов должна быть роль миграций; runtime-роль должна быть отдельной. Локальная аутентификация без пароля допустима исключительно в одноразовом изолированном кластере, не является настройкой для общей базы. Учётные данные хранятся вне Git.

До **каждой** миграции проверьте, что Laravel запущен из корня своего worktree, его `basePath()` и `Application::inferBasePath()` указывают именно туда, `APP_ENV=testing`, `DB_TEST_DATABASE` и фактический `current_database()` совпадают с отдельной тестовой базой и отличаются от `APP_PREVIEW_DATABASE`; `current_user` — тестовая роль миграций. Отдельным администраторским подключением проверьте, что `SHOW data_directory` указывает внутрь `.local` этого worktree и сервер слушает выделенный loopback-порт. Только после этого примените реальные миграции приложения ролью миграций. Отключите реальные отправки, используйте fake/array-драйверы, отдельные cache/session/queue и не запускайте планировщик.

После миграций для созданного стенда запустите, подставив только проверенные значения:

```text
psql -X -v ON_ERROR_STOP=1 -h 127.0.0.1 -p <test-port> -U <migration-owner> -d <souzpir_test_database> -v expected_database=<souzpir_test_database> -v runtime_role=<runtime-role> -f infra/database/grant-isolated-runtime.sql
```

В транзакции скрипт запрещает `CREATE` в `public` для `PUBLIC`, назначает runtime `USAGE` схемы, DML к имеющимся таблицам и `USAGE, SELECT` последовательностей, исключает таблицу `migrations` и её последовательность, настраивает аналогичные default privileges для **будущих объектов, созданных текущей ролью миграций**, и отказывает при обнаружении опасных действующих прав, в том числе через `PUBLIC`. Проверяет также по отдельности столбцовые `INSERT`/`UPDATE` для `migrations`. Ошибка откатывает весь bootstrap. `TRUNCATE`, `TRIGGER`, `REFERENCES`, владение и возможность `SET session_replication_role` runtime не выдаются. Это широкие DML-права приложения, а не предметная матрица прав отдельных таблиц. Права на функции скрипт не меняет.

Default privileges PostgreSQL принадлежат создающей роли: объекты, созданные другой ролью или в другой схеме, этим правилом не охватываются. Если таблица `migrations` пересоздана, default privileges дадут ей обычные DML-права до повторного bootstrap; после такого изменения повторно примените bootstrap и проверьте эффективные права до запуска runtime. Нельзя использовать этот промежуток для работы приложения.

## Адресная проверка

В корне этого worktree задайте следующие переменные для `python -m unittest discover -s infra/database/tests -p 'test_*.py' -v`:

| Переменная | Значение |
| --- | --- |
| `SP_ROLE_TEST_PSQL`, `SP_ROLE_TEST_PHP` | Абсолютные пути к `psql` PostgreSQL 16 и PHP приложения. |
| `SP_ROLE_TEST_HOST`, `SP_ROLE_TEST_PORT` | `127.0.0.1` и порт отдельного кластера. |
| `SP_ROLE_TEST_DB`, `SP_ROLE_PREVIEW_DB` | Имя `souzpir_test_*` и отличающееся имя preview-базы. |
| `SP_ROLE_TEST_ADMIN`, `SP_ROLE_TEST_OWNER`, `SP_ROLE_TEST_RUNTIME` | Три разные роли только этого тестового кластера. |
| `SP_ROLE_TEST_DATA` | Абсолютный путь к data directory внутри `.local` текущего worktree. |

Нужны применённые миграции и bootstrap выше. Тесты проверяют фактический data directory и соединения перед изменениями, работают с реальными миграциями, Laravel Eloquent и настоящим триггером `knowledge_release_immutable_trigger`. Тестовые данные находятся внутри откатываемых транзакций; временные таблицы удаляются. Тесты специально проверяют отказы при ошибочных ACL, владении и членстве; повреждённые условия восстанавливаются в `finally`. PHP smoke тестирует отдельные fake mail, notifications, очередь и запрет посторонних HTTP-запросов. Исполнять эти тесты на рабочем сервере или с общими ролями нельзя.

## Предлагаемый порядок перехода существующего окружения

Ниже только план для отдельного ревью; ни этот SQL, ни тесты не выполняют перенос существующих данных или ролей.

1. Интегратору и оператору инвентаризировать все базы, схемы, владельцев объектов, memberships и эффективные ACL, в том числе права `PUBLIC`, столбцовые права, default privileges всех создателей, функцию/trigger ownership, `SECURITY DEFINER`, расширения, права на создание схем и настройку `session_replication_role`. Проверить, какие фоновые процессы и миграции используют текущие учётные данные.
2. Согласовать план переключения и отката, подготовить резервную копию и проверить восстановление. В отдельной копии рабочей схемы разработать и независимо проверить конкретные команды переноса ownership и выдачи/отзыва прав; учесть все используемые схемы и роли-создатели. Не считать предоставленный test bootstrap таким переносом.
3. В согласованное окно остановить приложение и workers. Оператор создаёт отдельные учётные данные миграций и runtime, передаёт владение защищёнными объектами роли миграций и назначает только согласованные runtime-права, отдельно проверяя `migrations`, default privileges и права через `PUBLIC`. Секреты не помещаются в Git.
4. Применять миграции исключительно учётными данными мигратора; приложению и workers выдать runtime-учётные данные. До возобновления обычного трафика проверить фактического `current_user`, ownership, отказы в отключении защищённых триггеров и необходимые операции приложения, затем проверить аудит и фоновые процессы. Не менять старую роль до подтверждения результата и готовности согласованного отката.

Программа перехода, совместимость всех действующих операций приложения и откат для конкретной рабочей базы этим стендом не доказаны. Их нельзя выполнять без отдельной проверки, резервного копирования и согласованного окна.
