# SP-C-02 · Защищённая граница записи действий

**Граница после интеграции:** этот срез направляет отказ Guard на ручную проверку. Завершение общей границы вынесено в SP-C-02B; потребители зависят от SP-C-02B.

Один владелец: исполнитель, атомарно взявший эту карточку в очереди. Работать в отдельной ветке и worktree по `AGENTS.md` и `docs/parallel-workflow.md`.

## Цель и границы

По решению пользователя от 31.10.2026 создать общую серверную границу для безопасной записи действия. Первые потребители — `create_promise` продавца и восстановление сессии/бренда SP-E1-08 1б. Они выполняются отдельными зависимыми карточками после `done` этой задачи; простое наличие общего класса само по себе не означает готовность обоих пользовательских сценариев.

По решению пользователя от 01.11.2026 в эту же задачу временно передано владение изменениями Gateway, необходимыми для достоверного происхождения ответа ИИ: `app/Ai/Gateway.php`, `app/Ai/Protected/`, `app/Contracts/Ai/`, `tests/Feature/Ai/` и `docs/contracts/core.md`. Пока задача взята, другой исполнитель не изменяет пересекающиеся файлы. Существующий `complete` сохраняет контракт; новый защищённый путь получает доверенные данные стадии от серверного владельца и не считает публичный `AiResult` или `stageId` полномочием. Вызов провайдера выполняется вне транзакции, неопределённый исход не повторяется автоматически. Изменение охватывает только подтверждённую интеграционную потребность и должно иметь проверку на fake Gateway без сети.

Для этой же согласованной интеграции временно переданы `app/Seller/Engine/Extractor.php` и профильные тесты `ExtractorTest.php`, `ExtractorGatewayIntegrationTest.php`: допускается выделить построение запроса и разбор результата для защищённой стадии, сохранив поведение и проверки прототипа. Остальной Engine остаётся за своим владельцем. Публичные DTO сами по себе не подтверждают происхождение или полномочия; стадия проверяет привязку к серверному ходу, релизу, правам и Gateway.

В scope также входит `routes/features/C-02.php`: модульный POST-маршрут для явной постановки неопределённого хода на ручную проверку, с проверкой сессии, CSRF, прав, организации и бренда, атомарным аудитом и идемпотентным повтором. Общий загрузчик маршрутов и UI остаются вне scope. Автоматический повтор неизвестного вызова и таймаут не вводятся.

Граница должна поддерживать разные предметные проверки и блокировки для Seller и сессии, а не подменять авторизацию одним общим ключом. Для Seller закрыть существующий обход записи через `ConversationRepository::commitTurn`, в том числе при прямом вызове: неподтверждённый `TurnOutcome` не должен произвольно записывать действия. Учесть новую входящую реплику без потери сообщений и без бессрочного `processing`. Старые записи и уже начатые/неопределённые эффекты обрабатывать безопасно: отсутствие ledger не доказывает отсутствия внешнего действия, автоматический повтор неизвестного результата запрещён. Реальные внешние вызовы не выполнять.

Согласованное расширение владения для этой карточки: общие контракты границы, её реализация и миграции/реестр; Seller conversation repository и запись входящих сообщений для закрытия обхода; профильные тесты этой границы. Auth/Profile и Engine остаются владельцам зависимых карточек: не менять их без отдельного согласования. Один общий владелец всех файлов этой карточки; документационные и локальные изменения интегратора не входят в scope исполнителя.

## Definition of Done

1. Реальная PostgreSQL-транзакция связывает server-owned источник и полномочия действия, область организации/бренда, свежесть входа/хода и запись эффекта. Доверять произвольным идентификаторам, DTO, клиентскому состоянию или синтетическому флагу «проверено» нельзя. Контракт должен позволять защищённую привязку к конкретной сессии и её отзыв под той же блокировкой в будущем потребителе SP-E1-08 1б.
2. Вход между захватом и финализацией в обоих порядках не допускает устаревшую запись. Нельзя потерять новый вход, оставить диалог навсегда занятым или считать неизвестный внешний результат подтверждённо отсутствующим.
3. Повтор с тем же идентификатором и тем же содержимым даёт первоначальный результат без повторного эффекта; иное содержимое — конфликт. Проверить повтор, конфликт и неизвестный исход на отдельной тестовой БД; конкурентные сценарии учитываются в техдолге.
4. Отвергаются подменённое происхождение действия, другой tenant/brand, отозванные права/сессия и прямой старый обходной путь. Тесты фиксируют отсутствие записи и утечек. Неизвестное состояние fail-closed.
5. Миграции и безопасный переход существующих данных, реестр владения, адресные тесты и `docs/results/SP-C-02.md` с ограничениями. Результат — проверенный коммит и `submit`, затем интегратор объединяет в main и ставит `done`. Никаких реальных почты, ИИ и внешней доставки.

Карточки SP-E3-03P и SP-E1-08B зависят от SP-C-02; их исходные карточки могут продолжать другие независимые части. Окончательный runtime и фактическое выполнение `create_promise` эта карточка не объявляет завершёнными.
