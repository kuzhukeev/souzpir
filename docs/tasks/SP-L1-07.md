# SP-L1-07 · Создание клиента администратором

**Зачем:** второго клиента сейчас не завести: кабинет однокомпанийный — App\Tenancy\Cabinet::organizationId() возвращает одну организацию из env CABINET_ORGANIZATION_ID (app/Tenancy/Cabinet.php:10–18, config/features/E0-02.php:19), его используют ResolveTenant.php:24 и ещё 14 файлов входа, регистрации и приглашений. InvitationIssuer::issue() требует Request и сессию owner/admin и занят SP-E1-06J.
**Часть чего:** волна «Запуск-1» (planning/QUEUE.md): прод с живыми Продавцом (Telegram, режим черновиков) и Видением; экраны после запуска.
**Зависимость:** нет; можно брать параллельно с другими SP-L1 без пересечения scope.

## Приёмка
- `org:create {name} {owner_email} [--plan=...]` создаёт организацию, первый бренд (имя организации), тариф из config и приглашение владельца; печатает одноразовую ссылку (без SMTP); токен хранится только хешем, в лог не пишется; повтор с той же почтой/организацией — ошибка без дублей.
- Приглашение создаётся без InvitationIssuer (scope SP-E1-06J), в том же формате строки, который принимает InvitationAcceptance.
- Владелец по ссылке задаёт пароль и попадает в кабинет своей организации, а не CABINET_ORGANIZATION_ID.
- Cabinet: организация определяется по активному членству вошедшего пользователя (до входа — по приглашению); CABINET_ORGANIZATION_ID остаётся резервом текущей установки; вызовы Cabinet в перечисленных файлах заменяются только там, где нужно; существующие тесты проходят.
- Тест изоляции tests/Feature/Launch/L1-07/: две организации, владелец A не видит бренды, диалоги и замеры B; ресурс B по прямому URL → 404/403; вход, сброс пароля и приглашение работают для обеих.
- Feature-тесты только с Http::fake/Queue::fake, без живых и платных вызовов; ключи и токены только из env/config, не в коде и не в логах. Рефакторинг сверх нужного запрещён; чужие модули не менять; итоговый отчёт docs/results/SP-L1-07.md до 30 строк (тесты, долг, решения).
