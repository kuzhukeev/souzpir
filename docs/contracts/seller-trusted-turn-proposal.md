# Предложение интегратору: проверяемый ход Seller и безопасная отмена

Статус: **проект контракта, не включённый runtime**. Снимок и исполнение эффектов не готовы. Владелец интеграции и нового runtime — SP-E3-03B; записи `seller_turns` и диалогов принадлежат E3-04, опубликованные знания — E3-01, безопасность сессий — E1-01, платные вызовы и их учёт — E0-05, транспорт каналов — владельцам соответствующих адаптеров. До согласования с владельцами не регистрировать новые таблицы и не подключать отправки.

## Подтверждённая проблема

`InboundRecorder::ingest` добавляет клиентское сообщение, удерживая блокировку диалога, но не меняет `conversations.version`. `EloquentConversationRepository::commitTurn` сравнивает только `seller_turns.base_version` с этой версией. На неизменённом `066804f` в изолированной PostgreSQL последовательность claim → второе входящее сообщение → commit сохранила оба входа и устаревший ответ, а ход получил `completed` (диагностический тест: 1 тест, 4 проверки). Реплика может появиться и до claim; одного хеша истории после claim без правила обработки всех поступивших входов недостаточно.

`tests/Feature/Seller/Conversations/StaleTurnRegressionTest.php` в этой изолированной ветке намеренно проверяет требуемый отказ и сейчас **ожидаемо падает** с `The repository accepted a reply after a later input`. Не переносить тест в main до исправления: затем он должен проходить вместе с проверками восстановления `superseded/uncertain` и настоящих двухпроцессных гонок.

Пробный вариант увеличивал version при новой реплике во время `processing`: он отклонял устаревший commit, но оставлял turn в `processing`. Уникальный индекс `e304_one_active_turn_per_conversation` не позволял открыть следующий ход; `failed`/`suppressed` также отклонялись из-за несовпадения версии. Отдельно внедрять такой вариант небезопасно: он снят, изменения runtime в этой ветке отсутствуют. Отсутствие записи об эффекте в нынешней БД не доказывает, что эффект не начинался.

## Предлагаемые типизированные границы

Ниже — формы для согласования, не зарегистрированные исполняемые порты. Клиент передаёт идентификаторы и команду, но никогда не передаёт готовые history/state/goal/prompt/tool result как доверенные. Непрозрачная серверная ссылка — не сама по себе авторизация: при каждом применении хранилище повторно проверяет её и fence.

```php
interface TrustedSellerTurnSource {
    public function load(AuthorizedTurnActor $actor, string $turnId, #[SensitiveParameter] string $claimToken): TrustedTurnSnapshot;
    public function assertCurrentLocked(AuthorizedTurnActor $actor, TurnFence $fence): void;
}
interface SellerTurnFinalizer {
    public function finalize(AuthorizedTurnActor $actor, TurnFence $fence, StageReferences $stages): FinalizeResult;
    public function supersedeStale(AuthorizedTurnActor $actor, TurnFence $fence): SupersedeResult;
}
```

`AuthorizedTurnActor` должен быть подтверждённым сервером пользователем с проверенной сессией, активным membership, доступом к бренду, модулю и требуемому Gate; либо проверенным внутренним заданием из доверенного диспетчера с восстановленными ID и явной целью. Одного публично создаваемого `TenantContext(source: job)` недостаточно. Нельзя считать объект типизированного DTO свидетельством полномочий. Очерёдность блокировок для отзыва сессии и изменения membership согласовать с их владельцами до реализации.

`TurnFence` ссылается на организацию/бренд, диалог, input message/event, turn и секрет claim, базовую revision истории/состояния и версии server-side настроек, активный release ID/checksum и prompt ID/checksum. Токен и содержимое не попадают в логи/ошибки/трассы; DTO не сериализуется в клиент. Информация снимка — только из проверенных сохранённых записей: `messages`, `conversations`, event/channel, `KnowledgeRepository`, проверенные published prompts и серверные разрешённые настройки модели. `forRelease` сам по себе допускает старый опубликованный release, поэтому также нужно под блокировкой проверить, что ID/checksum ещё являются активными для бренда. `EngineFactory::forRelease` сейчас принимает модель и температуру от вызывающего; доверенный runtime должен выбирать/фиксировать их из подтверждённой серверной конфигурации и не принимать клиентские override.

Промежуточные Extractor/Goal/Guard/tool/summary — сохранённые, неизменяемые, tenant/turn/fence-bound этапы с проверкой версий и происхождения. Принятый состав каждого фактического запроса определяет `AiContext.dataClasses`; например, история — `conversation_content`, профиль клиента — `client_profile`, внутренние факты — `knowledge_internal`. Claim не разрешает передавать контакты или любую категорию данных во внешний AI.

## Ревизия и атомарная финализация

1. E3-04 и владельцы всех writer путей согласуют монотонную revision, учитывающую добавление, изменение и удаление участвующих сообщений и изменение mode/DND/state/назначения. Нужны индексированный порядок сообщений и чёткий cutoff входа; случайная сортировка ULID при одинаковом времени недостаточна. Новые входы сохраняются и не пропадают; порядок обработки нескольких уже накопленных входов определяется контрактом очереди, а не предположением snapshot.
2. Загрузка snapshot в короткой транзакции связывает claim с конкретными revision/cutoff и активными release/prompt/settings. Любой writer, влияющий на эти значения, сериализуется общим порядком блокировок и меняет соответствующий revision. Перед вызовом AI проверяются разрешения и категории данных; SQL-блокировки не удерживаются во время AI/HTTP.
3. Финализация в одной транзакции блокирует те же сущности в согласованном порядке, заново проверяет авторизацию/сессию, актуальность claim, revisions, активного release, prompt и настроек; атомарно сохраняет state, выходящие сообщения, задачи, утверждённые ссылки этапов и outbox. Отдельный `assertCurrentLocked`, после которого вызывается другой commit в новой транзакции, не закрывает TOCTOU. Старый claim не может создавать сообщения или эффекты.

## Неопределённые эффекты и переход stale

Для каждого допустимого эффекта E3-03B предлагает ledger `seller_turn_effects`, tenant/brand/turn-bound через составные FK и уникальный ключ `(organization_id, brand_id, turn_id, tool_call_id, effect_index)`, с типом, стадией, fence/revision и HMAC нормализованной команды. Raw аргументы, контакты и секреты в общих логах не сохранять. Точные имена таблиц и их schema ownership нужно зарегистрировать до миграции. Повтор того же ключа и тела возвращает сохранённый результат/состояние; иное тело — конфликт. Отдельный этапный ledger связывает AI calls с turn и отражает `in_progress`/`uncertain`; существующий `ai_calls.object_id=conversation` сам по себе не доказывает принадлежность конкретному turn.

Одних записей ledger недостаточно для доказательства отсутствия эффекта: все пути tools, доставки и платного AI обязаны проходить через контролируемую точку регистрации и fence; нельзя оставлять альтернативный выход в обход порта. Перед запуском передача получает уникальную зафиксированную intent и в короткой транзакции переходит к `transmitting` с проверкой fence. Транспорт сообщает подтверждённый результат; падение после начала передачи или неизвестный ответ — `uncertain`, без автоматического повтора. Адаптер должен сообщать, поддерживает ли провайдер проверяемую идемпотентность; отсутствие ответа не является отказом доставки.

При supersede транзакция сначала отзывает fence так, чтобы ни один worker больше не мог начать действие, и сериализуется с передачей. `superseded` допустим только когда закрытый для новых действий ledger и привязанные AI-вызовы подтверждают, что внешних передач/эффектов не начинали; заранее подготовленные, но не начатые intents отменяются атомарно. Если передача уже начиналась/была отправлена либо её исход неизвестен, старый turn остаётся `uncertain` и не повторяется автоматически до проверяемого reconciliation. Старые `processing` без закрытого ledger и источника происхождения трактуются как неизвестные, не как доказанно безопасные. Новые входы остаются в очереди; переход к следующему ходу возможен только после разрешённого terminal-состояния. TTL или исчезновение worker не доказывают отсутствие эффекта.

Для этого нужны согласованная миграция E3-04 статусов и partial-индекса (учитывая `uncertain` как блокирующий), реестр владения таблицами и адаптеры каналов/E0-05. Миграция старых записей должна закрываться при невозможности доказать их состояние, с отдельным операторским reconciliation; она не должна удалять входы или автоматически считать старые операции успешными/неотправленными.

## Проверки до включения

- Две сессии/процесса: новая реплика до claim, после snapshot и во время финализации в обоих порядках; повтор одного inbound event; правка/удаление истории и смена mode/state/settings. Проверять сохранность всех входов, отсутствие устаревшего ответа и восстановление без вечного `processing`.
- Изоляция двух организаций/брендов; подмена каждого ID, claim, prompt/release/checksum, серверных настроек и результатов этапов; отзыв сессии/membership/доступа к бренду/модулю в обоих порядках гонки; публикация нового release до финализации.
- Два worker для одного effect key, изменённое тело, потеря ответа/сбой до и после начала передачи, подтверждённая доставка, неясная доставка, отказ outbox/аудита и crash на каждой границе. Проверить единственность и атомарность, отсутствие повтора до reconciliation и корректную постановку нового turn.
- Настоящий путь persistence → trusted source → подготовленные E3-03 компоненты → fake AiGateway → fenced finalizer/outbox с явно указанными data classes; fake transport фиксирует точное число вызовов, а внешние сети запрещены. Проверить отсутствие raw contacts/secrets и диагностических аргументов в трассах при `zend.exception_ignore_args=0`.
