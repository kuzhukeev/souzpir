# Seller assignment database guard — proposed v1

Status: integration candidate, not deployed. This complements the Seller instance-save locks and Team checks; it is not a substitute for application authorization or tenant-scoped queries.

## Invariant

A new non-null assignee on a conversation or Seller task must have an active membership in that row's organization, access to its active brand, and the `seller.dialogs.write` role. The organization must be active at assignment time. The SQL `seller_assignment_roles()` function is the database-side v1 policy: owner, admin, editor and manager. Editor/manager both map to membership role `member` with its validated `settings.sales_manager`; owner/admin with an empty brand list are organization-wide. Viewer, disabled, missing or mismatched memberships are ineligible. Tenant IDs on existing Seller rows and membership identities cannot be changed.

Existing assigned rows prevent a membership change or deletion which would make any of them ineligible. Historical assignments survive later archiving of a brand or disabling of an organization, but new assignments are forbidden while either is inactive. Inactivation and assignment participate in the same concurrency protocol.

The migration locks the five affected tables, checks every existing non-null Seller assignment, and fails atomically if one is invalid. It does not silently repair data. Permissions configuration must match the database policy before migration. `PermissionEvaluator::allows` / `all` and the Seller eligibility helper compare the runtime configuration with the database policy and fail closed on divergence. Direct SQL is governed by the database policy; it cannot independently inspect an in-memory PHP configuration. Changes to roles or to effective-role mapping therefore require a coordinated migration and application release, never a configuration-only edit. Keep runtime config immutable until every request and worker runs the new version; stop writes during a policy transition. Callers that use configuration without the evaluator must not treat a conflicting configuration as authoritative.

## Transactions and error handling

Every relevant row trigger requires PostgreSQL `READ COMMITTED`, obtains a transaction-scoped advisory lock keyed by organization using `pg_try_advisory_xact_lock`, and raises `55P03` immediately if the lock is held by another transaction. It never waits for this advisory lock: a row-level trigger can execute after the target row was locked, so waiting would invert the application organization/brand/row order. Volatile trigger queries use fresh READ COMMITTED snapshots after row waits. Repeatable-read and serializable changes fail with `25001`; constraint violations use `23514`. The whole failing statement/transaction must be rolled back; callers may return a safe conflict and retry an entire idempotent operation. A normal application transaction can still wait on organization/brand/row or FK locks, and PostgreSQL can report `40P01`; callers must not assume all database waits or deadlocks are eliminated. Multiple organizations can proceed independently except for a possible hash collision, which causes only a false conflict.

The application instance-save path continues to lock organization then brand before checking membership, and holds the locks through commit. Team follows its corresponding organization-first protocol. The DB check closes direct query-builder, bulk, quiet-save and raw DML bypasses and races with external DML. Statements changing several rows are atomic; savepoint rollback releases locks acquired only inside the rolled-back subtransaction. The HTTP exception boundary returns a fixed, non-cacheable 409 for `55P03`, rolls back the failing Laravel/PDO connection and does not retry. A rollback failure purges the connection and returns a fixed 500. No exception text or SQL reaches the response or exception reporter. This does not roll back other connections or external effects already performed by application code; do not start such effects before the database commit.

## Deployment boundaries

PostgreSQL `public` schema is required by this implementation. The runtime database role must have ordinary DML only and **must not own the protected tables/functions or have privileges to alter/disable triggers**; migrations require a separate controlled owner role. Superusers, DDL-capable roles, replication-trigger bypass and an operator who changes the stored policy are outside this enforcement boundary. Automated migration and legacy-fixture tests use the owner of an isolated test database. A separate restricted role was also checked there: permitted DML was guarded and both `DISABLE TRIGGER` and `session_replication_role` changes were denied. This does not establish production privilege separation.

Apply migration before serving the new PHP policy checker. It takes write-conflicting table locks and rejects invalid historical assignments. Resolve and audit such assignments explicitly before retrying. A rollback removes this protection; stop all writers and transition application versions and DB roles together before rolling it back. Controlled retries outside HTTP and deployment role provisioning are integration responsibilities and are not implemented here. The migration is transactional in PostgreSQL; do not run its statements piecemeal.
