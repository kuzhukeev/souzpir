# Предложение: барьер выбранного бренда для сессии

Статус: **проект контракта, не реализован и не принят**. Основа: `8b6b51b`. До реализации и доказательства требований ниже не включать профильный кандидат `693ad86` и не считать E1-08 завершённой. Этот документ сам по себе не меняет настройки, схему, сервер или очередь.

## Подтверждённый разрыв

`BrandSwitchController` выполняет `session()->put('brand_id', ...)` внутри транзакции AuthSessionRegistry, но `StartSession` сохраняет file/database session позже, при возврате из middleware. Параллельный запрос успевает прочитать прежний `brand_id` до сохранения и дождаться блокировок уже с устаревшим tenant context. Registry lock сериализует транзакции, но не доказывает свежесть прочитанной session. Та же проблема относится к автоматически сохраняющим session GET, не только к одному `status`.

Пассивный статус не должен продлевать lease, сохранять session или cookie, запускать session GC либо тихо логинить через remember. Ветка-кандидат профиля проверяет эти свойства, но не решает гонку смены бренда. Гонка logout/опрос, уже проверенная прямыми вызовами AuthSessionRegistry, не заменяет HTTP-проверку двух процессов и независимых вкладок.

## Рекомендуемый контракт: авторитетный бренд в registry

1. Связать с **конкретным серверным lease** выбранный `brand_id` и монотонную ревизию `brand_revision` в AuthSessionRegistry. Имя схемы, миграцию и владельца согласует интегратор. Значения Laravel `session.brand_id` после перехода не являются источником прав. Ключ lease остаётся HMAC идентификатора сессии; сырой session id и bearer не хранить в базе, URL, аудите или логах.
2. `switch brand` под тем же row lock валидирует активную организацию, бренд и членство, меняет бренд и увеличивает ревизию в одной транзакции вместе с нужным аудитом. При ошибке всё откатывается. Сохранение file/database Laravel session не определяет выбранный бренд и не должно откатывать или перезаписывать registry.
3. `ResolveTenant` и все потребители session-контекста получают `brand_id` и revision из registry. Для мутаций и приватных выдач уже захваченный до ожидания контекст при повторной проверке под registry lock сравнивается с текущей ревизией; расхождение означает отказ/повторный запрос и не может незаметно переключить действие на другой бренд. Проверку нельзя ограничить одним Profile: старый tenant context есть и в других модулях. `brand.switch` — выделенное исключение с собственной валидацией назначения.
4. Пассивный status проверяет актуальность lease, owner, role, membership, организацию, бренд и ревизию под теми же блокировками, что logout/switch, без продления срока. Одновременные logout/switch и status сериализуются в БД; статус не создаёт lease через remember. Timeout/ошибка хранения — fail closed. Порядок блокировок должен быть единым и проверен вместе с остальными реализациями: session lease → user → organization → brand → membership/связи; операции с несколькими строками берут их в стабильном порядке. Это проектируемый порядок, не утверждение о соответствии всего текущего кода.
5. Вход, ротация session id, remember login и существующие leases требуют атомарного создания/инициализации или безопасного восстановления выбранного бренда после проверки прав. Нельзя доверять старому `session.brand_id` без повторной проверки. При невозможности однозначно выбрать доступный бренд — честный отказ; не переносить данные к другому бренду автоматически. При logout соответствующий lease отзывается под той же блокировкой. Несохранённая Laravel session не может его воскресить.
6. До включения нового контракта нужен безопасный план миграции и отката: сначала совместимый код, backfill под проверкой членства, проверка отсутствующих значений, завершение старых процессов, переключение единственного источника истины. Старые процессы, которые продолжают выбирать бренд из session, одновременно с новым контрактом недопустимы. При отказе миграции или потере БД приватные функции остаются закрыты; старое состояние и операторский план отката документируются без слепого запуска миграций на рабочей базе.

## Браузер и граница гарантии

Сериализация в БД определяет порядок **серверных решений**, но ответ старого status может быть доставлен в браузер позже завершившегося переключения. Поэтому нельзя утверждать, что серверная блокировка сама мгновенно скрывает уже отображённый старый экран. Клиент при инициировании switch/logout обязан синхронно скрыть приватное содержимое, отменить находящиеся в пути запросы и через BroadcastChannel оповестить остальные вкладки того же браузерного контекста; подтверждённая ревизия привязывается к ответу, а пришедшие после сообщения ответы предыдущего поколения отбрасываются. При отсутствии подтверждения, закрытом канале или ошибке статус не раскрывается без новой проверки. Отдельно проверить фоновые/замороженные вкладки, BFCache, переподключение и случай, когда действие начато с другой машины/процесса: один BroadcastChannel не является серверной гарантией и не является механизмом авторизации.

Не обещать мгновенное удаление уже полученных данных из памяти другого независимого клиента. База и Action обязаны отказывать устаревшему контексту; видимая граница и допустимая задержка сокрытия фиксируются в критериях интерфейса. Для чувствительных данных таймаут и восстановление доступа должны fail closed.

## Программа доказательства

- Реальные HTTP-запросы в двух независимых процессах сервера, одна синтетическая БД и две вкладки с одним session cookie; отдельные конфигурации `SESSION_DRIVER=file` и `database`. Однопроцессный встроенный PHP-сервер без второго worker не доказывает конкуренцию.
- Барьеры внутри **только тестового** middleware показывают: status удерживает решение и switch ожидает; switch зафиксирован первым и status видит новую ревизию/отказ; задержка доставки старого ответа после switch не раскрывает старый DOM. Второй процесс действительно ждёт `pg_locks`, а не просто запускается позже.
- Те же порядки для logout и status, смены роли/доступа и status, нескольких одновременно работающих вкладок и смены сессии/remember. Проверить реальную cookie, session file mtime / DB `sessions.last_activity` и payload, server lease expires_at, GC с принудительной лотереей, отсутствие случайных регистраций leases.
- Гонки stale действия с switch: после увеличения ревизии невозможны запись, чтение приватного payload, отправка или audit в старом/новом бренде без явного повторного выбора. Ошибки, обрыв ответа, таймауты и rollback не оставляют ложный успех; проверка ограничений и изоляции tenant и прав.
- Убедиться в отсутствии deadlock под встречным отзывом сессий, сменой ролей и параллельными переключениями; фиксировать реально выбранные блокировки и порядок. Проверить обычный login, logout, MFA, remember, cookie, существующие `/integrations/*` маршруты и общую регрессию до и после включения схемы.
- Проверить порядок миграции/отката и изоляцию тестовых БД без использования рабочей, fake внешние адаптеры. Нагрузочный и многосерверный тест обязателен перед выводом о поддержке нескольких узлов. Снимки интерфейса только на синтетических данных.

Альтернатива — общий session lock, который охватывает *загрузку*, всё использование и фактическое сохранение session для **всех** запросов, способных сохранить её, включая switch/logout и существующие `Route::block()`. Одной маршрутной блокировки status недостаточно; lock с истекающим TTL, file lock на одном узле или отдельные несогласованные замки не доказывают безопасность на нескольких узлах. Любой предлагаемый lock должен показывать поведение при истечении, сбое процесса и соединения, повторном подключении, ошибке сохранения и смене session id, без удержания неопределённой блокировки над живой сетью. После получения lock необходимо перечитать состояние до решения. Такой вариант может быть выбран только после конкретного прототипа и тех же тестов; ни один вариант здесь не утверждается реализованным.
