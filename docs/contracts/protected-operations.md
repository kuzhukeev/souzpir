# SP-C-02: внутренний транзакционный учёт повторов

`PostgresTransactionalIdempotency` — отдельный внутренний примитив для будущей
защищённой границы. Он не подключён к маршрутам, runtime или бизнес-операциям и
не подтверждает личность, права, происхождение результата, свежесть входа или
отсутствие внешних эффектов. В частности, он не закрывает прямой вызов
`ConversationRepository::commitTurn` и не разрешает повтор неизвестного эффекта.
Это только brand-scoped примитив: оба идентификатора обязательны. Для logout и
других операций сессии без выбранного бренда или membership он не подходит;
подставлять фиктивный бренд нельзя. Совместимый session-scoped контракт для
SP-E1-08B ещё не определён, общий finalizer не готов.

Вызов принимает идентификаторы организации и бренда, имя операции, ключ,
канонические байты запроса и доверенный внутренний callback. Составной FK
гарантирует принадлежность бренда организации. В пределах организации, бренда и
операции тот же ключ и те же байты возвращают сохранённый результат; другое тело
вызывает `IdempotencyConflict`. Канонизацию и полноту тела определяет будущий
вызывающий код. Идентичность измеряется по байтам, а не по смыслу JSON.

Callback должен делать только транзакционные записи через то же соединение с
PostgreSQL и возвращать JSON-совместимый массив. Нельзя вручную управлять его
транзакцией, менять соединение или выполнять внешние вызовы. Примитив не способен
обеспечить это ограничение для произвольного callback, поэтому к нему допускается
только доверенный код. Callback и сохранение результата происходят в одной
транзакции; при внешней транзакции результат предварителен до её commit. При
rollback callback и receipt откатываются, и следующий вызов исполняется заново.
Два процесса с одним ключом сериализуются через уникальный индекс и блокировку;
незавершённая видимая запись закрывает повтор с ошибкой. Вложенный рекурсивный
вызов с тем же ключом не считается успешным повтором.

Ключ и тело сохраняются только как разделённые по назначению HMAC, результат —
зашифрованным. Служебная singleton-запись фиксирует fingerprint `APP_KEY` и
закрывает вызовы после неожиданной смены ключа: иначе тот же ключ стал бы новым и
дублировал запись. Поддерживаемого механизма ротации пока нет; потеря ключа делает
историю недоступной. Таблицы сохраняют историю без автоматического истечения;
откат миграции запрещён, пока receipts существуют. Триггеры PostgreSQL запрещают
переписывание и удаление завершённых receipts, изменение key guard, `TRUNCATE`
и фиксацию незавершённого receipt. Привилегии владельца БД позволяют менять сами
триггеры и находятся за пределами этой гарантии. Общий ключ и история —
операционная зависимость, их сохранение необходимо для корректного повтора.

Только внутреннее подтверждённое несовпадение тела возвращает фиксированный
`IdempotencyConflict`. Все прочие ошибки, включая исключения callback, SQL и
шифрования, преобразуются в `IdempotencyFailure` с фиксированным текстом без
предыдущего исключения. Даже если callback выбросил `IdempotencyConflict`, он не
считается подтверждённым конфликтом и не может передать свой текст наружу.
Подробности исходной ошибки через этот API недоступны.

Это не завершает SP-C-02. Для настоящего потребителя остаются согласованные
server-owned происхождение стадии и авторизация под общей блокировкой, проверка
истории диалога, безопасная обработка неизвестных эффектов и закрытие старого
обхода. Без них подключение примитива к Seller или Auth запрещено.

## Низкоуровневая проверка актуальности Seller turn

`SellerTurnFence::assertCurrent` можно вызывать только внутри уже открытой
PostgreSQL-транзакции. Он блокирует активные организацию и бренд, диалог и ход;
сверяет tenant, реальный claim token и версию, статус обработки, серверные
history revision/cutoff и соответствующее последнее клиентское сообщение.
Защищённая запись должна выполняться в той же транзакции до освобождения этих
блокировок. Метод ничего не записывает и не возвращает объект или флаг, которые
можно сохранить как доказательство для будущей операции; не принимает callback.

Это **не авторизация** и не доверенный источник результата ИИ: `TenantContext`
или claim не доказывают действительную сессию, роль либо происхождение фоновой
задачи. Будущий владелец операции обязан дополнительно проверить actor/session
или доверенный job, права и опубликованный контекст, а также заново выполнить
проверку fence под теми же блокировками при применении результата. Внешний ИИ
нельзя вызывать внутри этой транзакции. Ошибка метода не доказывает отсутствие
ранее начатого внешнего вызова и не разрешает автоматический повтор. Метод не
сам по себе не закрывает обход `commitTurn`. Для отдельной fake-only стадии
резюмирования Gateway повторно вызывает эту проверку при резервировании и
чтении результата; этот путь не является готовым финализатором Seller.
