- S-5.2/S-5.3: базовая приёмка (снимок подписок, outbox+очередь, fake-транспорт с подписью и повторами, матрица общих уведомлений, код Telegram) закрыта ранее SP-E1-10H/I/J (`docs/release/2026-11-09-remaining.md`); подтверждено прогоном их тестов (WebhookSnapshotE110JTest, CompanyNotificationQueueE110JTest, CompanyTelegramE110JTest, FakeWebhookQueueE110JTest, FakeTimingErrorsE110JTest — все зелёные), новых изменений по этим пунктам не потребовалось.
- Дополнение 07.11.2026 (реестр S-7.1, D-10.3): `config/runtime.php` — `notification_driver` получил default `fake` (как `ai_driver`/`delivery_driver`); проверено: в окружениях без `NOTIFICATION_DRIVER` тихие часы/сводка (S-7.1, `NotificationTimingDraftTest`, `ProfileSettingsTest`) и переключатель напоминаний (D-10.3, `PlannedTest`) теперь доступны по умолчанию, `DrainNotifications` обрабатывает fake-очередь без лишних флагов. Сверено с макетами S-7.1 (`31/94e5477d`) и D-10.3 (`158/5c6b22a0`) — тумблер напоминаний и блок «Тихие часы»/«Сводка» должны быть активны, текущий UI уже реактивен на `reminders.available`/`timingAvailable`, правок вёрстки не потребовалось.
- Побочный эффект в scope: с новым default'ом общий вебхук-обработчик (`OutboxDispatcher`→`ProcessFakeWebhookEvent`) начал автоматически отправлять «сырую» (немаппленную) копию тестового CRM-события параллельно с собственной CRM-доставкой с полями. Исправлено в `app/Seller/Channels/Crm/CrmFakeDelivery.php`: синтетическое тестовое событие сразу помечается consumed для консьюмера `integrations.webhooks.v1`, маппинг остаётся единственной доставкой (проверено: `CrmMappingsE609DTest`).
- Поправлены тесты в scope, которые полагались на старый default (не-fake) как на «отключённое» состояние: `PlannedTest`, `NotificationTimingDraftTest`, `ProfileSettingsTest`, `NotificationRoutingTest`, `NotificationCoreTest`.
- Тесты: проверено — `php artisan test` по scope задачи: 42 теста зелёных (`PlannedTest`, `ContactReminderTest`, `NotificationTimingDraftTest`, `ProfileSettingsTest`, `CrmMappingsE609DTest`, `CrmFakeDeliveryTest`, `NotificationRoutingTest`, `NotificationCoreTest`). Дополнительно прогнаны `tests/Feature/Shell/Notifications`, `tests/Feature/Shell/Integrations`, `tests/Feature/Shell/Profile`, `tests/Feature/Seller/Channels/*` целиком — новых падений нет. `composer lint` (Pint) зелёный.
- Не менял .tsx/фронтенд — экраны уже управляются серверными флагами `available`/`timingAvailable`.

## Остаток / Нужно от интегратора
- Смена default `notification_driver` → `fake` ломает 14 тестов вне scope карточки в `tests/Feature/Seller/Settings/Limits/` (`DigestTest`, `NotificationsTest`, `PersonalDigestTimeTest`): `SellerNotificationRouter` трактует `cabinet`-канал как «immediate» именно при `notification_driver === 'fake'`, и эти тесты (без явной настройки драйвера) проверяют «боевой» путь digest-роутинга. Правки подготовлены и проверены локально (были в ветке, затем убраны как вне scope — `task.py submit` блокирует чужие файлы): везде, где тесты намеренно проверяют non-fake/digest-путь для cabinet, нужно добавить `config(['runtime.notification_driver' => null])`. Нужен `CI_SCOPE_EXCEPTIONS` на эти 3 файла либо отдельная задача/правка владельца модуля `Seller/Settings/Limits`, иначе CI на `main` после слияния станет красным.
- `.env.example` не трогал (строка `NOTIFICATION_DRIVER=fake` вне scope) — для согласованности с `AI_DRIVER`/`DELIVERY_DRIVER` её стоит добавить при слиянии.

## Техдолг
- На слоте exec-2 тесты с `IsolatedDatabaseMigrations` (в т.ч. `ProfileFeatureGateTest`, `OutboxDeferralTest`, race-группа) падают с «A dedicated, nonprivileged test database owner is required» — проблема окружения слота, не связана с этой задачей; воспроизводится и без моих правок.
- Старые outbox-события без снимка подписок по-прежнему не доставляются автоматическим вебхукам (известно по SP-E1-10J).

## Принято по умолчанию
- `notification_driver` по умолчанию `fake` везде, где явно не задан `NOTIFICATION_DRIVER`; боевой драйвер по-прежнему включается только явной переменной окружения.
