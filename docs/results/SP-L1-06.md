# SP-L1-06 · Уведомления менеджеров о сообщениях и черновиках

Сделано: новый модуль `app/Seller/Notifications/`. `QueueInboundNotification` — слушатель `eloquent.created` на `Message` (роль client), ставит `NotifyConversationEvent`; `LiveDraftJob::finish()` ставит тот же job при статусе `suggested` (`turn_id` в данных). `NotifyConversationEvent`: дедуп не чаще раза в N минут на диалог+тип события (`config/features/L1-06.php: dedup_minutes=5`, проверка по `outbox_events.envelope` за окно — без новой таблицы), создаёт `cabinet_notifications` для участников, прошедших `RecipientPolicy::permits` (owner/admin/member — менеджеры бренда, добавлены к существующим ключам handed_off/contact.reminder), с `link` на `/seller/dialogs/{id}`; и — при `NOTIFICATIONS_EXTERNAL_ENABLED` (`features.E0-04.defaults.external_delivery`) — одно сообщение в группу менеджеров через `TelegramSender::managers` (chat бренда `managers_chat_id`), текст = заголовок + ссылка, без прочих персональных данных. `DrainNotificationsSchedule` регистрирует `notifications:drain` каждую минуту (`withoutOverlapping`) через `ScheduleContributor` в `config/features/L1-06.php` — `routes/console.php` не трогали.

Тесты: `tests/Feature/Launch/L1-06/ConversationNotificationsTest.php` — входящее сообщение → кабинет (с `link`) для owner и менеджера бренда, изоляция чужого бренда (нет записи), группа Telegram молчит при выключенном флаге и в дедуп-окне, включение флага + истечение окна (`CarbonImmutable::setTestNow`, +10 мин) → ровно одно сообщение в `managers_chat_id` со ссылкой на диалог; `LiveDraftJob` со статусом suggested → уведомление владельцу. `DrainScheduleTest` — расписание регистрирует `notifications:drain` `* * * * *` с `withoutOverlapping`. Проверено: `php artisan test tests/Feature/Launch/L1-06` (3/3, 13 assertions); регрессия — `php artisan test tests/Feature/Shell/Notifications/NotificationCoreTest.php tests/Feature/Launch/L1-01 tests/Feature/Seller/Channels/Planned` (40/40; падения `OutboxTracePrivacyTest`/`OutboxDeferralTest`/`AfterCommitTest` при полном прогоне директории — известное ограничение слота «dedicated nonprivileged test database owner», см. `docs/results/isolated-test-database.md`, не относится к задаче). `composer lint` (pint) — зелёный.

## Техдолг
- Канал входящего сообщения в данных события берётся из `messages.channel_account_id`; если он не заполнен (например, виджет без привязки) — `channel: unknown`, без блокировки уведомления.

## Принято по умолчанию
- Получателями «менеджеров бренда» взяты активные участники бренда с ролями owner/admin/member — иначе менеджеры не узнавали бы о новых сообщениях.
- Группа в Telegram — существующий `managers_chat_id` Telegram-канала бренда; если не настроен, уходит только уведомление в кабинет.
- `docs/contracts/registry.json` и `EventCatalog::TITLES` не входят в scope карточки (общий контракт); события реализованы в обход общего outbox/`NotificationProcessor` — напрямую пишут `cabinet_notifications`/`notification_deliveries` своим кодом (заголовки — в `NotifyConversationEvent::TITLES`), чтобы не трогать чужие файлы и не ломать `NotificationCoreTest` (сверяет `EventCatalog` с `registry.json`).

## Нужно от интегратора
- Добавить `seller.conversation.inbound` и `seller.draft.ready` в `docs/contracts/registry.json` (owner SP-L1-06) и `EventCatalog::TITLES`, если нужно показывать их в общем списке уведомлений (`DashboardController`) по общему каталогу, а не только по сохранённому `title` в строке.
