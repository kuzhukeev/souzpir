# Кандидат общей защиты назначений Seller

Статус: отдельная интеграционная ветка `codex/sp-seller-assignment-db`, база `9f6c106`, работа не закоммичена, не объединена и в рабочую БД не применялась. Это временная совмещённая сборка: изменения Team `cab1b14` и helper `ed65d7c`/`c38461e` скопированы в worktree для проверок и остаются собственностью соответствующих задач. Не переносить эту сборку целиком в main без отдельного ревью. Контракт и границы описаны в `docs/contracts/seller-assignment-db-v1.md`.

Добавлены PostgreSQL-триггеры на назначения, изменение membership и доступность бренда/организации, аудит существующих назначений в транзакционной миграции и индексы для обратной проверки. Гонки синхронизируются неблокирующим advisory-lock организации и работают только на READ COMMITTED. PHP при проверке прав и назначении сверяет конфигурацию с DB-политикой. Обработчик HTTP превращает SQLSTATE 55P03 в безопасный 409, откатывает незавершённую транзакцию и не повторяет операцию. В тесте legacy-данных helper защищающие триггеры временно выключаются только внутри тестовой транзакции, непосредственно для создания искусственных записей.

Проверено на отдельном PostgreSQL 16 и синтетических данных:

- Общая матрица Team: 12/12 двухпроцессных тестов, включая оба порядка для роли, доступа к бренду и отключения участника; 84 assertions, пропусков нет.
- Финальный отдельный прогон DB concurrency: 9 тестов, 250 assertions. Прямой SQL: оба порядка для conversation/task против роли, списка брендов, отключения участника, архивации бренда и отключения организации; ошибки конфликта без ожидания advisory-lock.
- Трёхсоединённые тесты проверяют свежий снимок после ожидания row-lock в обоих направлениях. Проверены rollback savepoint и многострочного UPDATE, разделение организаций, отказ REPEATABLE READ/SERIALIZABLE, аудит старых записей и атомарный откат миграции, несовпадение PHP-конфигурации.
- `commitTurn`: реальные процессы в обоих порядках для трёх изменений membership, проверены отказ, сохранность задания и rollback других данных.
- Для 55P03: четыре HTTP-проверки JSON/браузера/приватной поддержки/прямой PDO-транзакции; debug включён, SQL и данные в ответ не попадают, попытка выполняется один раз, проверен полный rollback соединения. Отдельно privacy-регрессия: 18 тестов, 313 assertions.
- Отдельная тестовая DML-роль без владения таблицами выполняла разрешённое назначение, а недопустимое и отключение назначенного участника были отклонены. Отключение триггера и `session_replication_role=replica` этой роли запрещены. Продакшен-роли не менялись.
- Pint и `git diff --check` прошли. Один общий итоговый прогон нескольких наборов был прерван после затянувшегося ожидания; он не считается успешной проверкой. Отдельные приведённые выше прогоны завершились. Рабочая БД и живые внешние вызовы не использовались. Ранее отдельно выполненная read-only агрегированная проверка на момент просмотра не обнаружила назначенных Seller-записей в `souzpir_dev`; состояние могло измениться, миграция выполняет собственный аудит под блокировками.

Перед интеграцией нужны: ревью общей точки `app/Privacy/SupportExceptionHandler.php`; контроль порядка миграции и выпуска PHP; настройка runtime DB-роли без ownership и прав отключения trigger; проверка очередей/CLI на управляемый конфликт без повтора внешних действий; согласование неизменяемости v1-политики до совместной миграции. SQL-политика — источник истины для прямого SQL: база не может прочитать произвольное in-memory изменение PHP config, поэтому изменение прав только через config без синхронного обновления БД недопустимо. HTTP rollback относится к соединению, на котором произошла ошибка; внешние эффекты и другие соединения он не откатывает.
