# SP-E1-12 — помощь и обращения

Ветка `codex/sp-e1-12`, base claim `e332dabf4d2444be6cdc63cd332080fab67c1c2b`, отдельный worktree и изолированная тестовая база. После независимой проверки задача возвращена в работу. Исправления подготовлены в своей ветке; повторная передача на review возможна только после общих интеграционных изменений ниже.

## Результат

Реализованы страницы `/help`, `/help/support`, `/help/status`: разделы помощи и поиск по настроенной базе; собственные обращения с валидацией, приватными вложениями, уведомлением, аудитом и согласиями на 72 часа; статус приложения/БД и честные unknown-состояния для неподключённого мониторинга. Согласие отзывается и истекает по серверному времени, однако не предоставляет вход сотруднику поддержки: механизма идентификации сотрудника в проекте нет.

SMTP по умолчанию отключён и включается только явной настройкой транспорта и адреса. Письмо формируется после commit, успешным считается только подтверждённый receipt; неопределённая доставка отображается как uncertain. Путь к вложениям не публикуется: доступ проверяет собственника обращения и сессию, ответ attachment/no-store/nosniff. Реальных отправок не было.

## Исправления после проверки

- Ошибки создания обращения и доставки заменяются на безопасные без исходного exception/previous и SQL bindings; локальная граница контроллера очищает Request от form/JSON/raw body, query и файлов, включая кэш Laravel convertedFiles. Стандартные сообщения валидации и HTTP-статусы сохраняются.
- Файлы после сбоя удаляются только если callback транзакции не завершился, нет активной транзакции, база доступна и ссылка отсутствует. При неизвестном исходе COMMIT и сбое проверки сохраняется приватный orphan. Проверены фактический сбой после commit и отказ проверки БД.
- Policy разрешает активному наблюдателю создавать свои обращения и отзывать своё согласие, другие пользователи и организации по-прежнему изолированы. Для реальной работы POST обязательна общая поправка tenant middleware ниже.
- Перед каждым тестовым запуском проверены testing environment, basePath `.worktrees/sp-e1-12` и `current_database() = souzpir_test_sp_e1_12`. Реальных внешних отправок не было.

## Ограничения и интеграция

1. Для viewer общий `ResolveTenant` блокирует POST. Интегратору добавить `$ownSupportActions = $request->isMethod('POST') && $request->routeIs('help.support.store', 'help.support.access.revoke');` и `&& ! $ownSupportActions` в guard `canWrite`, сохранив все ранее выполняющиеся проверки active membership, выбранного brand/session и заголовка. Проверить собственные create/revoke, чужие ticket 404, другие viewer POST/PATCH 403 и stale brand 404. В модульных тестах эта строка проверялась с временным патчем; общий файл после запуска восстановлен и в commit не включён.
2. До запуска tenant/CSRF middleware нужна общая ранняя граница для POST поддержки и exception reporter/renderer: fail-closed включить `zend.exception_ignore_args=1`, восстановить исходное значение в finally (с проверкой long-lived worker); unexpected ошибки никогда не логировать в исходном виде, исключать message, previous, SQL bindings и Request, отвечать безопасным 500, сохраняя предусмотренные 401/403/404/419/422 и validation errors. Routing pipeline обрабатывает исключения внутри middleware, поэтому наружного catch недостаточно. Интегратор должен проверить pre-controller и post-controller ошибки при `zend.exception_ignore_args=0`, независимость последующего запроса и scoped behaviour. Это не утверждение о логах обратного прокси/PHP или сторонних систем.
3. Доступ сотрудника поддержки в чужой кабинет отсутствует по существующему контракту. Согласие реально сохраняется и истекает, но `entry_available=false`. Future access mechanism должен проверять staff identity, scope давшего согласие и актуальный TTL/отзыв на каждом запросе.
4. AI Gateway не публикует read projection cooldowns, а источников мониторинга компонентов и истории инцидентов нет. Fake cooldown adapter проверяет только отображение и истечение в проекции. Требуется adapter владельца AI и реальные read sources; отсутствие cooldown не выдаётся за работоспособность провайдера.
5. Вложения приватны и в почтовое уведомление не включены; механизм просмотра сотрудником, ответы и закрытие обращения требуют будущего support adapter. При выключенном или не настроенном SMTP обращение сохраняется локально, а UI честно сообщает, что письмо не отправлено.
6. Интегратору нужно выполнить `php scripts/generate-types/generate.php` и включить изменённые shared types после объединения.
