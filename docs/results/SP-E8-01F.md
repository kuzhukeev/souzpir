# SP-E8-01F — результат

Подготовлены tenant-scoped анкеты, неизменяемые версии профиля, таблицы batch/candidate с составными FK и сервис атомарного сохранения/submit/edit с audit. Контракт шагов и точные сигнатуры приведены в `docs/modules/E8-01F.md`.

`MeasurementRunner::start` через `PublishedKnowledgeBridge::buildProfile` записывает опубликованный разрешённый профиль и, при наличии анкеты бренда, отдельную self-declared проекцию с идентификатором и checksum версии в `measurements.profile_snapshot`. Заявления клиента не считаются проверенными фактами и не становятся частью release. Обновление анкеты создаёт новую версию, предыдущая остаётся доступной по ID. Старые snapshots без анкеты работают по прежнему пути; отзыв published grant закрывает и их.

Критическое ограничение интеграции: `EvidenceEvaluator` пока может положить весь snapshot в исходящий `knowledge_public`. Поэтому до отдельной защиты всех исходящих payload `KnowledgeGate` намеренно блокирует замеры со self-declared версией, хотя их snapshot создаётся. Интегратору необходимо внедрить фильтрацию, доказать отсутствие маркера анкеты в fake gateway на всех исходящих путях, проверить историческую версию и отзыв grant и только затем снять явный временный запрет. Реальная отправка самих данных анкеты требует отдельного data class/grant/data policy/ContactBoundary. AI-генерация вопросов и UI не подключены; batch по умолчанию blocked. Реальные внешние вызовы не выполнялись. Общий реестр `question_generation_batches` обновляет интегратор.

Проверено: 12 тестов, 90 assertions; Pint. Включены настоящий путь создания замера и fail-closed до вызова AI, исторический snapshot и отзыв grant, отказ viewer/stale-session/чужому бренду, два независимых процесса на одной revision, FK/immutability, откат при ошибке audit, глубина и типы данных, нормализация чисел в PostgreSQL JSONB и непопадание приватного маркера в аргументы трасс. Браузерных изменений и скриншотов нет.

Тесты после исправления окружения выполнены на выделенном PostgreSQL `127.0.0.1:55560`, в отдельной тестовой БД и с самостоятельной копией vendor; перед миграциями тест проверяет base path, runtime пути, `current_database()`, loopback и непривилегированную роль. Инцидент начальной настройки: до исправления junction `vendor` первый запуск направил `migrate:fresh` и rollback в общую **тестовую** БД `souzpir_test_main`; её предыдущее содержимое восстановить по имеющимся сведениям нельзя, интегратор уведомлён. Рабочая БД не использовалась.
