# SP-E1-01G — проверенный промежуточный шаг

Реализован сквозной путь новой ссылки восстановления: ссылка содержит email и одноразовый токен только после `#`; отдельная минимальная страница очищает адрес до загрузки Inertia и передаёт данные через POST. Общий ранний boundary из main `2af6056` убирает исходные данные из Request до middleware, а приложению передаёт SHA-256 токена и зашифрованный адрес. В сессии остаются только хеш и шифротекст. Токен в БД хешируется с доменом `v2:`: прежние выпущенные токены не подходят, их данные не удалялись. Применение по-прежнему проверяет срок, права и версию авторизации; успешная смена атомарно отзывает токен и сессии, обновляет версию и пишет audit.

Публичный HTTP по-прежнему запрещён; локальный HTTP разрешён только для подтверждённого прямого loopback. Новый путь закрыт для всех `Forwarded`, `X-Forwarded-*`, `X-Real-IP`, `CF-Connecting-IP` до отдельного согласованного proxy-контракта, даже если Apache передал `HTTPS=on`. Формирование ссылки через SMTP также отказывает небезопасному нелокальному адресу. SMTP не включали и реальную почту не отправляли.

## Проверки

- `PasswordDeliveryTest`: **16 тестов / 247 проверок** в отдельной PostgreSQL `souzpir_test_sp_e1_01g`, loopback-порт 55841, отдельная роль-владелец `sp_e101g_app` без административных прав. Fake mail, срок, одноразовость, повторная выдача, устаревшие токены, полномочия и конкурентная смена прав/сброса, удаление сессий и fake SMTP.
- `ResetRedirectTest` и `AuthFlowTest`: **24 теста / 259 проверок**, включая поддельный `X-Forwarded-Proto` при `HTTPS=on`, безопасные редиректы и регрессию авторизации. Тесты работают из этого worktree; общая test DB не использовалась.
- `npm run typecheck`, `npm run build` и Pint для изменённых PHP-файлов — успешно.
- Chromium → отдельный Apache 2.4.66 с обычным OSPanel-форматом `combined` → отдельный PHP на loopback → тестовая БД: **3 browser-теста**, реальный POST обмена и смена пароля, в том числе замена ссылки во время выполняющегося обмена и очистка некорректного фрагмента; адреса запросов, browser history/state/storage, access/error Apache и application log не содержат синтетические token/email; обычные события и синтетическая ошибка upstream присутствуют в журналах. Это изолированная конфигурация-проба, не изменение или полная проверка работающего OSPanel. Проверен только Chromium. Скриншоты внутри игнорируемого worktree: `.local/screenshots/e1-01g-reset-{1440,1024,390}.png` и `.local/screenshots/e1-01g-reset-390-{neutral,confectionery,pyro}.png`; просмотрены вручную, горизонтального overflow нет.

## Оставшийся блокер: прежние URL в инфраструктурных журналах

Синтетическая старая ссылка `/reset-password/{token}?email=…` получает 404 и не даёт восстановить пароль, но в отдельной пробе штатный Apache с `combined` записал в access log и token, и email до приложения. Фактический шаблон OSPanel `C:/OSPanel/modules/Apache/conf/httpd.conf` использует `%r` в `LogFormat combined` и доменных `CustomLog`; сторонние proxy и копии журналов не проверены. Поэтому исходный DoD «все журналы» не выполнен. Нужны согласованная обработка старых URL на входе и проверка access/error журналов каждого фактически используемого сервера, proxy, системы наблюдения и их копий, без отключения остальных событий. Неизвестные proxy остаются fail-closed; применение настройки OSPanel и реальная доставка требуют отдельной интеграции и проверки.

Карточка остаётся в работе; этот промежуточный результат не означает `review` или `done`. Конфигурации OSPanel, общие рабочие БД и чужие проекты не менялись.

## Исправление после ревью: канонический адрес письма

SMTP-адаптер строит ссылку из проверенного `config('app.url')` и относительного маршрута, без использования Host, схемы и порта текущего Request. Для рабочего адреса обязателен HTTPS, локальный HTTP разрешён только для `souzpir.local`; неверный адрес, userinfo, query, fragment и неподходящий маршрут приводят к отказу без вызова mailer. `app.url` остаётся операторской настройкой канонического домена и порта.

До исправления адресный тест воспроизвёл ссылку на подменённый HTTPS Host. После исправления **4 теста / 46 проверок** прошли в собственной тестовой PostgreSQL: выполнение настоящего `DeliverPassword::handle` с fake mailer, подменённый Host и порт, сохранение канонического HTTPS-порта, согласованный локальный HTTP с портом и отказ при некорректном `app.url`. Реальную доставку не включали. Ограничение старых URL и статус карточки выше сохраняются.
