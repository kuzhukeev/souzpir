- `TelegramManagerMessageTransport`: сам делает HTTP sendMessage (без изменения `HttpTelegramTransport`/`TelegramSender`, они вне scope и не дают статус/код), различает ok / retryable (429, 5xx, обрыв соединения) / терминальный отказ (4xx — чат не найден, бот заблокирован); при успехе пишет `meta.delivery=live` и `meta.telegram_message_id`; при терминальном отказе пишет `delivery_error` без исключения; при retryable — бросает `RuntimeException`. Защита от повторной отправки уже доставленного сообщения. Проверено: `test_retry_on_429_then_success_...`, `test_4xx_failure_is_terminal_without_retry`, `test_transport_does_not_resend_an_already_delivered_message`.
- `DeliverManagerMessage`: `tries=4`, `backoff=[10,30,120]`; после попытки проверяет статус строки и ставит `delivered_at` только если нет ни `delivered_at`, ни `delivery_error`; `failed()` пишет `delivery_error` из исключения после исчерпания попыток. Проверено: `test_failed_hook_persists_error_once_retries_are_exhausted`.
- `DialogMessageController::store`: `meta.delivery` и флеш-текст («…очередь отправки в Telegram.» / «…тестовую очередь.») зависят от живого режима и типа канала диалога. Проверено: `test_dialog_message_flash_and_meta_reflect_live_mode`.
- `TelegramRegistrationController` не менялся — уже вызывает `register()` с `secret_token`/`allowed_updates`, при живой привязке реально шлёт запрос. Проверено: `test_webhook_registration_sends_secret_token_in_live_mode`, `test_webhook_registration_shows_friendly_error_on_telegram_failure`.
- Новых колонок не потребовалось: статус/ошибка хранятся в существующих `messages.delivery_error` и `messages.meta` (jsonb).

Техдолг: статус отправки (retryable/терминальная) определяется прямым HTTP-вызовом внутри `TelegramManagerMessageTransport`, в стороне от `HttpTelegramTransport`/`TelegramSender` (они возвращают только bool, вне scope карточки) — логика запроса к Telegram частично дублируется; стоит вынести общий клиент с детальным результатом отдельной карточкой с решением владельца интерфейса.

Принято по умолчанию: без вопроса владельцу — чисто техническая реализация (retry policy, формат error_code, выбор backoff) не влияет на видимое поведение клиента сверх текста карточки.
