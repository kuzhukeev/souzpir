# Интеграция заявки на смену тарифа для SP-E1-07

Типизированный порт поддержки, команда, результат и статусы описаны в [контракте](../contracts/plan-request.md). Публичный план и активные сессия, организация, бренд, членство, фактическое владение организацией и `billing.manage` проверяются сервером. Запрос с чужим бренд-контекстом, не публичным планом или старой сессией не создаёт данных. Повторный одинаковый ключ возвращает исходный ticket; другой запрос с тем же ключом конфликтует.

`plan_request` хранится отдельно от обращений `support`; сохранение ticket, audit и зарегистрированного события `shell.plan_request.created` происходит в одной транзакции. Событие содержит только ID заявки, получателем подтверждения в кабинете может быть только текущий активный владелец организации с доступом к активному бренду. После commit почтовая доставка через существующий TicketDelivery сообщает `not_configured`, `disabled`, `sent` или `uncertain`. Сообщение в кабинете не является доставкой оператору поддержки.

Проверки на отдельном PostgreSQL `127.0.0.1:55531`, база `souzpir_test_sp_plan_request`, роль `sp_plan_app` без административных прав и отдельный vendor/storage: 8 тестов / 53 assertions нового порта; 24 теста / 192 assertions регрессии поддержки и уведомлений; Pint и `git diff --check`. Использовались `Mail::fake`, fake-очередь и запрет внешних HTTP; реальных писем и запросов не было. Новые проверки включают HTTP middleware/tenant, отказ в правах и при неверном бренде, сессию, отозванную перед запросом, две организации, архив бренда до обработки события, rollback outbox/audit/ticket, повтор по ключу, конфликт ключа, диагностируемую недоступную и неопределённую доставку.

Ограничения: SP-E1-07 ещё должен вызвать порт, передавать стабильный ключ, корректно обработать 403/404/409 и фактическую доставку. Созданная заявка без SMTP может остаться недоступной оператору: головная админка и очередь поддержки не реализованы. Подтверждение `sent` означает подтверждение транспорта, не обработку оператором. Потеря ответа либо неопределённая отправка не инициирует автоматическую повторную внешнюю отправку. Отдельный двухпроцессный тест гонки одинаковых запросов не проводился; сериализация опирается на блокировку организации в `SupportAccess::lock` и уникальный индекс `(organization_id, user_id, submission_key)`.
