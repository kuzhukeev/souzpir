# Интеграция заявки на смену тарифа для SP-E1-07

Типизированный порт поддержки, команда, результат и статусы описаны в [контракте](../contracts/plan-request.md). Публичный план и активные сессия, организация, бренд, членство, фактическое владение организацией и `billing.manage` проверяются сервером. Запрос с чужим бренд-контекстом, не публичным планом или старой сессией не создаёт данных. Повторный одинаковый ключ возвращает исходный ticket; другой запрос с тем же ключом конфликтует.

`plan_request` хранится отдельно от обращений `support`; сохранение ticket, audit и зарегистрированного события `shell.plan_request.created` происходит в одной транзакции. Событие содержит только ID заявки, получателем подтверждения в кабинете может быть только текущий активный владелец организации с доступом к активному бренду. После commit почтовая доставка через существующий TicketDelivery сообщает `not_configured`, `disabled`, `sent` или `uncertain`. Сообщение в кабинете не является доставкой оператору поддержки.

Проверки на отдельном PostgreSQL `127.0.0.1:55531`, база `souzpir_test_sp_plan_request`, роль `sp_plan_app` без административных прав и отдельный vendor/storage: 10 тестов / 75 assertions нового порта; 24 теста / 192 assertions регрессии поддержки и уведомлений; Pint и `git diff --check`. Использовались `Mail::fake`, fake-очередь и запрет внешних HTTP; реальных писем и запросов не было. Проверены HTTP middleware/tenant, отказ в правах и при неверном бренде, сессия, отозванная перед запросом, две организации, архив бренда до обработки события, отдельные ошибки audit и outbox с откатом всей транзакции, повтор по ключу, конфликт ключа, недоступная и неопределённая доставка.

Дополнительно два PHP-процесса с разными активными сессиями и соединениями PostgreSQL одновременно вызывают порт с одним ключом. Тест удерживает блокировку организации, подтверждает по `pg_stat_activity`, что оба процесса ожидают блокировку, и затем освобождает её: получены одна заявка, одна audit-запись, один outbox-event и ровно одна fake SMTP-отправка. Отдельно сценарий повторён три раза успешно; это проверка порта с настоящими транзакциями, не двухпроцессный HTTP-тест.

Ограничения: SP-E1-07 ещё должен вызвать порт, передавать стабильный ключ, корректно обработать 403/404/409 и фактическую доставку. Созданная заявка без SMTP может остаться недоступной оператору: головная админка и очередь поддержки не реализованы. Подтверждение `sent` означает подтверждение транспорта, не обработку оператором. Потеря ответа либо неопределённая отправка не инициирует автоматическую повторную внешнюю отправку.
