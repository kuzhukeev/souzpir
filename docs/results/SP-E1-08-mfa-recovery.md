# Интеграционный кандидат: резервные MFA-коды

Ветка `codex/sp-mfa-recovery` основана на SP-E1-08 и включает main `a4060070a8d428e0b3f8cad8a3fff43072cc272a`. Это кандидат для проверки интегратором, а не завершение SP-E1-08. Очередь и main не менялись.

## Контракт

- Подтверждённый MFA-пользователь с активной сессией и действительным новым TOTP-кодом получает 10 независимых кодов по 128 бит. Показ происходит один раз в ответе JSON `no-store`; в таблице хранится только HMAC. Выпуск нового набора удаляет предыдущий, повышает `auth_version`, сохраняет текущую сессию и аннулирует остальные; отключение MFA удаляет набор.
- TOTP и резервный код проверяются через общий challenge с общей для аккаунта БД-квотой: пять ошибок за 15 минут; состояние и потребление сериализуются блокировкой пользователя. Запись использованного кода обновляется условно, в транзакции вместе с событием аудита `account.mfa.recovery_code_used`. Повышение версии аккаунта инвалидирует старый незавершённый challenge. В случае ошибки после фиксации потребления код не восстанавливается: пользователь применяет следующий.
- Глобальная граница целевых POST заменяет исходный код на HMAC до маршрутизации и удаляет входное поле из Laravel Request и старого ввода. Для выдачи и входа клиент использует `fetch`, а не Inertia-форму; страница создания не передаёт коды через Inertia. Код очищается при уходе со страницы, незавершённые запросы отменяются. Ротация APP_KEY сделает имеющиеся HMAC недействительными, поэтому заранее нужен новый набор при работающем MFA.
- Стандартный выпуск требует `SecureAccountContext`. Дополнительный HTTP допускается только при `APP_ENV=local`, host `souzpir.local`, подтверждённых прямых loopback-адресах и отсутствии forwarding headers по `VerifiedHttps::directLoopback`. Локальная отдельная HTML-страница не использует Inertia/Web Crypto, имеет CSP nonce и `no-store`; она доступна только в том же узком локальном контексте. Для входа резервным кодом действует аналогичная проверка канала. Production и другие хосты через это исключение не открываются.

Тематический набор после правки logout: 12/12, 166 assertions, включая гонку двух процессов за один резервный код и оба порядка гонки выпуска и logout. Полный `FileSessionRaceTest`: 9/9, 145 assertions; его синтетический worker теперь задаёт локальный SERVER_ADDR, нужный для теста MFA.
- Четыре действующих серверных теста Auth challenge: 4/4, 41 assertion. Ранее известный тест enrolment с неустановленным `SERVER_ADDR` не включён в этот адресный прогон.
- Chromium: реальный вход по TOTP, переход из настроек на локальную страницу, выпуск кодов, Back с очисткой и отсутствие кода в history, выход, вход по коду и отказ повторного применения; синтетические пользователь и данные, отдельный PHP-сервер. Также проверен визуальный fixture и искусственный `pagehide`. Скриншот до ввода: `.local/screenshots/mfa-recovery-local.png`.

## Ограничения интеграции

- Браузерный локальный сценарий использует тестовый PHP router, который задаёт известный `SERVER_ADDR`, и отдельный порт; это не доказательство реального окружения OSPanel/Apache. До включения локального исключения в основной работе интегратор должен проверить адреса и forwarding headers фактического запроса.
- Очистка Laravel Request не управляет журналами reverse proxy, веб-сервера, APM, трассировкой или записью тела HTTP и ответа на других уровнях. Для реального развёртывания необходимо подтвердить исключение POST body и тела ответа этих маршрутов из инфраструктурных логов и диагностик. Не заявляется защита от расширений браузера, DevTools или скомпрометированного клиента.
- Новые общие таблицы `mfa_recovery_codes` и `mfa_challenge_limits`, глобальная middleware-граница, объединённый login challenge и файлы общей аутентификации требуют отдельного ревью и согласования интегратором. Нужно оценить миграцию и порядок развёртывания на всех PHP-процессах, роль фоновых процессов и поведение при смене APP_KEY; в main не переносить без проверки.
- Локальное создание **нового MFA-секрета** по-прежнему запрещено без Web Crypto/HTTPS; разрешение местного HTTP относится только к описанному безопасному пути резервных кодов. Это не реализация ежедневной сводки, тихих часов или их runtime-доставки.

## Гонка выдачи и выхода: общий контракт Auth

Два PHP-процесса с одним снимком сессии выполняют настоящий `MfaRecoveryController::issue` через `ProfileAccess::run` и `SessionController::destroy`. Первый остаётся внутри внешней транзакции после завершения своего действия; по `pg_locks` подтверждено, что второй уже ожидает блокировку. При первом logout выдача отвергается, кодов и события выдачи нет; при первой выдаче сохраняются десять хешей и одно событие аудита с правильными actor/organization, после чего logout отзывает эту сессию. Повторные проверки lease со старой и с новой версиями после выхода отклоняются. Тест выполняется не полным параллельным HTTP-транспортом, а с двумя изолированными приложениями и синтетическими server-side snapshot сессии; отдельно проверен POST-маршрут logout через Laravel HTTP kernel.

До исправления при первой выдаче logout ошибочно отклонялся из-за старой `auth.version`, и актуальный lease оставался активным. `POST /logout` теперь исключён только из глобальной `EnforceAuthVersion`: он сохраняет `auth`, CSRF, `AuthenticateSession` и вызывает отдельный `withinLogout` с блокировками и проверкой hash текущей сессии, владельца, срока, отзыва, актуальной версии самого lease и remember fingerprint. Более старая версия snapshot даёт право только отозвать этот же активный lease. Для других действий `withinActive` остаётся строгим. Проверены отказ отзыва чужого пользователя, невалидные версии, неактуальный и истёкший lease и неверный remember fingerprint. Это изменение общего Auth, требующее самостоятельного ревью интегратора.
