# SP-E1-10 — промежуточный результат

## Проверенный срез API-ключей после обновления main

В актуальном main уже реализованы управление ключами бренда и реальный защищённый `GET /api/v1/brand`; повторный guard не добавлялся. Проверено настоящее UI → HTTP → сохранение → bearer API → отзыв на отдельной PostgreSQL с database-сессиями и блокировками: ключ с `read` возвращает свой бренд, подстановка другого бренда даёт 404, после отзыва ключ даёт 401; ключ только с `leads` получает 403 на чтение бренда. Повторный запрос секрета возвращает 404, открытый ключ не попадает в историю и браузерные хранилища. Браузерные trace, video, снимки ошибок и подробные снимки страницы выключены. Реальных отправок нет.

После обновления main два существующих теста переключения бренда выдавали 409 из-за подмены сессии; они переведены на настоящий `/brand/switch`, сохранив проверку изоляции и одноразового раскрытия. Перед миграциями этих тестов добавлена проверка тестовой БД. Пройдено: 9 адресных серверных тестов, 101 assertion; один настоящий браузерный сценарий с двумя ключами; TypeScript, ESLint, Pint и PHP lint. На текущий момент seller `turn` и API лидов не реализованы, вебхуки и внешние отправки в этом срезе не включались; полная SP-E1-10 не завершена. В ветке ранее сохранены отдельные незавершённые изменения транспорта вебхуков — этот срез их не проверял и не объявляет готовыми.

Статус: реализация не прошла полную приёмку. Не считать задачу готовой к интеграции до устранения блокирующих контрактов ниже.

## Защита трассировки при ошибке шифрования

При ошибке шифрования секрета вебхука исходное исключение отбрасывается: наружу выходит общее исключение без `previous`. Регрессионный тест при `zend.exception_ignore_args=0` подтверждает, что секрет присутствует в аргументах трассировки исходной ошибки, но отсутствует в новой трассировке; создание вебхука и receipt откатывается.

Проверены остальные операции с секретами и отзыв сессии: новых подтверждённых дефектов не обнаружено. Существующие тесты отдельно проверяют отзыв после первоначального допуска, параллельное получение секрета и гонку logout с защищённым действием; отдельного двухпроцессного теста гонки logout именно с выдачей секрета нет.

Проверки после исправления: PHPUnit `tests/Feature/Shell/Integrations` с `zend.exception_ignore_args=0` — **40 тестов, 287 assertions**, включая регрессию и тест отзыва сессии; Pint для двух изменённых PHP-файлов — успешно. Перед миграциями проверены basePath, PostgreSQL `127.0.0.1:56410`, база `souzpir_test_sp_e1_10`, ограниченная роль и отдельный storage. Vendor — обычный каталог; внешние отправки не выполнялись. Новые скриншоты не требуются для серверного исправления.

## Что выполнено

- Страница подключений читает `channel_accounts` в текущей организации и бренде; статусы unconfigured/disabled/planned и неизвестные коды выводятся по-русски, незавершённые каналы отмечены «Скоро».
- Ключи бренда: создание, SHA-256 хеш, маска, выбранные abilities, отзыв, проверка прав и аудит. Ключ создаётся, но ещё не обслуживает запросы `/api/v1/*`; интерфейс прямо предупреждает об этом.
- Вебхуки: HTTPS, словарь пяти событий из registry, зашифрованный секрет, HMAC, изоляция по бренду, аудит, не более десяти строк истории. Для доставки проверяется публичный DNS, IP фиксируется на время запроса, redirects запрещены. Отправка по умолчанию выключена; зарегистрирована независимая команда `integrations:webhooks-drain` без запуска по расписанию.
- Одноразовые секреты не передаются в Inertia props: создание и POST `integrations/api/secrets` требуют HTTPS либо непосредственный loopback в local/testing без прокси. Host сам по себе не подтверждает локальный доступ: проверяются также socket `REMOTE_ADDR` и `SERVER_ADDR`. Ответы no-store.
- Flash зашифрован и аутентифицирован даже при `session.encrypt=false`, привязан к типу секрета, session ID, actor/organization/brand. Выдача перепроверяет действующую сессию, права, membership и бренд под блокировками в порядке session → user → organization → membership → brand. Создание и выдача не разрешены внутри внешней транзакции.
- Таблица `integration_secret_receipts` хранит только хеш случайного nonce, срок и факт получения. Запись создаётся в транзакции ключа и атомарно погашается перед выдачей; восстановление старого flash не позволяет получить секрет повторно. Настройка вебхуков сейчас закрыта. Истёкшие записи удаляются отдельной ограниченной командой, а не во время создания ключа; подробности — в `docs/modules/E1-10.md`.
- Для показов требуется server-side session и общий atomic lock store. В production разрешены database (кроме SQLite), Redis, Memcached, DynamoDB; cookie и локальные/in-memory locks запрещены. В явно односерверном local окружении файлы допускаются только с `INTEGRATIONS_SINGLE_NODE_LOCKS=true`. Оператор должен обеспечить одинаковые общие хранилища для всех узлов; одни имена драйверов не проверяют сетевую топологию. Массивные драйверы разрешены исключительно в процессе PHPUnit с `APP_ENV=testing`.
- Экран корпоративных уведомлений честно отключён, поскольку действующий runtime не обслуживает этот сценарий.

## Запрос интегратору — блокеры полной приёмки

1. Владельцу bootstrap/tenancy/API: предоставить установленный и совместимый Sanctum (общие composer manifest/lock принадлежат другому владельцу), guard `auth:sanctum`, `tenant.token`, проверку abilities и согласованную поддержку tokenable=Brand. Сейчас `FeatureRegistry` ссылается на отсутствующие guard/alias, E5-03 ещё не реализован. Нужно проверить настоящий endpoint `/api/v1/leads`: отсутствие `leads` → 403; отозванный ключ → 401. В scope SP-E1-10 менять общий bootstrap/модели/lock нельзя.
2. Владельцам E0-04/E3-04/E5-01: согласовать брендовый storage для Telegram-чата и почтовых адресатов, company-recipient delivery/outbox и проверяемый challenge/inbound Telegram flow. `channel_accounts` запрещает тип `telegram_notify`; личные `notification_settings`/`notification_deliveries` требуют user_id, а их runtime доставляет только личным адресатам. Контракт `notifications.router` уже занят E6-07. Нужен реальный тест `seller.conversation.handed_off` → чат компании и передача докладов, а не искусственная отправка или неиспользуемые настройки.
3. Выделить операторский механизм запуска `integrations:webhooks-drain` или согласованный subscriber для committed outbox. Только включения флага доставки недостаточно. При аварии после установки статуса `sending` исход неопределён; автоматическое восстановление не реализовано. Для внешних вызовов нужно отдельное операторское разрешение.

## Дополнительная проверка транспорта перед интеграцией

Обнаружен и закрыт обход: Laravel `TrustProxies` автоматически доверяет peer при Host `*.on-forge.com` / `*.on-vapor.com`, поэтому клиентский `X-Forwarded-Proto` мог привести к ошибочному `isSecure()`. Проверка теперь использует серверный признак TLS либо явно настроенные конкретные IP/CIDR доверенных прокси без wildcard/универсальных подсетей. Локальный HTTP разрешён только при двух физических loopback адресах и отсутствии proxy-заголовков; `souzpir.local` на локальном компьютере поддерживается, Host сам по себе не служит доказательством. Исходные server-поля также проверяются, если middleware удалил `X-Forwarded-Host`.

Новые и затронутые серверные проверки: 20 тестов, 96 assertions, Pint. Есть тест настоящего `TrustProxies` и запросов на все три secret-маршрута, native TLS, explicit CIDR, wildcard, неоднозначных заголовков и local/production. Тесты выполнены на выделенном PostgreSQL `souzpir_test_sp_e1_10`, перед миграциями проверяются checkout, runtime и подключённая база; сетевых отправок нет. Общие функциональные ограничения из предыдущего раздела остаются.

## Сверка идентичности outbox

Consumer сверяет `event_id`, `organization_id` и `brand_id` входящего envelope с заблокированной записью outbox до выбора получателей. При несовпадении транзакция откатывается, событие не помечается обработанным и доставка не создаётся. Тест сначала воспроизвёл ошибку старой реализации, затем проверил отказ при подмене каждого поля, отсутствие jobs и внешней отправки. Вся группа вебхуков прошла: **10 тестов, 89 проверок** на выделенной тестовой БД, HTTP и очередь подменены. Временной порядок включения подписки по-прежнему не доказан: включать реальную доставку нельзя до общего контракта и проверок конкурентных транзакций.

## Временная блокировка исходящих вебхуков

До появления общего проверенного снимка подписок и отдельной квитанции ручного теста отправка отключена жёстко: даже включённый конфигурационный флаг не открывает сетевой путь. Outbox не помечает события потреблёнными и не создаёт pending-доставки; drain явно возвращает ошибку. Ранее созданные pending и ручные test-строки не отправляются даже при прямом вызове сервиса. На странице кнопка теста недоступна и показано предупреждение. Исторические тесты сетевого теста и его подписи временно пропущены, а не представлены как действующая возможность. Восстановление отправок требует отдельно реализовать и проверить контракт, получить операторское разрешение и повторить тесты.

На отдельной тестовой базе группа интеграций: 42 теста, 291 assertion, из них 4 намеренно пропущены до восстановления безопасной доставки. Проверены отсутствие новых доставок, потребления события, job и HTTP-запроса, а также сохранение старых pending без отправки; Pint и `git diff --check` прошли. Живых вызовов не выполнялось.

## Отображение состояния чтения бренда через API

Страница управления ключами сообщает о настроенном `GET /api/v1/brand` отдельно от недоступных API диалогов, лидов и исходящих вебхуков. Статус виден только пользователю с существующим правом `integrations.write`. Положительный статус требует защищённого транспорта, зарегистрированного ожидаемого маршрута с guard и правом `read`, Sanctum с моделью брендового токена, доступной схемы и поддерживаемого ограничителя; backend ограничителя проверяется чтением без расходования квоты. Ошибка проверки даёт отрицательный статус.

Это проверка текущей конфигурации, а не гарантия доступности сервера или прав конкретного ключа: фактический запрос по-прежнему проходит все защитные проверки и лимиты. Никаких API-ключей или секретов на страницу статуса не передаётся. Вебхуки, диалоги и лиды этим срезом не включаются.

Адресные проверки: 8 PHP HTTP-тестов, 121 assertion, включая успешный настоящий bearer-вызов, отключённый и недоступный limiter, непригодный путь файлового кэша, небезопасный транспорт, изменённый маршрут/guard и отказ участнику без прав; браузерный HTTP→страница для обоих состояний; 10 UI fixture-проверок с темами и размерами 1440/1024/390; отдельные клавиатура и axe. TypeScript, ESLint, Pint прошли. Несекретный screenshot положительного состояния: `.local/screenshots/e1-10/api-brand-read-configured-390.png`; отрицательное состояние: `.local/screenshots/e1-10/api-neutral-390.png`. Использовалась отдельная PostgreSQL в новом worktree на 127.0.0.1:58451, внешних отправок не было.
