# SP-E5-01M — виджет: первое сообщение на свежем бренде без базы знаний

- Режимы «Автономно»/«Подсказки», запуск runtime без сессии менеджера и автоматические ответы уже реализованы в SP-E5-02C (`WidgetInboundRuntime` ведёт тот же защищённый pipeline, что API/session-каналы); визуальная сверка с макетом сделана там же (скриншот `widget-chat-1440.png`). Этой карточкой закрыт только этап 20:00 из текста карточки — блокер сценариев 6–8 сквозной приёмки.
- Проверено: `WidgetInboundRuntime::completeBotTurn` — при падении `FollowupCoordinator::orchestrateTurn` (нет базы знаний/релиза на свежем бренде) или незавершённом ходе диалог переводится в `manager`-режим (`handoffToManager`): турн фиксируется как `failed` (без исходящих сообщений, как и `suppressed`), сообщение посетителя остаётся сохранённым, `/widget/message` отвечает 201 без `reply` вместо 503. Повтор с тем же `idempotency_key` возвращает тот же результат (без повторного AI-хода).
- Тесты (проверено `php artisan test`): новый `tests/Feature/Seller/Channels/Widget/WidgetFreshBrandE501MTest.php` — 2 теста: свежий бренд без знаний → 201 без reply, диалог `manager`, турн `failed`, 1 сообщение в БД, идемпотентный повтор; бренд с загруженной базой знаний (`seedProtected`) → бот всё равно отвечает (regression). Регрессия: `tests/Feature/Seller/Channels/Widget/*` (10 тестов) и `tests/Feature/Seller/Runtime/*` (всего 18 тестов, 303 проверки) — зелёные. Pint — зелёный.
- Права/изоляция брендов отдельно не перепроверялись (поведение не менялось, покрыто ранее зелёными `WidgetSessionTest`/`WidgetContactTest`).

## Остаток
- Нет видимых пунктов макета вне scope; задача была узко про обработку ошибки runtime, без изменений интерфейса.

## Техдолг
- Нет новых; старый техдолг SP-E5-02C (автооткрытие по `delay_seconds` без AI-хода, fewshot `open_greeting_widget`, очистка просроченных widget-сессий) не менялся.

## Принято по умолчанию
- При недоступном бот-ходе турн помечается статусом `failed` (уже предусмотрен в `EloquentConversationRepository`/`TurnOutcome`, но ранее не использовался production-кодом); ответ клиенту — как у `suppressed` (201, без `reply`), раз контроллер уже принимает оба статуса одинаково.
