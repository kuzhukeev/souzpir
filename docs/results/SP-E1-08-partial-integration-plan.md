В общем `AuthSessionRegistry` сохранён ровно один дополнительный `SessionRegistered` для профиля; отдельной копии logout нет. Код и миграции E1-08 ещё не интегрированы в main. Этот документ — план, а не разрешение менять рабочую БД или конфигурацию.

После merge реестра дополнительно прошли Auth logout + MFA + Billing + Notifications: **38 / 505**, валидатор контрактов — 120 таблиц без ошибок, а браузерный локальный сценарий с Billing и повторным входом — **1/1** на тестовом PHP router. Реальная БД и конфигурация OSPanel не менялись.

**Рекомендация: отложить включение на рабочем сайте**, пока не закрыты проверка журналирования MFA, фактического OSPanel и безопасное отображение недоступных внешних каналов. В текущей архитектуре `config/features/E1-08.php` регистрирует слушатель и routes автоматически; отдельного общего feature flag для безопасного включения только экрана профиля сейчас нет. Один лишь скрытый пункт меню не защищает прямые маршруты и не отключает listener. Перед поэтапным запуском нужен согласованный server-side флаг/граница для незавершённых частей либо интеграция целого кода при выполнении всех перечисленных условий.

## Последовательность

1. Интегратору проверить итоговую ветку на актуальном main, ownership и `docs/contracts/validate.py`, повторить Auth/MFA/Billing и privacy-тесты в собственной изолированной БД. Обновить принадлежащие интегратору generated types/translations и проверить их генератором: текущий `scripts/generate-types/generate.php --check` завершается на устаревшем `translations.ts`, последующие файлы в этом запуске не проверены. Не считать устаревшие `docs/results/SP-E1-08.md` и старые формулировки `docs/modules/E1-08.md` актуальными по состоянию recovery/лимитера — их переписать по итоговому коду.
2. До запуска **любого нового PHP-процесса** применить в целевой среде все три миграции E1-08 после проверки плана миграций и резервной копии: `180000_create_mfa_recovery_codes` (`mfa_recovery_codes`, `mfa_challenge_limits`), `180800_e1_08_create_profile_tables` (`profile_preferences`, `profile_email_changes`, `profile_telegram_accounts`, `profile_telegram_links`, `profile_session_details`), `190108_e1_08_create_profile_test_notifications` (`profile_test_notifications`). Предварительные users/organizations/brands/auth_session_registry должны существовать. Новые группы поставляются как одна совместимая версия schema+code, а не включаются частичным выбором миграций.
3. Причина порядка: login создаёт `auth_session_registry` и синхронно вызывает listener `CaptureSessionDetails`, которому нужна `profile_session_details`. Новый challenge обращается к `mfa_challenge_limits` даже без резервных кодов; отключение MFA обращается к `mfa_recovery_codes`. Код раньше миграций может нарушить существующий вход. Проверить существующие сессии без записей details: `leftJoin` оставляет их рабочими, но исторические IP/устройства не восстанавливаются.
4. После миграций и согласованного обновления всех процессов проверить routes/config cache и сборку. Не откатывать миграции автоматически после создания пользовательских данных: потребуется отдельный план сохранения/отката. `APP_KEY` должен оставаться общим и неизменным: его замена инвалидирует MFA HMAC и затрагивает другие зашифрованные данные.

## Маршруты и доступ

- В реальном `navigation.json` «Настройки» сейчас ведут на `/settings/notifications`; E1-08 предоставляет этот адрес как совместимый alias страницы уведомлений. Из неё внутренние вкладки ведут на `/profile`, `/profile/notifications`, `/profile/security`; старые `/settings/profile` и `/settings/security` также существуют. В текущем `CabinetLayout` имя пользователя — статический элемент, отдельного перехода на профиль там нет. Перед выпуском добавить явный доступный пункт «Профиль» к `/profile` или проверенный dropdown в общей оболочке, сохранить корректные разрешения `profile.own`, проверить keyboard/390 px и отсутствие ссылок на demo-preview.
- Вкладка безопасности `/profile/security` использует защищённую историю; создание/просмотр нового секрета MFA требуют HTTPS или настоящего loopback с Web Crypto. Исключение локального HTTP пользователя на `souzpir.local` относится только к выдаче и вводу **резервных** кодов через отдельный no-store путь `/profile/security/mfa/recovery-local`/POST `/profile/security/mfa/recovery`: `APP_ENV=local`, точный host и `VerifiedHttps::directLoopback` без forwarding. На этом hostname по HTTP новый MFA-секрет включить пока нельзя; не обещать пользователю обратное.
- Браузерная проверка была на отдельном PHP test router с заданным SERVER_ADDR. До использования локальной функции проверить реальный `REMOTE_ADDR`, `SERVER_ADDR` и forwarding на OSPanel без вывода секретов. Production/внешние адреса должны использовать проверенный HTTPS и доверенный proxy; не расширять локальное исключение.

## Уведомления и отложенные функции

- Общие тихие часы и ежедневная личная сводка **не работают**: `timingAvailable=false`, UI «Скоро». Нужны согласованный runtime-контракт, отложенная доставка по получателю/каналу, часовой пояс и ежедневное время пользователя, тесты гонок/повторов и задача интегратора. Сводка только продавца не заменяет общую.
- Смена email не готова к рабочей доставке: `EmailChanges::available()` разрешает её только в `testing` с fake sender. Оставить `PROFILE_EMAIL_CHANGE_ENABLED=false`; URL подтверждения содержит bearer и требует отдельной безопасной схемы, исключения утечки в логи, реальной проверки SMTP и контроля повторов. Не включать её одним изменением конфигурации.
- Внешние тестовые email/Telegram используют общий `NOTIFICATIONS_EXTERNAL_ENABLED` и реальные adapters, если они включены. Не менять общий флаг вслепую, поскольку он затрагивает другие модули: до частичного запуска проверить фактическую конфигурацию и добавить при необходимости отдельный feature gate. Email-переключатели матрицы сейчас могут сохранять предпочтение даже при недоступном транспорте; перед показом пользователям обозначить реальную недоступность доставки и согласовать поведение сохранения. Тестовый канал «кабинет» можно проверить без внешних отправок.
- Telegram: без настроенных bot username/secret подключение недоступно; реальные webhook/доставка не проверялись. Проверить безопасную выдачу capability и отдельное согласование внешнего канала до включения; неизвестный результат не отправлять повторно автоматически.

## Обязательные проверки перед включением

- Убедиться, что веб-сервер, proxy, APM и обработчики ошибок не сохраняют тела запросов/ответов MFA и capability; Laravel boundary не контролирует внешние логи. Проверить локальный и production путь без реальных секретов; Octane/Swoole не проверен из-за работы с `$_POST`, не включать этот runtime до отдельного решения.
- Повторить настоящие пользовательские сценарии без отправок: профиль и аватар, matrix c реальными permissions/brands, пароль и отзыв устройств, двухфакторный вход, одноразовые коды, logout/remember, переходы Back/Forward, 1440/1024/390 и три темы. Проверить production HTTPS и непрохождение поддельных заголовков/внешнего peer. Фактические SMTP/Telegram отправки — отдельный операторский этап.
- Миграции, конфигурацию сервера и рабочую БД в рамках подготовки плана не менять; до готовности перечисленных условий не переносить E1-08 в состояние «Готово» и не выдавать незавершённые каналы за работающие.
