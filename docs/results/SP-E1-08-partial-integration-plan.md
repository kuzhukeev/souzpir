# План частичного подключения профиля и MFA

## Состояние кандидата

Ветка `codex/sp-mfa-recovery` включает принятый logout из main `584e2b3` и реестр main `bc797a4`. В общем `AuthSessionRegistry` сохранён ровно один дополнительный `SessionRegistered` для профиля; отдельной копии logout нет. Код и миграции E1-08 ещё не интегрированы в main. Этот документ — план, а не разрешение менять рабочую БД или конфигурацию.

После merge logout прошёл общий изолированный прогон Auth + MFA + Billing: **71 тест / 985 проверок**. После merge реестра дополнительно прошли Auth logout + MFA + Billing + Notifications: **38 / 505**, валидатор контрактов — 120 таблиц без ошибок, а браузерный локальный сценарий с Billing и повторным входом — **1/1** на тестовом PHP router. Реальная БД и конфигурация OSPanel не менялись.

После добавления gating объединённый адресный прогон Auth/MFA/Profile/Billing прошёл **74 теста / 958 проверок**, включая последовательное выключение/включение флага, отсутствие и частичную потерю схемы, fallback TOTP, единый лимит и route/config cache. Два старых Auth-теста используют HTTPS для выдачи MFA-секрета; ограничение runtime не ослаблено. TypeScript, ESLint и production build прошли. Изолированный Chrome + PHP test router: **1/1**, в том числе локальная одноразовая выдача и повторный вход с резервным кодом. Использовались синтетические записи, отдельная PostgreSQL, fake-транспорты; реальных отправок не было. Скриншот `.local/screenshots/mfa-recovery-local.png` не содержит кодов. Результат test router не подтверждает настройки настоящего Apache/OSPanel.

Для исходной базы `bc797a4` также воспроизведён реальный браузерный переход в **одном синтетическом каталоге** с file session/cache: старая MFA-сессия → три E1-08 миграции при работающем старом PHP → новый код с flag off/on/off → старый код. Сессия и синтетическая запись `profile_preferences` сохранились; браузер **1/1**. Перезапуск PHP test server делался между версиями: доступность при настоящей смене процессов не доказана. Гонки `FileSessionRaceTest` на файловом cache: **10 / 156**, отдельная межпроцессная file-cache блокировка — **1 / 9**. Внешних отправок не было. Возврат старого кода не удаляет данные новых таблиц, но старый код не умеет принимать уже выданные резервные коды; до такого отката нужен отдельный план доступа пользователей. Старые Vite-ассеты следует сохранить при выкладке новой сборки: обычная сборка очищает каталог результата, а открытые вкладки могут запрашивать прежние файлы.

**Рекомендация: отложить включение на рабочем сайте**, пока не закрыты проверка журналирования MFA, фактического OSPanel и безопасное отображение недоступных внешних каналов. Кандидат теперь имеет серверный флаг `PROFILE_SETTINGS_ENABLED`, по умолчанию выключенный. Маршруты остаются зарегистрированными для route cache, но при выключенном флаге отвечают 404, при включённом флаге и неполной схеме — 503; listener и ранее поставленные задания не обращаются к отсутствующей схеме. Подпункт меню отключается, выдача и использование резервных кодов закрыты. Обычный вход и TOTP работают без таблиц E1-08; после повторного включения MFA старые резервные коды не восстанавливаются. Это граница доступности, а не доказательство готовности всего профиля.

## Последовательность

1. Интегратору проверить итоговую ветку на актуальном main, ownership и `docs/contracts/validate.py`, повторить Auth/MFA/Billing и privacy-тесты в собственной изолированной БД. Обновить принадлежащие интегратору generated types/translations и проверить их генератором: текущий `scripts/generate-types/generate.php --check` завершается на устаревшем `translations.ts`, последующие файлы в этом запуске не проверены. Не считать устаревшие `docs/results/SP-E1-08.md` и старые формулировки `docs/modules/E1-08.md` актуальными по состоянию recovery/лимитера — их переписать по итоговому коду.
2. С флагом `false` можно развернуть код до миграций, но не включать функциональность. После проверки плана и резервной копии оператор применяет все три миграции E1-08: `180000_create_mfa_recovery_codes` (`mfa_recovery_codes`, `mfa_challenge_limits`), `180800_e1_08_create_profile_tables` (`profile_preferences`, `profile_email_changes`, `profile_telegram_accounts`, `profile_telegram_links`, `profile_session_details`), `190108_e1_08_create_profile_test_notifications` (`profile_test_notifications`). Предварительные users/organizations/brands/auth_session_registry должны существовать. Readiness проверяет записи миграций и необходимые столбцы всех восьми таблиц; она **не доказывает** правильность типов, индексов и ограничений, поэтому оператор отдельно проверяет миграции и целостность схемы.
3. Завершить старые PHP- и queue-процессы и развернуть одну версию на всех узлах; переход не обеспечивает атомарности между старыми и новыми версиями. Лимит MFA использует общий cache и, когда доступна таблица лимитов, также БД. Нужен общий cache store для всех процессов/узлов, включая период без миграций. Проверить конфигурацию cache и блокировки отдельно. Существующие сессии без details продолжают работать; исторические IP/устройства не восстанавливаются.
4. После миграций, проверки готовности и отдельного решения о запуске установить `PROFILE_SETTINGS_ENABLED=true`, пересобрать config cache и перезапустить процессы. Route cache можно сохранить: guard проверяется на каждом запросе. При повторном выключении остановить/вычистить выполняющиеся процессы; уже начатая внешняя отправка не может быть отозвана флагом. Задания E1-08, начавшиеся уже после выключения или при неполной схеме, завершаются ошибкой без отправки и требуют операторского решения о повторной постановке. Не откатывать миграции автоматически после создания пользовательских данных: потребуется отдельный план сохранения/отката. `APP_KEY` должен оставаться общим и неизменным: его замена инвалидирует MFA HMAC и затрагивает другие зашифрованные данные.

## Конкретный операторский порядок schema-first

Этот раздел не запускает операции и не разрешает их автоматически. Считать старой версией только проверенный интегратором SHA, присутствующий в основном checkout, а не просто `fd7b844`: после дальнейших merge зависимости и объём схемы могут измениться. Каждый переход остановить при неожиданном результате. Данные доступа и значения `APP_KEY`, токены, HTTP-тела и секреты не выводить в консоль или логи.

1. В отдельном сборочном каталоге интегратор объединяет и проверяет финальный кандидат, включая registry, навигацию и generated-файлы. Сверить `composer.json`/`composer.lock` и `package.json`/`package-lock.json` с фактическим baseline. Относительно `fd7b844` кандидат не меняет lock-файлы; этот baseline **уже требует** `laravel/sanctum` из своего lock. Если текущий vendor не соответствует lock, заранее выполнить `composer install --no-interaction` в отдельной сборке, проверить `composer check-platform-reqs`; production-сборку при необходимости создавать с `--no-dev`. Composer-скрипт `post-autoload-dump` запускает `package:discover`, поэтому его нельзя считать чистым копированием файлов. Не подменять `vendor` junction/symlink другой ветки, не выполнять `composer update` и не устанавливать зависимости в работающий каталог во время запросов.
2. До сборки frontend интегратор выполняет из подготовленного checkout `php scripts/generate-types/generate.php`, проверяет diff четырёх shared файлов `resources/js/types/generated/{data.ts,translations.ts,permissions.ts,routes.d.ts}`, фиксирует согласованный результат и повторяет команду с `--check`. Затем `npm ci`, typecheck/lint и `npm run build` из зафиксированного lock; сборка выполняется вне работающего `public/build`. Предыдущие страницы могут запрашивать старые хэшированные JS/CSS после открытия вкладки: скопировать новые ассеты с сохранением старых, новый manifest переключить только вместе с совместимым backend; не выполнять штатный Vite build прямо в обслуживаемом каталоге. Доступность старых ассетов и согласованность asset-version проверить отдельно — атомарность выкладки на Windows/OSPanel ещё не доказана.
3. Навигация принадлежит интегратору: в `resources/js/components/navigation/navigation.json` оставить `settings` → `/settings/notifications` и permission `profile.own`; добавить видимый пункт «Профиль» → `/profile` с `profile.own` и доступной иконкой `UserRound`, либо реализовать dropdown профиля в общей оболочке. В `Sidebar.tsx` распространить уже существующую проверку `profileSettingsAvailable` на все новые пункты E1-08: при `false` они не должны оставаться активными ссылками из-за присутствующих в Ziggy зарегистрированных маршрутов. Протестировать owner/admin/editor/viewer, клавиатуру и мобильный вид; не подменять `/settings/data` и другие общие ссылки. Сгенерированные общие типы и перевод подписи изменить штатным генератором после согласования.
4. Снять проверенную резервную копию целевой PostgreSQL и отдельно сохранить перечень применённых миграций, версию кода/lock, `.env`, `.local/runtime` (включая file sessions/cache), конфигурацию OSPanel и активные процессы; не выводить содержимое секретных файлов. Доказать имя, хост и роль целевой БД независимой read-only проверкой и проверить восстановление резервной копии на отдельной базе. Если бэкап/восстановление не подтверждены, миграции не запускать. Не вызывать `migrate:fresh`, `migrate:rollback`, `db:wipe` или очистку session/cache.
5. Старый проверенный код продолжает работать. Сверить по SHA-256 и поместить **только** три миграции E1-08 из готового candidate в отдельный staging-каталог вне загружаемых файлов; проверить имена и содержимое. Из действующего checkout со старым vendor и тем же `.env` сначала выполнить `infra/osp/php.ps1 artisan migrate --pretend --realpath --path=<абсолютный_путь_к_staging_миграциям> --force`, проверить SQL и ожидаемые три создаваемые схемы, затем ту же команду без `--pretend`. Сверить таблицу `migrations`, полную структуру таблиц, FK, unique/check индексы и отсутствие других изменений; не считать проверку одного только набора столбцов доказательством корректности. Тест с `fd7b844` проверяет именно вызов через старый код и `--realpath`, но будущий baseline требует повторной проверки.
6. Оставить `PROFILE_SETTINGS_ENABLED=false`, `PROFILE_EMAIL_CHANGE_ENABLED=false`, не включать новые внешние подключения. В том же `C:/OSPanel/home/souzpir.local` сохранить путь runtime, session cookie, шифрование и тот же `APP_KEY`; не стирать `.local/runtime`. Обновить код и подготовленный vendor совместимым способом, исключающим смешанные версии при обработке запросов, обновить route/config cache и package discovery, завершить старые PHP/queue-процессы и сбросить OPcache согласно реальной конфигурации OSPanel. Общий file cache на одном узле должен указывать на прежний каталог; другое размещение создаст отдельный лимит MFA. Включить новую сборку с сохранёнными старыми ассетами. Конкретный способ согласованного переключения процессов без краткого простоя пока не доказан: не обещать zero downtime и не смешивать старые/новые workers до такой проверки.
7. До включения проверить существующую сессию, новый login/TOTP и logout; `/profile` и alias настроек должны быть 404, а скрытые пункты не кликабельны. Проверить API-ключи, прямой/поддельный прокси и запрет неготового webhook с искусственными данными. Записать статус миграций/readiness и состояние очереди без payload. Только после всех проверок и отдельного операторского решения задать `PROFILE_SETTINGS_ENABLED=true`, пересобрать config cache и перезапустить процессы; проверить `/profile`, `/profile/security`, `/profile/notifications`, tenant и права. Смена email, общие тихие часы/сводка и внешняя доставка остаются недоступными/неподтверждёнными, как описано ниже.

### Откат

- Первый вариант: выставить `PROFILE_SETTINGS_ENABLED=false`, пересобрать config cache и заменить/перезапустить все соответствующие PHP/queue-процессы, не удаляя таблицы, сессии, кеш, ключи и сохранённые настройки. Проверить прежнюю сессию и новый TOTP-вход, 404 профиля и отсутствие новых внешних отправок. Уже начатую отправку нельзя отозвать конфигом; остановленные/ошибочные задачи изучаются оператором по неприватным идентификаторам до повторного запуска.
- Если требуется возврат предыдущего backend: до переключения подтвердить, что все пользователи MFA имеют работающий TOTP или согласованный восстановительный путь. Старый код не поддерживает резервные коды новой версии, хотя хеши и предпочтения сохраняются в БД. Вернуть совместимый прежний код, vendor, manifest и route/config cache, сохранив неизменными данные, runtime, cookie и `APP_KEY`; проверить старую сессию, новый вход и API ключи. Повторно включать E1-08 только на совместимом коде после проверки схемы и невыполненных заданий. Восстановление всей БД из бэкапа без анализа уничтожит изменения после бэкапа и не является обычным откатом релиза.

## Маршруты и доступ

- В реальном `navigation.json` «Настройки» сейчас ведут на `/settings/notifications`; E1-08 предоставляет этот адрес как совместимый alias страницы уведомлений. Из неё внутренние вкладки ведут на `/profile`, `/profile/notifications`, `/profile/security`; старые `/settings/profile` и `/settings/security` также существуют. В текущем `CabinetLayout` имя пользователя — статический элемент, отдельного перехода на профиль там нет. Перед выпуском добавить явный доступный пункт «Профиль» к `/profile` или проверенный dropdown в общей оболочке, сохранить корректные разрешения `profile.own`, проверить keyboard/390 px и отсутствие ссылок на demo-preview.
- Вкладка безопасности `/profile/security` использует защищённую историю; создание/просмотр нового секрета MFA требуют HTTPS или настоящего loopback с Web Crypto. Исключение локального HTTP пользователя на `souzpir.local` относится только к выдаче и вводу **резервных** кодов через отдельный no-store путь `/profile/security/mfa/recovery-local`/POST `/profile/security/mfa/recovery`: `APP_ENV=local`, точный host и `VerifiedHttps::directLoopback` без forwarding. На этом hostname по HTTP новый MFA-секрет включить пока нельзя; не обещать пользователю обратное.
- Браузерная проверка была на отдельном PHP test router с заданным SERVER_ADDR. До использования локальной функции проверить реальный `REMOTE_ADDR`, `SERVER_ADDR` и forwarding на OSPanel без вывода секретов. Production/внешние адреса должны использовать проверенный HTTPS и доверенный proxy; не расширять локальное исключение.

## Уведомления и отложенные функции

- Общие тихие часы и ежедневная личная сводка **не работают**: `timingAvailable=false`, UI «Скоро». Нужны согласованный runtime-контракт, отложенная доставка по получателю/каналу, часовой пояс и ежедневное время пользователя, тесты гонок/повторов и задача интегратора. Сводка только продавца не заменяет общую.
- Смена email не готова к рабочей доставке: `EmailChanges::available()` разрешает её только в `testing` с fake sender. Оставить `PROFILE_EMAIL_CHANGE_ENABLED=false`; URL подтверждения содержит bearer и требует отдельной безопасной схемы, исключения утечки в логи, реальной проверки SMTP и контроля повторов. Не включать её одним изменением конфигурации.
- Внешние тестовые email/Telegram используют общий `NOTIFICATIONS_EXTERNAL_ENABLED` и реальные adapters, если они включены. Не менять общий флаг вслепую, поскольку он затрагивает другие модули: до частичного запуска проверить фактическую конфигурацию и добавить при необходимости отдельный feature gate. Email-переключатели матрицы сейчас могут сохранять предпочтение даже при недоступном транспорте; перед показом пользователям обозначить реальную недоступность доставки и согласовать поведение сохранения. Тестовый канал «кабинет» можно проверить без внешних отправок.
- Telegram: без настроенных bot username/secret подключение недоступно; реальные webhook/доставка не проверялись. Проверить безопасную выдачу capability и отдельное согласование внешнего канала до включения; неизвестный результат не отправлять повторно автоматически.

## Обязательные проверки перед включением

- Убедиться, что веб-сервер, proxy, APM и обработчики ошибок не сохраняют тела запросов/ответов MFA и capability; Laravel boundary не контролирует внешние логи. Проверить локальный и production путь без реальных секретов; Octane/Swoole не проверен из-за работы с `$_POST`, не включать этот runtime до отдельного решения.
- Повторить настоящие пользовательские сценарии без отправок: профиль и аватар, matrix c реальными permissions/brands, пароль и отзыв устройств, двухфакторный вход, одноразовые коды, logout/remember, переходы Back/Forward, 1440/1024/390 и три темы. Проверить production HTTPS и непрохождение поддельных заголовков/внешнего peer. Фактические SMTP/Telegram отправки — отдельный операторский этап.
- Миграции, конфигурацию сервера и рабочую БД в рамках подготовки плана не менять; до готовности перечисленных условий не переносить E1-08 в состояние «Готово» и не выдавать незавершённые каналы за работающие.
