# SP-E1-04: компания, бренды и доступность модулей

В кабинете одна организация. Владелец и администратор редактируют её профиль, сохраняя другие настройки. Только владелец может передать владение активному участнику: организация и обе записи участников блокируются, смена владельца, ролей и audit выполняется одной транзакцией. Удаление организации не предусмотрено.

Владелец и администратор создают и архивируют бренды. При создании строка организации блокируется до проверки `brands.max` и вставки; будущие изменения тарифа и другие пути создания бренда должны использовать ту же блокировку. При создании ограниченным администратором его membership получает доступ к новому бренду в той же транзакции; wildcard-доступ остаётся без изменений. Перед передачей владения после блокировки повторно проверяется доступ владельца к выбранному активному бренду. Архивирование требует подтверждения, сохраняет данные и не допускает архивирование последнего активного либо последнего доступного актору бренда. При архивировании выбранного бренда текущий выбор снимается. Приватный логотип из онбординга читается только через авторизованный маршрут бренда и допустимый tenant-путь; исходные настройки бренда сохраняются.

## Состояние модулей

`brand_modules` хранит явное включение `seller` и `vision`, уникальное для пары бренд/модуль и связанное с организацией составным внешним ключом. Выбор `brands.settings.onboarding.modules_requested` — только предпочтение и не включает модуль. Доступен модуль, лишь если организация и бренд активны, сохранено включение и тариф разрешает модуль. `modules.seller` / `modules.vision`: явный ноль запрещает, положительное значение разрешает, отсутствующий лимит не блокирует согласно существующему контракту тарифов. UI, shared props и завершённый `/start` используют один источник `App\Shell\Organizations\ModuleEntitlements`; при отсутствии допустимого brand context shared props остаются null.

Tenant web-пути `/seller/*` и `/vision/*` закрываются с 404 при выключенном модуле. Для других защищённых маршрутов после разрешения tenant context обязательно применять middleware `module.enabled:seller` или `module.enabled:vision`. API/token middleware в фундаменте пока отсутствует: новый API обязан применять тот же guard после аутентификации и tenant resolution. Фоновые задания обязаны вызывать `ModuleEntitlements::enabled($tenant, 'seller'|'vision')` перед побочными действиями; автоматического перехвата произвольных jobs нет. Отключение не отменяет уже исполняющийся код, поэтому длительные задания должны повторно проверять entitlement перед эффектами. Guard и клиентский флаг не заменяют авторизацию и tenant isolation.

Экран модулей показывает реально настроенные `seller.dialogs_month` / `vision.runs_per_week` и UsageReader для `seller.dialogues` за месяц / `vision.measurements` за неделю. Отсутствующий источник отображается как недоступный, а не как нулевое использование; цены и лимиты не придумываются. Свойство страницы `targetBrand` отделено от общего выбранного `brand`.
