# E8-01E — постоянный реестр выдач знаний Видения

Реестр `vision_knowledge_grants` хранит ULID, organization/brand/release, purpose=vision, data_class=knowledge_public, checksum точной политики, выдавшего, время и необратимый отзыв. Сами факты, адреса и промпты в нём не хранятся. Одна активная запись на бренд. Каждая повторная выдача создаёт новый ID; замена сначала отзывает прежнюю и записывает аудит.

`GrantRegistry::issue(TenantContext $tenant, string $releaseId, array $allowedFactIds)` доступен владельцу и администратору с действующим membership и доступом к бренду; выбирает только существующие активные факты опубликованного активного релиза. Список logical IDs сортируется и вместе с новым ID используется в checksum совместимо с E8-01D. Сервис в той же транзакции записывает `brands.settings.vision_knowledge` и аудит. Отдельное разрешение `ai_data_policy.knowledge_public` сервис не создаёт и не меняет.

`GrantRegistry::revoke(...)` доступен тем же ролям, переводит revoked_at только из null в timestamp, записывает actor/reason и аудит. Повторный отзыв не восстанавливает запись. PostgreSQL запрещает её удаление, truncate, изменение неизменяемых полей и любые последующие изменения отзыва.

`DatabaseGrantAuthority::assertActive(TenantContext, grantId, releaseId, policyChecksum)` реализует согласованный интерфейс E8-01D, и зарегистрирован в контейнере после совместной проверки с мостом. Проверка без открытой транзакции отвергается. В транзакции берутся shared locks organization → brand → membership (при наличии пользователя) → опубликованный активный release → grant. Проверяются точные tenant/source, текущие активные права, цель и класс данных, checksum политики, необратимый отзыв и отдельное разрешение `ai_data_policy.knowledge_public` со значением `any`, как требует текущий E8-01D. Для job допустим доверенный контекст без пользователя; изменение выдачи ему недоступно. Caller обязан удерживать общую транзакцию до окончания проверки; блокировка после commit не действует.

Публикация нового релиза и переключение на другой исторический релиз в DatabaseKnowledgeRepository под теми же блокировками сначала отзывают активные выдачи, записывают аудит и удаляют устаревшую Vision policy, затем меняют active_knowledge_release_id. При возврате к тому же релизу, без изменения указателя, выдача не отзывается. DB trigger запрещает прямое изменение указателя, пока выдача активна: обходящий репозиторий код получает отказ и должен использовать безопасный путь. При ошибке аудита транзакция полностью откатывается.

DB trigger также запрещает изменять `settings.vision_knowledge` или `settings.ai_data_policy.knowledge_public` при активной выдаче. Это предотвращает выключение и последующее восстановление старой policy без реального отзыва. Будущий редактор настроек должен сначала авторизованно отозвать grant, поменять отдельное согласие, затем при необходимости выдать новый ID; прямое изменение защищённых полей намеренно завершится ошибкой. Если отдельное AI разрешение отсутствовало при выдаче, сам grant не включает передачу; для изменения согласия нужен отзыв и новая выдача.

E8-01D использует оригинальный интерфейс и DatabaseGrantAuthority; совместные тесты проверяют реальную выдачу, снимок и блокировку при конкурентном отзыве. Тестовая копия интерфейса предназначена только для независимой ветки. Маршруты, UI, worker, scheduler, LLM/почта/сеть и разрешение live здесь не добавляются. При будущей интеграции E8-01 nullable evidence (включая recommendation, positions и неполноту mentions/sources) нельзя превращать в отрицания: считать отдельные подтверждённые знаменатели.
