# SP-E6-07: лимиты и уведомления продавца

D-11.3 показывает проверенные счётчики и сконфигурированные лимиты: диалоги и сообщения за календарный месяц UTC, активные каналы и участников, расход и доступный бюджет в учётных единицах. Значение неизвестного или не заданного лимита не выдумывается; суммы USD не показываются. Источники: `UsageReader`, `PlanLimits`, `ai_budgets`, contributor `usage.seller_limits` (`seller.dialogues` и `seller.dialogs_month` дают один измеренный счётчик). Данные запрашиваются в рамках текущих organization/brand.

D-11.4 хранит отдельные правила организации/бренда/события: получатель, разрешённые каналы, «сразу» или «сводкой». Личное время HH:MM хранится отдельно для каждого получателя и бренда (по умолчанию 09:00), на странице `/seller/settings/notifications/digests`; его может изменить сам участник, у которого есть доступные события. Редактирование доступно owner/admin (`seller.settings.write`); правила только сужают RecipientPolicy и личные настройки сотрудника. Выбор manager/editor допустим лишь для событий, где они разрешены текущим RecipientPolicy. Получатель теста всегда текущий пользователь. Повтор UUID с теми же параметрами не создаёт ещё одну доставку, с другими отклоняется.

Сводки группируются по организации, бренду, получателю, каналу и местной календарной дате бренда. Каждая личная настройка задаёт одно время для всех событий получателя. Если для даты уже есть ожидающий слот, новое событие присоединяется к нему с ранее назначенным временем, даже после изменения настройки или часового пояса. После закрытия слота новое событие переносится на следующую местную дату, чтобы не создать вторую сводку за день. При отсутствии слота используется ближайшее будущее личное время в текущем часовом поясе бренда; момент хранится в UTC. В пропущенный DST час время сдвигается на размер разрыва (02:30 → 03:30); при повторении часа однозначно выбирается первый реальный момент для данной местной даты. Создание item, сборка и закрытие batch сериализованы advisory lock по org/brand/user/channel/local-date. Идемпотентность item: event/user/channel; batch: org/brand/user/channel/local-date.

Команда `seller:notification-digests` вызывается планировщиком раз в минуту при разрешённом feature scheduling; не требуется постоянный веб-запрос. Включать `SELLER_DIGEST_ENABLED` только после интеграции общего router и проверки entitlement продавца, по умолчанию false. При выключенной функции событие с действующим правилом сводки откатывается в outbox для повторной обработки; настройки не меняются и событие не помечается обработанным. Наружная отправка отдельно управляется E0-04 external_delivery; фейки в тестах, никаких live-вызовов. Перед передачей повторно проверяются активность организации/бренда/участника, RecipientPolicy, правило и личный канал. Статусы batch и теста — pending/sending/sent/failed/uncertain/cancelled; автоматически повторяются только pending. `sending` после аварии и `uncertain` никогда автоматически не переотправлять без отдельной сверки. Невозможно отменить данные, передача которых уже началась. Внешний сетевой эффект запрещён внутри незавершённой DB-транзакции.

Кабинетная сводка появляется только одновременно с переводом batch в sent, в `seller_digest_cabinet_notifications`; тест — в `seller_test_cabinet_notifications` вместе с sent. Текущий пользователь видит `/seller/settings/notifications/digests` при `profile.own`, активном membership и brand grant; при чтении каждого event_key повторно применяется RecipientPolicy. Контракт для общей ленты E1-03: digest (batch_id, organization_id, brand_id, user_id, titles, event_keys, created_at) + batch.status=sent; test (delivery_id, organization_id, brand_id, user_id, title, created_at) + test_delivery.status=sent и event_key. Обязательно сохранить эти проверки при объединении лент и добавить ссылку для менеджера без выдачи права читать настройки.

Необходимая интеграция перед признанием задачи готовой: shared `NotificationRouter`/`NotificationRouting` из main (outbox и проверка перед external), обёртка `withinActive` для изменения правил, личного времени и создания теста до блокировок org/brand/membership, проверка `ModuleEntitlements` при записи/доставке/показе после E1-04, а также повторный интеграционный прогон. Регистрация router — `notifications.router` в FeatureRegistry. Персональный opt-out всегда имеет приоритет. Действующие правила и pending доставки не доказывают, что scheduler и внешний транспорт включены в конкретной среде.
