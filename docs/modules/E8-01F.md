# SP-E8-01F — анкета и версии профиля

## Граница доступа

Публичные методы Questionnaire и SelfDeclaredProfile::read принимают актуальный `Illuminate\Http\Request` с серверной сессией и работают в `TenantContextRunner` с `source=session`. Под транзакционными блокировками проверяются действующая lease и `auth.version`, активные организация и бренд, активное членство/выданный бренд, доступность модуля и `vision.quiz.write`. `brand_id` в сессии должен совпадать с context; клиентский `X-Brand-Id`, если передан, тоже должен совпадать. Контекст job/token/public и viewer не получают права обращаться к Questionnaire или SelfDeclaredProfile::read. Внутренний job pipeline описан ниже. HTTP-контроллеры обязаны включить стандартные auth, verified, tenant, CSRF и no-store. На ошибках сервис возвращает фиксированное сообщение без исходного исключения и SQL bindings. Контроллер должен отображать пользователю общую ошибку, не отдавая stack trace.

## API для SP-E8-02

`app(Questionnaire::class)` (`App\Vision\Core\Profiles\Questionnaire`):

- `start(Request $request): array{id:string,version:int,revision:int}` — найти активный draft или создать его с новой версией. Блокировка строки бренда и partial unique index не допускают два draft.
- `read(Request $request, string $quizId): array{id,version,revision,status,current_step,answers}` — прочитать только анкету текущего бренда.
- `saveStep(Request $request, string $quizId, int $expectedRevision, int $step, array $values): int` — атомарно заменить одну секцию, вернуть следующую revision; несвежая revision даёт `QuizConflict`, а не перезаписывает чужие данные.
- `submit(Request $request, string $quizId, int $expectedRevision): array{id:string,version:int}` — атомарно отправить и создать immutable профиль вместе с audit. При повторении с исходной revision возвращается та же версия профиля. Повторная отправка не запускает AI и не обещает создание вопросов.
- `edit(Request $request, string $expectedProfileId, int $step, array $values): array{id:string,version:int}` — создать новую версию по актуальной, с явным expected id; устаревший id даёт `QuizConflict`.
- `profile(Request $request, string $profileId): array{id,quiz_id,version,checksum,answers}` — приватное чтение конкретной версии и проверка checksum.

`answers` — объект из `step1`…`step7`: сайт/бренд, названия, предложение/аудитория, конкуренты, факты, площадки, вопросы; восьмой шаг — только просмотр. Каждая секция — JSON object. Пустая секция допустима; отправка требует наличие всех семи и непустой `step1.brand_name`. До submit/edit проверяется совместимость всей проекции, включая корректность URL конкурентов и лимит 50 aliases; незавершённые drafts могут содержать временно некорректные данные. Технические пределы: глубина 32 для всего документа, 32 000 байт на секцию; если присутствуют `step4.competitors`, `step5.facts`, `step7.questions`, это списки не более 10/10/15. Это не тарифы. При сохранении секции клиент передаёт весь объект, а не patch. Разрешённые поля для private projection: `step1.brand_name` и `step1.site` (полный http/https URL либо null), `step2.aliases` (строки), `step3.category` (строка либо null), `step4.competitors` (объекты `{name,site}`), `step5.facts` (строки); другие данные хранятся как приватные ответы и не попадают в эту проекцию.

Пример: `step1={"brand_name":"Пример","site":"https://example.test"}`, `step2={"aliases":["Пример"]}`, `step3={"category":"Категория"}`, `step4={"competitors":[{"name":"Другая компания","site":null}]}`, `step5={"facts":["Утверждение пользователя"]}`, `step6={"presence":[]}`, `step7={"questions":[]}`.

`app(SelfDeclaredProfile::class)->read(Request $request, string $profileId)` (`App\Vision\KnowledgeBridge\SelfDeclaredProfile`) возвращает `{profile_id,version,checksum,source:"self_declared",name,site,brand_domain,domains,category,aliases,competitors,facts}`. У каждого факта `source=self_declared`, `verifiable=false`; у конкурентов также указан источник. Это только приватное чтение конкретной immutable версии: редактирование создаёт другую версию и не меняет ранее прочитанную. Данные анкеты не становятся независимо подтверждёнными фактами и не получают разрешение на передачу ИИ.

## Что реально попадает в замер

Обычный `MeasurementRunner::start()` внутри транзакции вызывает `PublishedKnowledgeBridge::buildProfile($context)` и сохраняет возвращённый объект в `measurements.profile_snapshot` вместе с checksum. Если у текущего бренда есть отправленный профиль, в snapshot дополнительно помещается `self_declared` — версия профиля, checksum и приватная проекция name/site/domain/category/aliases/competitors/facts с указанным неподтверждённым источником. Это не включается в approved knowledge release и не подменяет его grant. Без профиля форма snapshot прежняя. `SelfDeclaredProfile::read()` остаётся отдельным пользовательским private API.

`KnowledgeGate` сверяет зафиксированный snapshot и checksum, отдельно пересчитывает опубликованную часть и активный grant, и по ID сверяет именно историческую версию self_declared. Старая версия не подменяется актуальной после редактирования. Существующие замеры без self_declared сохраняют прежний путь. Но пока `EvidenceEvaluator` отправляет весь snapshot под классом `knowledge_public`, gate **временно запрещает обработку всех замеров с self_declared**; это намеренная блокировка, а не готовый runtime. Существующая проверка ContactBoundary применяется только к утверждённой опубликованной части, не выдавая анкету за release.

Точный запрос интегратору: исключить self_declared из всех исходящих AI payload и доказать это тестом с маркером и fake gateway, отдельно проверить повторную version-bound проверку и отзыв grant, затем убрать явно помеченный временный fail-closed в `PublishedKnowledgeBridge::assertAllowed`. Перед реальной отправкой самих данных анкеты нужен отдельный data class, действующий grant, data policy и ContactBoundary для этого содержимого. `forExternalAi()` всегда отказывает. В ветке не совершаются внешние вызовы.

Внутреннее чтение версии реализовано private-методом моста после его tenant, активного бренда/организации/модуля, release и grant checks; вызвать его напрямую невозможно. При `source=session` и наличии анкеты `buildProfile` дополнительно выполняет полную `ProfileAccess` проверку актуальной сессии/роли/выбранного бренда. Фоновый `source=job` разрешён только для совпадающего scoped tenant без actor/membership с активным опубликованным release и grant. Произвольные job контексты не являются пользовательским API и не дают прямого права на анкету.

`question_generation_batches` и `question_candidates` сохраняют составные tenant/profile/quiz FK; batch по умолчанию `blocked`. Ни генерация, ни потребитель/очередь здесь не подключены. Нужна отдельная функциональная задача V-2; реальных AI вызовов не делали. `question_generation_batches` требуется зарегистрировать владельцу общего registry.
