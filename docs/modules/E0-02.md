# E0-02 — фундамент организации и брендов

Реализован инфраструктурный слой одной организации кабинета. Регистрация feature происходит через `config/features/E0-02.php`: scoped context, middleware alias `tenant`, lazy shared props, invitation contract и explicit seeder. Общие bootstrap, manifests и locks не менялись.

## Установка и данные

В локальном `.env` и `.env.testing` задать `CABINET_ORGANIZATION_ID` — один серверный ULID организации. Значение читается только через cached config `features.E0-02.defaults.organization_id`. Headers, query string и body не выбирают организацию. Неполная установка не предоставляет tenant data.

```powershell
./infra/osp/php.ps1 artisan migrate
./infra/osp/php.ps1 artisan features:seed E0-02
```

Сидер доступен только local/testing и выполняется явно. Он создаёт одну демонстрационную организацию и три бренда с темами confectionery, pyro, neutral. Повторный запуск сохраняет существующие данные. Изменение installation ID не создаёт вторую организацию. PostgreSQL advisory transaction lock защищает параллельные запуски.

Сидер **не создаёт пользователя, пароль или membership**. `owner_user_id=null` допустим на этом initial provisioning шаге; первый настоящий владелец создаётся будущим onboarding в одной транзакции вместе с owner membership. Это не готовая авторизация. После назначения владельца model guards не позволяют удалить его membership, отключить или понизить роль, пока owner pointer не передан другому active owner. Удаления организации в кабинете нет.

Миграция создаёт только четыре таблицы: organizations, brands, memberships, invitations. Все entity/user FK — ULID. У brands есть unique `(id, organization_id)` для composite FK будущих brand-owned roots; memberships имеют unique `(organization_id, user_id)`. PostgreSQL CHECK constraints ограничивают роли, статусы, темы, JSON типы, sales_manager и invitation token hash.

## Контекст и доступ

`TenantContext` — immutable value, зарегистрированный scoped. До resolver это пустое значение с organizationId=null; такое состояние не даёт доступа. В resolved context доступны organizationId, brandId, actorId, membershipId и source (session/token/job/public).

`TenantContextRunner::run(context, closure)` проверяет active organization, принадлежность active brand и, если указан membershipId, его соответствие actor/organization/brand. Предыдущий контекст восстанавливается в finally, в том числе после nested exception. Worker должен передавать persisted IDs через runner; не сохранять mutable context в singleton.

`BelongsToTenant` по умолчанию требует organization **и** brand. Organization-only модели явно возвращают false из tenantUsesBrand. Отсутствующий обязательный контекст возвращает пустую выборку и запрещает запись. Model create/update/delete проверяют tenant IDs. Brand lookup ограничен текущим выбранным брендом; resolver получает список доступных брендов отдельным явно ограниченным server-side запросом.

**Integration prerequisite:** root bootstrap должен поставить ResolveTenant перед SubstituteBindings в middleware priority. Regression test для implicit Eloquent binding намеренно падает на исходном E0-01 bootstrap (валидный current-brand ID даёт 404 до установки context). Интегратор исправляет shared bootstrap после merge E0-02 и обязан получить green regression до mark-done. Worker не подменяет kernel priority в тестах.

Это Eloquent/application isolation и composite FK, не PostgreSQL RLS. Raw SQL, `withoutGlobalScopes`, bulk update/delete обходят model events; они допустимы только в проверенных служебных границах. Domain Actions должны использовать scoped lookup и instance mutations. Любой brand-owned root обязан создать composite FK на brands; это проверено на отдельной тестовой таблице.

`ResolveTenant` выбирает только configured organization и active membership. Список ограничен активными брендами и grants. Сессионный бренд выбирается из этого списка. Устаревшая сессия переходит на первый доступный бренд только для safe read или explicit brand.switch. Остальная мутация с отсутствующим/отозванным/архивным выбранным брендом получает 404 без смены сессии и записи; старый tab не может молча записать в другой бренд. `X-Brand-Id` может лишь совпасть с выбранным брендом, иначе 404. Режимов support/staff/cross-company нет.

| Роль | Пустой brand_ids | Непустой brand_ids |
|---|---|---|
| owner/admin | Все активные бренды этой организации | Только перечисленные бренды |
| member/viewer | Нет доступа к брендам | Только перечисленные бренды |

brand_ids должны быть уникальным списком ULID брендов той же организации. Legacy null не записывается в новую schema. settings.sales_manager — boolean, true только у member. Точную матрицу бизнес-действий и `can` реализует E0-03; E0-02 не объявляет второй источник этих прав. Текущий coarse guard запрещает viewer мутации кроме смены собственного UI-контекста.

## Переключение и props

`POST /brand/switch {brand_id}`, route name `brand.switch`, проходит web/session/auth/verified/tenant/CSRF. Чужой или недоступный бренд → 404, malformed ID → 422; разрешённый → session brand_id и redirect на фиксированный `/`.

`TenancySharedProps` отдаёт organization, brand (включая theme) и brands через lazy closures: они разрешаются после route tenant middleware. Приватные settings/owner/email/token не сериализуются. Preview продолжает получать собственные anonymous PreviewProps; E0-02 не превращает его в authenticated UI.

Первая контрольная точка не содержит production web UI. `/` пока ведёт к preview; полноценных auth routes и страниц ещё нет. Интегратор задаёт literal guest redirect `/login` без зависимости от отсутствующего route name; адрес появится в E1-01. Authenticated shell E0-08 должен подключить switch и сбрасывать cache/form state при смене brand; текущая задача не создаёт второй frontend store или вручную дублированные TS DTO.

## Приглашения — контракт для E1-01/E1-06

Binding `App\Tenancy\Invitations\AcceptsInvitations`:

- `inspect(User, token): InvitationDetails` — email-bound безопасное описание; нет raw token/token_hash.
- `accept(User, token): Membership` — verified email, транзакция и одноразовое принятие.

Raw token — 64 alphanumeric символа; хранится только SHA-256. Unknown, malformed, wrong email, foreign organization, expired (now >= expires_at), revoked и accepted возвращают одинаковый 404. Email нормализуется lower/trim. При принятии User перечитывается под lock, поэтому изменённый email или снятая verification не обходятся старой in-memory моделью.

Организация и invitation блокируются в транзакции. Первый accept создаёт membership и записывает accepted_at/accepted_by атомарно; второй получает 404. Существующее членство сохраняется полностью: owner не понижается, viewer не повышается, disabled не активируется, brand grants не расширяются. Ошибка записи потребления откатывает новый membership. Реальная гонка проверена двумя процессами PostgreSQL.

Invitation не выдаёт owner: допустимы admin/member/viewer. Grant envelope (email, role, brand_ids, settings, hash, issuer, expiry) после создания неизменяем; повторная отправка с новым сроком должна выдать новое invitation и отозвать старое. Consumed/revoked state нельзя восстановить. E1-06 отвечает за право создавать приглашения, resend/revoke UI и доставку; E1-01 — за auth routes. E0-04 позже добавляет transactional audit integration; здесь не создаётся чужая audit schema или фиктивный успешный audit.

## Проверка

`./infra/osp/php.ps1 vendor/bin/pest tests/Feature/Tenancy` требует точную изолированную PostgreSQL test DB по guards E0-01. Concurrency test запускает два PHP subprocess в том же worktree, использует только fixture token и test DB. Никаких LLM/mail/Telegram calls.

Тесты проверяют unknown/foreign scope, same-org cross-brand 404, mutation guards, scoped cleanup, actor mismatch, disabled grants, viewer, csrf, lazy props, DB constraints, invitation expiry/revocation/reuse/email/rollback/concurrency и идемпотентный seed. Visual screenshots неприменимы: новых экранов этот infrastructure task не создаёт.
