# SP-E8-01D: знания продавца для Видения

Мост `PublishedKnowledgeBridge` преобразует только явным образом разрешённые активные факты опубликованного релиза текущего бренда. По умолчанию он **закрыт**: `GrantAuthority` привязан к `DenyGrantAuthority`, поскольку постоянный реестр выдачи и отзывов ещё не создан. Настроек внутри бренда недостаточно для разрешения: изменение настроек назад не доказывает, что старое согласие не было отозвано. Этот код не запускает AI и не включает live.

## Выдача профиля

Из доверенного tenant context в **той же DB-транзакции до INSERT measurement** вызвать `PublishedKnowledgeBridge::buildProfile($tenant)` и сохранить результат целиком в `measurements.profile_snapshot` и `CanonicalJson::hash($profile)` в `profile_checksum`. Транзакция удерживает shared locks до вставки; вызов без внешней транзакции отклоняется. Для session/token контекста повторно проверяются активный участник и доступ к бренду; доверенный job context может не иметь actor. Публичный контекст отклоняется. Доступность Vision повторно проверяется через `ModuleEntitlements` и актуальный тариф.

В `brands.settings.vision_knowledge` нужны одновременно `enabled: true`, уникальный `grant_id` ULID, `release_id` активного опубликованного релиза этого бренда, `allowed_fact_ids` — список уникальных logical ULID фактов, `data_classes: ["knowledge_public"]`. Дополнительные ключи отклоняются. Нужен и существующий `ai_data_policy.knowledge_public`, содержащий `any`. Текущие настройки не являются доказательством действительности grant: отдельная authority должна проверить постоянный реестр. Настройки нельзя предоставлять UI без отдельной авторизованной операции с audit, одноразовой выдачей grant и обязательной синхронизацией с отзывом.

Ровно разрешённые логические ID выбираются из активных фактов подтверждённого checksum релиза; отсутствующие, повторяющиеся, чужие или неактивные ID приводят к отказу. Одинаковый текст разных фактов не объединяется. Проекция содержит ровно:

```text
{name, aliases, facts: [{id, topic: "knowledge_fact", value, verifiable: false, source}],
 knowledge: {grant_id, release_id, checksum, data_classes: ["knowledge_public"], policy_checksum}}
```

`name` и `aliases` берутся из текущего бренда и его onboarding aliases, `id` — logical ID факта, `source` — только enum `manual/import/url`. Происхождение задают ID факта и ID/checksum релиза; произвольный ключ группы, прочие namespaces продавца и внутренние условия не раскрываются и не превращаются в ограничения без отдельного согласованного контракта. `verifiable=false`: публикация сама по себе не является независимым подтверждением факта. Вся проекция до возврата проходит `ContactBoundary`; сырые контакты, включая неоднозначные закодированные формы, приводят к отказу. Возможны консервативные отказы по числам, похожим на телефоны.

`KnowledgeGate::assertAllowed(TenantContext, measurementId, frozenProfile)` повторно проверяет текущий tenant, активность организации/бренда, членство, модуль и тариф, policy/authority и release. После повторной сборки он сравнивает **весь** переданный профиль с ней и с профилем, сохранённым для данного tenant/measurement, включая проверку сохранённой checksum. Дополнительные поля, подменённые имя/алиасы/факты/источник/классы/release/grant, несоответствующая контрольная сумма и чужие измерения отклоняются. Общее исключение не содержит оригинальных данных. После проверки lock освобождается: отзыв между проверкой и началом внешнего AI нельзя атомарно отозвать без удержания блокировки на сети; вызывающий Evidence повторно проверяет до вызовов и после, а результаты отзываются при последующей проверке.

## Обязательный постоянный реестр

`GrantAuthority::assertActive(TenantContext $tenant, string $grantId, string $releaseId, string $policyChecksum): void` вызывается в транзакции после shared-lock organization → brand → membership (если применимо) → published release. Реализация обязана заблокировать запись grant до commit и сверить tenant (organization_id, brand_id), grant ULID, release ULID, назначение Vision, data class `knowledge_public`, точный policy checksum, статус active и отсутствие `revoked_at`. Отсутствие/неоднозначность — исключение. Разрешение должно быть неизменяемой записью с однонаправленным отзывом; новый grant ID создаётся при каждом изменении/повторной выдаче и никогда не восстанавливает старый. Фиктивная authority допустима только в тестах.

При каждой смене активного релиза E3 publish/rollback обязан **атомарно**, под совместимым порядком блокировок organization → brand → release → grant, отозвать прежние grants прежде, чем переключить ссылку на релиз. Возврат старого релиза не оживляет старое разрешение; запись отзыва не удаляется и не отменяется. Операция выдачи/отзыва должна быть авторизована и аудитирована. После реализации интегратор меняет default-deny binding, выполняет конкурентные тесты выдачи/отзыва/смены релиза и сквозной тест Core → Evidence → fake AI. До этого передача остаётся заблокированной.

Интерфейс `App\Vision\Evidence\Contracts\KnowledgeGate` принадлежит E8-01C. В исходной базе ветки его не было; при интеграции сначала объединить E8-01C и проверить binding. E8-01 должен построить и сохранить профиль в транзакции и подключить gate к вызовам; без этого сквозной сценарий не завершён.
