# E1-05 · Карточка бренда

Экран S-2.3 доступен по `GET /brands/{brand}/settings`. Собственные маршруты, bindings и shared-props contributor подключаются через `routes/features/E1-05.php` и `config/features/E1-05.php`. Страница — `resources/js/pages/Shell/Brands/Settings.tsx`; бизнес-операции — `app/Shell/Brands/Actions/BrandSettings.php`.

## HTTP и права

Все маршруты находятся в группе `web` с session/CSRF, auth, verified, tenant, `auth.version` и `auth.nostore`.

| Метод и путь относительно `/brands/{brand}/settings` | Назначение |
|---|---|
| GET `/` | Карточка, домены, права и состояние модулей |
| PATCH `/general` | Название, сайт, алиасы, сфера, регион, язык, часовой пояс |
| PATCH `/theme` | Пресет, подпись, промо-карта, загрузка/удаление логотипа |
| GET `/logo` | Приватный PNG для участника с `brand.read` и доступом к бренду |
| POST `/domains` | Новый домен и случайное проверочное значение |
| POST `/domains/{domain}/verify` | Проверка файла или DNS TXT; throttle 10/мин |
| DELETE `/domains/{domain}` | Удаление привязки домена |
| POST `/website/check` | HTTP-доступность сохранённого сайта и robots.txt; throttle 10/мин |

Карточка и изменения требуют `brand.write`. `BrandAccess` проверяет организацию и доступ к целевому бренду; мутации повторно читают активное членство owner/admin, grants, выбранный и целевой бренды внутри `AuthSessionRegistry::withinActive`. Организация, членство и целевой бренд блокируются до commit. Запись выполняется в контексте целевого бренда через `TenantContextRunner`, затем прежний контекст восстанавливается. Архивная карточка доступна без изменений. Аудит сохраняется в той же SQL-транзакции, что и мутация.

## Данные и интерфейс

`targetBrand`, `domains`, `moduleItems`, `permissions` — собственные props страницы; они не заменяют shared `brand` и `modules` выбранного кабинета. `permissions.manage` учитывает архивное состояние после проверки прав доступа.

- Основные поля сохраняются в `brands`; алиасы — в `settings.aliases`. Алиасы обрезаются по краям, удаляются пустые и повторные значения. Форма после сохранения получает канонический массив из ответа сервера. Изменение адреса сбрасывает прежнюю проверку сайта.
- Пресеты: `confectionery`, `pyro`, `neutral`. Подпись и флаг промо-карты — `settings.theme`. Предпросмотр использует существующие токены F-01 внутри локального `data-theme`: брендовая область сайдбара и шапка, логотип, подпись и промо-карта; глобальную тему он не переключает.
- Логотип: PNG/JPEG/WebP до 2 МиБ и 2048 × 2048, декодирование и повторная запись PNG, результат до 4 МиБ. Приватный путь совместим с onboarding: `organizations/{organization}/onboarding/logos/{random}.png`. Новая запись компенсируется при отказе/rollback; прежний файл удаляется после commit при отсутствии других ссылок. HTTP-выдача проверяет путь и права, использует `no-store`, `nosniff` и ограничительную CSP.
- `brand_domains` имеет organization/brand FK и уникальность `(organization_id, brand_id, host)`. Назначение: `widget` или `widget_and_visibility`; способ: `file` или `dns`; состояние: `pending`, `verified`, `failed`. Проверочное значение скрыто в обычной сериализации модели и выдаётся в инструкции авторизованной карточки. В аудит оно не попадает. Перед записью результата повторно сверяются token и `check_version`; удалённая или параллельно проверенная запись не перезаписывается устаревшим результатом.
- `moduleItems` содержит фактическое и настроенное включение, доступность по плану, лимит, квоту и usage. Неуказанные тарифные значения остаются `null`/не настроено; цены не рассчитываются.

Переключение модулей использует существующий `PUT /brands/{brand}/modules/{module}` из E1-04 и его проверки. После операции существующий controller перенаправляет на отдельную страницу `Shell/Organizations/Modules`; пользователь уходит с вкладки карточки. Архивирование также использует существующий `PATCH /brands/{brand}/archive`; удаления организации здесь нет.

Протокол подтверждения соответствует источнику R-S-10: файл `/.well-known/eyon-domain-verification.txt` содержит обычный token без префикса; DNS TXT с именем `_eyon.<host>` содержит то же обычное значение. Точные индивидуальные значения выдаёт `BrandDomain::instructions()`.

## Сеть и ограничения

Внешние проверки сайта и домена по умолчанию выключены: `features.E1-05.defaults.external_checks` принимает только boolean true из операторского параметра `BRAND_EXTERNAL_CHECKS_ENABLED=true`. Его можно включать только на отдельно разрешённом операторском этапе. Отключение проверяется на сервере до DNS/TXT/HTTP; оба POST возвращают понятную ошибку формы и не меняют сохранённые данные, статус домена или аудит. Интерфейс показывает недоступность и отключает действия проверки. Добавление домена, инструкции и сохранение настроек при этом работают.

У проверки сайта есть непрозрачная версия в `settings.website_check_revision`. Смена URL (включая A→B→A) и успешная запись результата под блокировкой бренда обновляют её. Завершившийся сетевой запрос сравнивает исходную версию и адрес в транзакции с повторной авторизацией; если пока прошла другая проверка или изменился URL, он получает 409 и не записывает ни результат, ни аудит. Сеть вне транзакции, первый завершившийся запрос с неизменённой версией побеждает.


`PublicHost` нормализует IDN, отклоняет IP-литералы, служебные имена и непубличные адреса. Для HTTP проверяются все полученные A/AAAA, проверенный адрес фиксируется через `CURLOPT_RESOLVE`; используется явный `CurlHandler` без fallback на stream transport. Hostname сохраняется для TLS-проверки. Разрешены HTTP/HTTPS со стандартным портом, без credentials, proxy и автоматических redirects. Автоматическая распаковка выключена; запрашивается `Accept-Encoding: identity`.

HTTP connect timeout — 3 с, timeout одного запроса — 8 с. Лимиты тела: сайт 1 МиБ, robots.txt 64 КиБ, проверочный файл 4 КиБ; проверяются объявленный размер, ход загрузки и итоговый размер. Проверка сайта может выполнить два последовательных HTTP-запроса. `robots_blocked` отражает общие правила `User-agent: *` для корня `/`; это ограниченный разбор robots.txt.

Нативный `dns_get_record()` использует DNS resolver ОС и не имеет отдельного управляемого deadline в этой реализации. Указанные HTTP timeout не ограничивают время DNS/TXT-проверки или суммарное время операции. Сеть выполняется вне SQL-блокировок. Для автоматических проверок требуется подмена и `DomainDnsResolver`, и HTTP; реальные проверки доменов/сайтов в рабочем окружении не являются частью тестового прогона.

## Точные действия интегратора

Следующие общие файлы находятся вне scope исполнителя E1-05 и здесь не изменены.

1. В `resources/js/pages/Shell/Organizations/Brands.tsx` добавить для доступных активных брендов ссылку «Настройки» на `/brands/{id}/settings`. Сохранить самостоятельное действие переключения кабинета бренда.
2. В `app/Data/Shared/SharedPropsV1.php` описать nullable `brandAppearance`; создать shared DTO `app/Data/Shared/BrandAppearanceData.php` с `logo_url: ?string`, `subtitle: string`, `promo_card: bool`. Источник уже существует: `app/Shell/Brands/BrandAppearance.php`, лениво ограниченный текущим tenant/brand. Публичные страницы не должны получать эту авторизованную проекцию.
3. В `resources/js/components/navigation/Sidebar.tsx` подключить `brandAppearance` выбранного бренда: приватный логотип с fallback, подпись, условную промо-карту. В `resources/js/layouts/CabinetLayout.tsx` согласовать брендовые области шапки с предпросмотром. Использовать существующие токены, сохранить semantic action/nav цвета F-01, compact/mobile режимы и читаемые подписи. Сейчас настоящая оболочка **не использует** `brandAppearance`; сохранение дополнительных настроек и локальный предпросмотр работают отдельно от её будущего подключения. При редактировании другого бренда оболочка должна оставаться оформлением выбранного кабинета, а не `targetBrand`.
4. После интеграции выполнить `scripts/generate-types/generate.php` и проверки владельцем generated contracts. Обновить `resources/js/types/generated/data.ts` для нового shared DTO и `resources/js/types/generated/routes.d.ts` для `brands.settings.*`; generated файлы вручную не редактировать.

В base `8ed6f5f` уже обнаружено устаревание `resources/js/types/generated/translations.ts`: отсутствует ровно `navigation.seller_digests` — 31 ожидаемый ключ против 30 generated. `lang/`, navigation JSON, loader, generator и generated translations в worktree побайтно совпадают с base. Меню обновлено commit `7273390`, translations ранее генерировались в `6c1cf24`. Исправление shared generated translations также выполняет интегратор; E1-05 этот общий файл не переписывает.
