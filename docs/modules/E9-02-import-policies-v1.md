# SP-E9-02: политика исторического архива Eyon и соответствие прототипа v1

Статус: решение интегратора для реализации и тестов; не разрешает реальный импорт, публикацию, отправку сообщений или внешние вызовы. Дополняет docs/modules/E9-02-vision-contract.md. Если для конкретного поля этой версии нет точной схемы, оно считается неподдержанным и даёт безопасный conflict. Это не полное покрытие всех версий Eyon.

## Исторический архив и доступ

Архив — отдельное приватное хранилище исторических данных и снимков Eyon для явно выбранных организации и бренда. Это не исходный ZIP пользователя и не доверенные vision_reports; старые данные маркируются unverified/historical, не попадают в runtime, ИИ или публичные ссылки автоматически. Оригинальная offline-копия остаётся у оператора вне проекта, без изменения и удаления.

Применение batch и архивное чтение разрешены только активному owner с действующей проверенной сессией, доступом к выбранному бренду и отдельным явным архивным grant для этого бренда. До применения owner подтверждает неизменяемый digest источника, соответствие бренда, версию политики и категории текста/контактов, которые разрешены к архивированию. Grant и подтверждение хранятся server-side с actor/tenant/source/batch/policy и аудитом без payload. Grant действует до отзыва; опциональный срок может быть установлен владельцем явно. Каждый запрос/выдача повторно проверяет актуальные session, membership, организацию, бренд, grant и состояние записи; отзыв действует немедленно для последующих блоков выдачи. Не удерживать общие DB-блокировки во время сетевого вывода.

Физический срок хранения исторических записей не установлен; автоматически ничего не удалять. Отзыв доступа не удаляет сам архив. Удаление приватных записей, резервных копий и исходного ZIP — отдельное согласованное действие; rollback batch и tombstone следуют E9-02-vision-contract. Публичные capability-ссылки не создаются и старые tokens не копируются.

## Eyon JSON: политика eyon-legacy-private-v1

Общие правила: versioned allowlist фиксируется как eyon-legacy-private-v1 и применяется до записи каждого полного JSON-документа; объект содержит только перечисленные ключи, без wildcard и неограниченных вложений. Неподдержанная версия, тип, ключ, слишком большой/глубокий JSON или сомнительное содержимое — conflict записи; не отбрасывать поля и не подменять null, false, ноль или пустой массив. Диагностика содержит только фиксированный код, известную колонку и безопасный идентификатор строки, но не неизвестные имена ключей, значения, пути источника, SQL bindings и payload. Обрабатываются только неизменяемые offline-копии; чтение/отображение не исполняет HTML, скрипты и URL.

Подтверждённый shape исходного app/Services/Visibility/PromptSets.php:

- prompt_sets.questions — JSON array объектов: n положительное целое; text и intent строки; qid строка, если присутствует. Других ключей нет. Отсутствие qid сохраняется как отсутствие, идентификатор не выдумывается.
- audit_snapshots.payload — только root-ключи с проверенными типами: generation и revision — целые >= 1; brand_name и methodology_version — строки; site_url — строка; timezone — строка; published_at — строка времени; profile_hash и parser_version — string или null; planned_repeats — целое >= 1; fill — строка; next_run_at — строка времени или null; complete — boolean. Отсутствующие необязательные поля остаются отсутствующими. Даты валидировать без предположения часового пояса.
- Встроенный payload.questions — массив тех же объектов n/text/intent с необязательным qid, если весь документ соответствует этой версии. Это не разрешение других узлов payload.
- audit_runs.configuration/result/errors, prompt_sets.variables, measurement_answers.search_evidence, answer_facts.claims/suspected_errors и другие не описанные выше вложенные JSON-поля v1 не разрешает. Собранный исходным VisibilityAggregator payload обычно содержит metrics, profile и другие вложения: такой снимок закономерно получит conflict, а не частичный импорт. Исполнитель обязан выписать каждый реальный producer и typed leaf-schema и предложить следующую версию политики с synthetic fixtures; нельзя называть текущий whitelist полным импортом.

Исходные error_code, ids, hash, методика, даты и числовые агрегаты — только исторические метаданные. Не копировать credentials, токены публикации, session data, raw_disk/raw_path, файлы и прочие источники секретов, не создавать настоящие AI-вызовы и не подписывать прежний payload как новый ReportSeal.

Любой разрешённый свободный текст и контакт — частные данные. Шифровать в tenant/brand scoped archive; не включать в разрешённую публичную или AI-проекцию. До записи свободного текста необходимо отдельное явное подтверждение owner по конкретному набору и проверка на запрещённые секреты; при сомнении или выявленном секрете — conflict с сохранением исходника у оператора. Поиск по шаблонам сам по себе не доказывает отсутствие всех секретов. Строки UTF-8 ограничиваются заранее объявленными лимитами схемы без усечения. URL только http/https без userinfo, query и fragment; не разыменовывать, не обрезать молча: иначе conflict. Любые значения отображать как текст с экранированием.

## Прототип Seller: mapping prototype-seller-v1

Исходник: .local/references/laravel-prototype/database/migrations/2026_10_24_000001_create_agent_tables.php, app/Agent/LeadState.php. Цель: database/migrations/E3-04/2026_10_31_060400_e3_04_create_seller_conversation_tables.php. Весь mapping явный, версионированный, tenant/brand scoped и валидируется до commit; сохраняется source ID и postimage в tracking, все неоднозначности — conflict, не потеря данных.

- leads.channel: web / telegram / api сохраняется как исходное значение в отдельном приватном provenance. Для предполагаемой связи web→widget, telegram→telegram, api→api оператор явно выбирает существующий channel_accounts.id того же tenant/brand и типа; сам текст channel не является доказательством привязки. Аккаунты, credentials и токены не создавать и не включать. Реальную связь conversations.channel_account_id не создавать, пока нельзя выполнить неизменяемый контракт inbound сообщений ниже.
- leads.source: только site_form / telegram / manual / simulator как приватный provenance; неизвестные значения — conflict. simulator явно отмечать как тестовое происхождение, не выдавать за реального клиента и не запускать автоматическую отправку; ручное включение такой истории в рабочие данные — отдельное осознанное решение.
- leads.external_id — прежний контекстный chat_id, НЕ идентификатор события и НЕ доказательство личности. Сохранять только encrypted/private provenance с исходным source/channel и выбранной оператором связью аккаунта. Не записывать его в external_event_id, не придумывать сообщения или события, не сливать контакты по external_id. Если отсутствует безопасное provenance-хранилище, запись conflict и оригинал остаётся только в offline-копии.
- leads.phone — nullable строка в пределах target contacts.phone (40). Переносить только после штатной валидации; номер приватен, не логируется, E.164/код страны не придумываются. Неоднозначный или несовместимый формат — conflict. Совпадение телефона само по себе не основание объединять клиентов; reuse существующего контакта только по явно утверждённому mapping, иначе отдельный контакт с tracking.
- leads.next_contact_at — сохранить исходное значение в приватном provenance. В conversations.next_followup_at переносить только при точно известном часовом поясе источника, строгом разборе и запрете любых автоматических отправок/джобов после импорта; неоднозначное/неверное значение — conflict, не считать текущим временем. До появления безопасного режима использовать только provenance.
- leads.flags и leads.missing дублируют state.flags/state.missing. Разрешать лишь документированные ключи/типы действующего LeadState; одинаковые значения записывать один раз, различия при одновременном наличии — conflict. NULL и отсутствие не превращать в пустые значения. Прочие state-поля проверять по версии прототипа, неизвестные не удалять молча. Флаг do_not_disturb должен согласованно сохраняться в состояние и отдельную колонку; противоречие — conflict.
- Сообщения client в conversation с channel_account_id требуют настоящие channel_inbound_events и их external_event_id по triggers E3-04. У прототипа они не хранятся. Поэтому не подделывать события и не ослаблять triggers: исторические диалоги без этих доказательств импортировать только как внутренние с channel_account_id=null и отдельным private provenance; привязка к живому каналу — отдельный подтверждённый механизм владельца Seller. Все импортированные диалоги начинать с mode=manager; импорт не инициирует delivery, bot/AI, уведомления или followup.

Сопоставления и ссылки на contacts/channel accounts перепроверять под блокировками и по составным tenant FK. Если account недоступен, тип не совпадает, исходный текст невалиден, есть чужая связь или источник/временная зона не определены — conflict без раскрытия значений. Повтор и параллельный импорт не создают дублей; rollback не удаляет чужие, общие или изменённые после импорта записи. Нужны интеграционные тесты NULL/пусто, несовпадающих флагов, нескольких брендов, неоднозначных контактов, архивного channel mapping, отсутствующих inbound event IDs, конкурирующих batch и отсутствия внешних отправок.

### Архив исторических review, llm_calls и evaluations

При явном подтверждении owner по конкретному набору допустим только отдельный зашифрованный архив provenance с привязкой к организации, бренду, source и batch. Исходные идентификаторы, разрешённые связи, NULL и исходные значения сохраняются без притворного заполнения. Обработка возможна только для проверенной версии схемы: неизвестные поля или типы, неподтверждённый текст либо подозрение на секрет дают conflict без записи payload в журнал. Данные остаются частными, не становятся `message_reviews`, `ai_calls`, фактическими счетами, уведомлениями, данными для ИИ или действиями продавца; никаких вызовов и отправок импорт не запускает.

В исходной миграции `review` содержит `lead_id`, необязательный `message_id`, текстовые `type`, `comment`, `better_text`, `author`, `status`, `applied_to` и timestamps. Эти строки не являются утверждёнными enum или идентификаторами пользователя. У `llm_calls` необязательны ссылки на lead/message; `prompt` и `response` — вложенный JSON с возможными персональными данными и секретами, `component`, `model`, токены, `cost_usd`, задержка, статус, ошибка и timestamps — исторические атрибуты. У `evaluations` — lead, date, агрегат, JSON scores/flags/issues/unknown_questions, тексты worst_reply/fix/comment, число ходов, cost и timestamps. Полную схему переменных `prompt.params` и provider-specific response/usage считать неизвестной до подтверждения; неизвестное не пропускать и не объявлять поддержанным.

Nullable-ссылку можно сохранить как NULL только при подтверждённых source и бренде и отсутствии противоречий; несогласованные связи дают conflict. Время без часового пояса хранить как исходный текст с пометкой неизвестной зоны, не превращая в доказанный момент. Стоимость — historical/unverified: сохранять точное исходное представление без вычислений float и молчаливого округления; ноль из прототипа не доказывает бесплатный вызов. Если точное значение или безопасный формат нельзя доказать, сохранять только явно разрешённое исходное представление в закрытом архиве либо возвращать conflict. Данные архива не включаются в текущий баланс и расчёты.

Для версии `Supervisor::evaluateLead` подтверждён формат `evaluations`: scores с ключами naturalness/goal/facts/objections/brevity и целыми оценками 1–5; flags с ключами forbidden_promise/invented_fact/off_topic_fulfilled/two_questions/repeated_question/bureaucratic/lied_about_bot/argued и boolean; issues — список объектов type/layer/severity/turn/quote/explanation/fix, layer extractor/policy/responder/guard/knowledge, severity low/medium/high, turn integer; unknown_questions — список строк. Типы issues брать из `Supervisor::ISSUE_TYPES` соответствующей версии источника, не угадывать. Nullable-значения сохранять как NULL. Тексты требуют подтверждения owner и проверки на секреты; неизвестную вложенную форму не урезать, а возвращать conflict.

### Откат импортированных записей Seller

До появления проверенного и согласованного с владельцем Seller lifecycle adapter физическое удаление созданных импортом записей Seller при rollback запрещено: пакет с такими записями возвращает conflict. Для reused-записей допустима только проверенная отвязка участия текущего batch; сам объект и принадлежность других batch не меняются. Source identity mapping, provenance и аудит сохраняются, в том числе при conflict; состояние учёта после разрешённой отвязки должно оставаться непротиворечивым.

Rollback пакета атомарен: при хотя бы одной спорной записи, неподтверждённой зависимости, изменённом postimage или гонке не выполнять частичного отката. Наличие только FK-проверок и перечня известных связей не доказывает отсутствие ссылок в JSON, файлах, событиях или других модулях. Будущий adapter должен для каждого типа записи определить подтверждённых владельцами потребителей, все доступные механизмы ссылок и единый способ предотвратить их конкурентное создание на время проверки и удаления; при неизвестном потребителе или невозможности сериализации — conflict. Он не должен обходить существующие ограничения и lifecycle владельцев данных.

Из уже известных примеров в E3-04: `messages.conversation_id`, `seller_turns.conversation_id`, `seller_turns.input_message_id`, `seller_tasks.conversation_id` и `message_reviews.message_id` защищены составными tenant FK с `restrictOnDelete`. Это примеры подтверждённых связей, не полный реестр зависимостей и не разрешение на удаление.
