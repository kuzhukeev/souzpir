# E1-12 — помощь и обращения

Модуль реализует S-8.1 `/help`, S-8.2 `/help/support`, S-8.3 `/help/status`. Используются feature loader, CabinetLayout, текущие session/auth.version/tenant guards и AuditWriter. Владение таблицами `tickets`, `ticket_attachments`, `support_access_grants` закреплено за E1-12 в registry. Shared models, manifests, generated files и bootstrap не изменяются.

## Маршруты и данные

- GET `/help` (`help.index`) — шесть разделов и только реально настроенные статьи/ссылки. Поиск фильтрует доступные названия/описания. Не настроенные материалы обозначены «Скоро»; демонстрационные статьи не добавляются.
- GET `/help/support` (`help.support`) — форма и страницы собственных обращений. Даже owner/admin видит только собственные tickets; scope — organization + user, без чтения чужих brand-owned данных.
- POST `/help/support` (`help.support.store`) — multipart subject/module/body/attachments/support_access, проверка и атомарное сохранение, JSON 201 с ticket и достоверным состоянием письма. Tenant/user/ID не принимаются из формы. Ограничение частоты 10 запросов в минуту.
- GET `/help/support/{ticket}/attachments/{attachment}` (`help.support.attachments.show`) — только собственное вложение собственного обращения; проверка текущей сессии, membership, path, размера и SHA-256. Ответ attachment, private/no-store, nosniff и sandbox CSP.
- POST `/help/support/{ticket}/access/revoke` (`help.support.access.revoke`) — идемпотентный отзыв своего действующего согласия и аудит.
- GET `/help/status` (`help.status`) — текущая проверка приложения/БД, доступные настройки провайдеров и честное отсутствие остальных источников.

Новые модели organization-owned, ULID. Composite FK связывают attachments/grants с организацией и владельцем ticket. `type=support` отделяет обращения от будущих plan_request. Тексты и имена файлов не входят в audit; используются topic/module, число вложений и факт согласия. Служебные пути/hash не входят в DTO.

## Вложения и уведомление

Файлы сохраняются на private local disk под серверными ULID, в storage собственного окружения. Имена отображаются в очищенном виде. Разрешены JPEG/PNG/WebP/PDF/plain text; текущие защитные ограничения — до 5 файлов по 5 MiB (feature config, не тарифные лимиты). Ошибка записи/audit/DB откатывает ticket/grant/metadata и удаляет созданные файлы. Нет public URL или прямого static download.

Письмо отправляется после завершения бизнес-транзакции, только если настроены SUPPORT_RECIPIENT, SUPPORT_MAIL_ENABLED=true, SUPPORT_SMTP_ENABLED=true и SUPPORT_MAILER с transport=smtp. Defaults отключают отправку; log mailer не используется для текста обращений. Фактический SentMessage означает sent; null/exception/прерванное sending — uncertain. CAS pending→sending предотвращает повторную отправку. Автоматического retry нет; uncertain требует проверки результата. В письмо входят номер, тема, модуль, описание и адрес для ответа; вложения остаются приватными в кабинете. Общий notification event catalog не расширяется.

## Согласие на 72 часа

Отдельная запись создаётся только при явном чекбоксе. `granted_at` и `expires_at` задаёт сервер; срок ровно 72 часа контролируется DB CHECK. На каждом чтении состояние вычисляется заново: `now >= expires_at` уже expired; отзыв действует немедленно. Scheduler не нужен для enforcement срока.

Это пользовательское согласие, а не staff identity или полномочие войти в чужой аккаунт. Согласно `docs/contracts/data.md`, механизма cross-account support в текущем кабинете нет, `entry_available=false`. UI прямо сообщает об этом. Donor `admin.support`, is_staff и синтетическая viewer membership не копируются; головная админка не создаётся.

## Статус сервиса

Успешная обработка текущего запроса подтверждает только этот ответ приложения; локальный SELECT 1 проверяет соединение БД. Остальные компоненты unknown без monitor source. Реальная базовая health route — `/up`; `/health` не добавляется. История инцидентов не подменяется пустым успешным результатом: available=false.

ProviderCatalog даёт конфигурацию supported/planned моделей, но не live availability. Собственный read boundary `Contracts/ProviderCooldowns::snapshot(TenantContext)` по умолчанию unavailable; actual `ai_provider_cooldowns`/read adapter в claim base отсутствуют. Полученный от будущего adapter действующий cooldown показывается как пауза; его отсутствие не означает operational. Отдельные тесты с fake projection проверяют mapping/expiry, но не доказывают интеграцию отсутствующего AI runtime source. Сетевых probes к провайдерам нет.

## Точные действия интегратора

1. Обновить shared `resources/js/types/generated/{routes.d.ts,translations.ts}` штатным `php scripts/generate-types/generate.php` после merge.
2. Для соответствия исходному «все роли могут написать в поддержку» добавить в shared `App/Tenancy/ResolveTenant.php` исключения для `help.support.store` и `help.support.access.revoke`, аналогично собственным notification settings. Module policy должна одновременно разрешить active viewer только создание собственного support ticket/отзыв собственного согласия; проверить own/foreign organization/user, revoked session/membership и отсутствие других viewer мутаций. Пока обе capability для viewer false, интерфейс не предлагает неработающее действие.
3. Операторский вход поддержки требует согласованного identity/access mechanism вне scope. Его consumer должен проверять identity, текущие tenant/grants, активность/срок/отзыв согласия на каждом запросе; согласие само по себе не даёт никаких дополнительных прав. Не включать console/organization impersonation из донора автоматически.
4. Владелец AI предоставляет tenant-safe read projection cooldowns/checked_at и adapter к Support ProviderCooldowns; интегратор заменяет default binding E1-12, не дублирует AI таблицы. Аналогично нужны реальные read sources мониторинга компонентов/истории инцидентов.

## Воспроизведение проверок

Backend: `php vendor/bin/pest tests/Feature/Shell/Support --compact` в выделенной PostgreSQL test DB. Frontend: `node node_modules/vitest/vitest.mjs run resources/js/features/Shell/Support`.

Browser fixture: APP_ENV=testing, E112_FIXTURE_ENABLED=1, E112_FIXTURE_ORG должен совпадать с CabinetID; затем `php tests/Browser/E1-12/prepare-fixture.php`. Fixture требует test DB marker, отличие от preview, проверяет коллизии, добавляет только собственные synthetic записи и не удаляет организацию/обращения. Запуск: RUN_SUPPORT_E2E=1, PLAYWRIGHT_BASE_URL=http://127.0.0.1:8212, PLAYWRIGHT_BROWSERS_PATH на own `.local/browsers`; `node node_modules/@playwright/test/cli.js test --config=tests/Browser/E1-12/playwright.config.ts`. Нужны актуальный production build и локальный testing server с public webroot. Итоги и ограничения — в `docs/results/SP-E1-12.md`.
