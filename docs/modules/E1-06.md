# SP-E1-06: чтение матрицы ролей

Первая функциональная часть карточки предоставляет `GET /team/roles/matrix` (`team.roles.matrix`). Это внутренний JSON endpoint с обычными для кабинета сессией, подтверждённым пользователем, проверкой версии авторизации и tenant; отдельно требуется `team.manage`, то есть по текущей конфигурации владелец или администратор. Ответ не кэшируется. Список участников, адреса почты и другие персональные данные endpoint не возвращает.

В `roles` передаются ключ и подпись пяти вариантов и их отображение на техническую роль membership и `sales_manager`. Редактор и менеджер — два варианта одной технической роли `member`, а не новые роли. В `abilities` каждая строка содержит ключ зарегистрированного role-based разрешения E0-03 и отдельный boolean для каждой роли. Источник — текущая конфигурация `permissions.abilities` и реестр реально зарегистрированных evaluator; неизвестные, незарегистрированные или оцениваемые другим feature разрешения не выдаются как работающие. Изменение `permissions.abilities` отражается в проекции без второй матрицы прав.

Эти значения описывают только типичные разрешения роли и не являются решением об авторизации пользователя: фактический доступ требует действующего участника, разрешённого активного бренда, включённых модулей и применимых политик конкретной модели. Это выражено в `limitations` ответа. Пользовательские роли и отдельные grants модулей не реализованы.

Экран `/team/roles`, список команды, изменение участников, приглашения и взаимодействия S-3.1–S-3.4 остаются последующими частями карточки. Ключи abilities предназначены для программной обработки; при создании экрана нужны понятные русские подписи и честное представление частичных прав, без сведения разных действий к ложному «полный доступ».
