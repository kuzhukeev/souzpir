# E3-04: ранний слой диалогов и каналов

Владелец первоначальной схемы: E3-04. Все модели tenant-scoped: без разрешённого контекста запросы не дают доступа; для дочерних записей составные FK связывают организацию, бренд и родителя. Чужой бренд через repository или inbound recorder получает 404. Доступность бренда пользователю проверяется вызывающим слоем и существующим tenancy middleware; сервисы принимают уже проверенный `TenantContext`. При смене исполнителя модель проверяет активное членство и доступ к бренду, FK также запрещает назначение человека вне организации. Review может создать только текущий actor с доступом к бренду.

Модели: `App\Seller\Conversations\Models\{Contact,Conversation,Message,SellerTask,MessageReview,SellerTurn}`, `App\Seller\Channels\Core\{ChannelAccount,ChannelInboundEvent}`, `App\Seller\Settings\BrandSellerSettings`. Поля описаны миграцией `database/migrations/E3-04/2026_10_31_060400_e3_04_create_seller_conversation_tables.php`. `channel_account_id` и `contact_id` у диалога могут быть null. Модели не реализуют экран, HTTP API или канальные адаптеры.

`ChannelAccount`: type `telegram|widget|api|email|whatsapp`, default_mode `bot|suggest|manager`, status `unconfigured|active|disabled|error|planned`; `settings` содержит только несекретные данные. Credentials хранятся Laravel encrypted cast в поле `credentials`, managers_chat_id также зашифрован; оба скрыты при сериализации. Проверка ключей settings отклоняет названия вроде token/password/api_key, но потребитель обязан проверять свои поля и не класть секреты в значения произвольных ключей. Ротация APP_KEY требует сохранения старых ключей Laravel и отдельного безопасного плана миграции. `ChannelInboundEvent.payload` скрыт при сериализации и может содержать персональные данные; доступ и срок хранения должен определить канальный слой.

`BrandSellerSettings` содержит defaults прототипа: follow-up 20 часов и максимум 2 автоматических, `second_hours=null` означает сохранить унаследованный расчёт (20 часов × номер отправки); off-topic streak 3 переводит в spam; negative streak 2; прямое использование цен каталога отключено. Остальные объекты намеренно не изобретают настройки. E3-02 и E3-03B обязаны применять собственные правила прототипа к отсутствующим полям и составлять начальный LeadState из E3-02, пустой JSON в новой строке диалога не является полноценным runtime state. Эта задача не реализует выполнение сценариев, подсчёт таймеров или фактическую отправку.

## Контракт для E3-03B

Экспортируется `App\Seller\Conversations\Contracts\ConversationRepository`: `find(TenantContext, string): ConversationState`, `claimTurn(TenantContext, TurnCommand): TurnClaim`, `commitTurn(TurnClaim, TurnOutcome): void`. DTO единственного владельца E3-04 находятся в `App\Seller\Conversations\Data`; это readonly объекты, изменять или дублировать их в E3-03B нельзя. Enum для режимов, ролей, типов каналов, задач и отзывов находятся там же.

- `TurnCommand(conversationId, inputMessageId, text, externalEventId, idempotencyKey, expectedVersion = null)`. Входное сообщение роли client заранее сохранено в этом диалоге; text обязан совпадать. `externalEventId` при наличии — ULID **внутренней** записи `channel_inbound_events`, принадлежащей каналу диалога; это не ID поставщика. Для канального входа адаптер вызывает `InboundRecorder::ingest(context, channelAccountId, externalId, payload, conversationId, text)`: event и client message связываются атомарно; затем в TurnCommand передаются `message.id` и `message.external_event_id`. Адаптер до ingest обязан проверить отправителя и выбрать его диалог: схема сама не устанавливает личность клиента по произвольному payload. `record()` сохраняет только event и не предназначен для создания входного сообщения.
- `claimTurn` возвращает `TurnClaim.status`: `claimed` (единственный владелец имеет доступ к секретному `token()`), `in_progress` или `finished` (у последнего есть сохранённый `outcome`). Повтор с тем же ключом и телом возвращает прежнее состояние; другое тело — 409. Ключ уникален в пределах бренда. Одно входное сообщение допускает один turn; использование другого ключа для него — 409. Один диалог имеет не более одной активной обработки. Хеш токена хранится в БД, сам токен нельзя логировать, сериализовать или отдавать клиенту.
- `TurnOutcome(turnId, conversationId, status, version, assistantMessageId, goal, guard, toolCalls, state, messages=[], tasks=[], events=[])`: status `completed|suggested|suppressed|failed`, version равна baseVersion+1. Каждый элемент messages содержит ULID `id`, `role` (`agent|system|tool`), `text`, optional `meta`; `assistantMessageId` при наличии обязан ссылаться на сообщение роли agent; элементы tasks содержат ULID `id`, `type`, optional `payload`, `due_at`, `status`, `priority`, `assigned_user_id`; events — проверяемые зарегистрированные DomainEvent envelopes. `commitTurn` проверяет token и version, сохраняет state/messages/tasks/outbox в одной транзакции, повтор того же outcome идемпотентен, конфликт отклоняется. Сам `commitTurn` ничего не отправляет и не вызывает LLM.
- LLM и внешние операции выполнять вне SQL транзакций. После зависания worker `processing` не освобождается по таймеру и не считается доказанно безопасным для повторных side effects; механизм восстановления/сверки и статусы доставки должны быть спроектированы владельцем runtime/адаптера. `failed` — сохранённый терминальный результат; автоматического повторного запуска здесь нет.

`InboundRecorder` атомарно дедуплицирует `(channel_account_id, external_id)`: то же тело возвращает запись, другое тело даёт 409. Тот же внешний ID на другом канале допустим. JSON hash нормализует порядок ключей объектов, порядок массивов сохраняется.

One inbound event can own only one turn even across different conversations and keys. Concurrent claims lock the inbound event and return 409 for reuse; exact same-key replay retains its original state. TurnClaim cannot be serialized or unserialized.

Привязка внешнего события к сообщению и диалогу неизменяема; уникальный event может иметь только одно сообщение. Канальный client message не может быть создан без event; null допускается только для внутренних сообщений в диалоге без канала. Claim сверяет ID события с origin сообщения; те же правила дополнительно проверяются в PostgreSQL. Повтор ingest с другим текстом или диалогом даёт 409. Claim и commit внутри транзакции проверяют и блокируют активную организацию, затем бренд в общем порядке E3-01. Если бренд был архивирован во время ожидания, запись отклоняется.

Удаление входного сообщения сейчас запрещено ограничением базы, чтобы не потерять связь с событием. Регламент хранения и контролируемое удаление с сохранением идемпотентности требуется отдельно спроектировать до внедрения удаления данных.

Канал диалога можно назначать или менять только до появления в нём любых сообщений. После первого сообщения связь сообщения с диалогом и канал диалога неизменяемы. Вставка сообщения и смена канала сериализуются блокировкой строки диалога; claim и ограничение БД дополнительно отклоняют старые неконсистентные записи с каналом и входом без события.
