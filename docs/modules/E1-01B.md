# Авторизационные сессии E1-01B

`auth_session_registry` хранит HMAC ID сессии, user ID, версию авторизации, срок и отметку отзыва. Исходный ID, cookie и remember token в таблице не сохраняются. `EnforceAuthVersion` на web-запросе проверяет запись и свежего пользователя; ранее выданные сессии без записи отвергаются и требуют нового входа. Login создаёт запись после смены ID, а `rotate(Request)` атомарно переносит привязку на новый ID. Прямое `session()->regenerate()` после авторизации без `rotate` отзовёт доступ к такой сессии.

Logout и `AuthSessionRegistry::withinActive(Request, Closure)` блокируют одну строку реестра и затем строку пользователя в одной DB-транзакции. При logout-first действие отвергается, при action-first logout ждёт его commit. Метод `withinActive` должен быть внешней транзакцией до любых domain/user locks; нельзя выполнять внутри него LLM, почту, webhook или другие долгие внешние вызовы. MFA setup/confirm/disable, подтверждение email и принятие приглашения подключены; при изменении MFA текущая запись и версия синхронизируются атомарно. Другие доменные операции требуют отдельной интеграции: одна проверка middleware не сериализует их с logout.

Для remember-me re-entry запись создаётся только после перепроверки токена по свежей строке пользователя под блокировкой. Её fingerprint привязан к remember token и проверяется при каждом запросе; вращение token на logout/reset/MFA отзывает такие восстановленные сессии. Независимые обычные сессии того же и других пользователей logout не удаляет. Смена пароля и MFA меняет `auth_version`, поэтому старые записи fail-closed; отдельная задача периодической очистки истёкших/отозванных записей ещё не создана. Истечение записывается с UTC offset и сверяется как абсолютное время.

## Обязательная интеграция

На текущем основном checkout требуют обёртки короткой транзакционной фазы `NotificationSettingsController::update`, `JournalController::retry`, `OnboardingController::draft/finish` и будущая запись результата `RecoveryService::inspect`. Для `LogoController::store` сначала безопасно принять файл во временное приватное место, затем под `withinActive` повторно проверить сессию и атомарно обновить DB; после commit опубликовать/перенести файл через надёжный outbox, при отказе или rollback удалить временный объект. Не писать файл в постоянное место до авторизации и не держать блокировку на обработку файла/сеть. Доставка verification email также требует outbox после проверки под lock. `BrandSwitchController` меняет только session state, однако может использовать тот же контракт для единообразия. Список нужно сверить с новыми маршрутами при merge.

Существующие тесты `TenancyTestCase::actingAs` создают фиктивную аутентификацию без записи и без cookie. Интегратору нужно в helper после `parent::actingAs`, настройки `auth.version` и создания нового session ID вызвать `issue` с тестовым Request и его реальным Session Store, затем передать session ID через `withCookie`; при смене пользователя изолировать сессию/ID. Middleware выключать или добавлять test-only bypass нельзя. Тесты реального входа и двухпроцессной файловой гонки остаются без bypass.


## Границы и хранение

Реестр пока не очищается автоматически: истёкшие и отозванные записи остаются в БД неопределённо долго. Это требует отдельной задачи с политикой сроков хранения, фоновой очисткой и проверкой гонок; перед реализацией удаления пользователя необходимо согласовать обработку записей и внешний ключ. Сырые cookies и session ID в реестре не хранятся.

Механизм подключён к web middleware; будущий stateful Sanctum/API и любые иные guard/session пути необходимо отдельно подключить и проверить на отзыв, восстановление remember-me и смену версии. Сам по себе текущий реестр не защищает stateless API tokens.

Middleware проверяет сессию в начале запроса и не прерывает уже начатый долгий GET при последующем logout. Для чувствительного чтения или выдачи данных после долгой работы нужна повторная проверка и сериализация короткой заключительной фазы с logout; никакие долгие вычисления или сеть нельзя выполнять под блокировкой. Для потоковых ответов после начала передачи отзыв не может отозвать уже отправленные байты.

Выдача remember token и cookie при входе происходит только после проверки версии свежей строки пользователя под блокировкой. Logout использует эту же свежую заблокированную строку, а не устаревший объект guard. Если завершение входа не удалось, guard и поставленная в очередь cookie очищаются.
