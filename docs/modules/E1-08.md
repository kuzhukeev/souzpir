# SP-E1-08 — личные настройки

## Пути и граница доступа

Страницы: `/profile/notifications`, `/profile/security`, `/profile`. Совместимые GET aliases `/settings/notifications`, `/settings/security`, `/settings/profile` подключаются этим feature; существующая ссылка меню уведомлений работает без изменения общей оболочки.

Личные endpoints используют группу `auth`, `verified`, `auth.version`, `auth.nostore`, `profile.context`. Общий `ResolveTenant` разрешает viewer только прежний PATCH уведомлений; новое `ProfileContext` обслуживает только личные маршруты. Для GET/HEAD оно делегирует существующему `ResolveTenant`. На мутациях оно берёт исключительно текущий server-session `brand_id`, активную единственную организацию Cabinet, собственное активное membership, точное совпадение `X-Brand-Id` при наличии и существующий `TenantContextRunner`. Нет fallback бренда на мутации и нет подмены HTTP method/route names. Общий tenant middleware не изменён.

`ProfileAccess::run` повторно проверяет и блокирует действующую сессию/user → organization → brand → membership непосредственно в транзакции действия. Viewer может менять свои настройки, но переданные user_id, organization_id, role или brand_id не дают права менять другого пользователя. Все бизнес-изменения и audit выполняются атомарно. Числовые throttle имеют отдельные prefixes по семействам действий: обычные profile/avatar/notification/session запросы не расходуют password/MFA лимиты. У email request и cancel/confirm, Telegram start и confirm/disconnect отдельные buckets из-за разных лимитов и окон; исходные значения лимитов сохранены.

## S-7.1: матрица и Telegram

Матрица строится из существующего `EventCatalog::TITLES`: сейчас 7 событий Продавца, 6 Видения и 3 кабинета. Отключённые или недоступные по плану модули скрываются; мутация их строк отклоняется. Предельный размер одного запроса определяется числом событий каталога и трёх каналов, поэтому новый event не блокирует сохранение полной матрицы. Фактическая `RecipientPolicy` отмечается `eligible`; preferences не расширяют доступ получателя. Defaults совпадают с runtime: кабинет включён, email/Telegram выключены.

PUT `/profile/notifications` принимает `changes: [{event,channel,enabled}]` и использует существующий `ConfigureNotification`. Сохранённая строка `notification_settings` непосредственно читается `NotificationProcessor`, `ExternalDelivery` и routing; отдельной демонстрационной матрицы нет. Неизвестные/повторные события, лишние ключи строки, отключённый модуль или Telegram без завершённой привязки отклоняют весь пакет атомарно.

Telegram использует отдельные `PROFILE_TELEGRAM_BOT_USERNAME` и `PROFILE_TELEGRAM_WEBHOOK_SECRET` (секрет >=32 символов). Оператор должен зарегистрировать webhook `/webhooks/profile/telegram` с Telegram secret header отдельно; разработка этого не делает. POST `/profile/notifications/telegram` создаёт одноразовый deep link на 10 минут только в защищённом контексте. База хранит SHA-256 токена, session временно хранит URL; audit не получает токен. Inertia получает только признак доступности; отдельный защищённый GET `/profile/notifications/telegram/link` повторно проверяет активные пользователя, бренд и токен и отвечает no-store redirect на Telegram. После потребления, отзыва или истечения redirect недоступен.

Для явно разрешённой локальной разработки Telegram capability также доступна по HTTP строго на `souzpir.local` при `APP_ENV=local`, непосредственном loopback-соединении по `VerifiedHttps::directLoopback` и без forwarding-заголовков. Это исключение не действует в production/testing или для других hostname и не расширяет доступ к MFA и email: у браузера на `http://souzpir.local` нет Web Crypto, поэтому их чувствительные Inertia props остаются закрыты. Telegram URL всё равно передаётся в заголовке отдельного redirect и на сторону Telegram; он не является Inertia prop. Реальное подключение бота и webhook не проверялось.

Webhook проверяет secret constant-time до чтения токена, ограничивает body, принимает только `/start <token>` в private chat, совпадение from.id/chat.id и пользователя, не бота. Токен однократно переводится в pending encrypted chat. Это ещё не подключение: авторизованный пользователь видит username/маску и явно подтверждает POST `/profile/notifications/telegram/confirm`. Пересланный deep link сам по себе не меняет получателя.

При подтверждении уникальная глобальная `profile_telegram_accounts.chat_fingerprint` не позволяет одному Telegram принадлежать двум пользователям. Тот же пользователь может использовать чат в нескольких своих брендах. Нельзя заменить connected chat без отключения; другой чат нельзя привязать, пока предыдущий используется в другом доступном бренде. При явном подтверждении нового чата удаляются только собственные старые bindings текущей организации в архивированных или уже недоступных брендах, их destinations очищаются. Доступные bindings и чужие данные сохраняются. Destination шифруется существующим ConfigureNotification, все события сохраняют прежнее enabled или false. DELETE отключает конкретный бренд, очищает destinations и выключает Telegram preferences; global reservation удаляется после последней активной привязки. Никаких outbound Telegram API calls в handshake нет.

Тест уведомлений обслуживает собственный `Profile/TestNotifications` (POST `/profile/notifications/test`): cabinet-тест сохраняется в `profile_test_notifications` и показывается в истории личной страницы, а не в общем inbox и не как выдуманный domain event. Внешние каналы требуют явной настройки транспорта. Повтор запроса идемпотентен; sending/uncertain автоматически не повторяются. Если процесс упал в sending, требуется операторский разбор результата передачи.

## S-7.3: профиль, аватар, email

PUT `/profile` сохраняет собственные name/phone и `profile_preferences` timezone/language. Поддерживается только ru; en не имитируется. Null timezone означает часовой пояс текущего бренда; роль и единственная организация доступны только для чтения. Ненужные идентифицирующие поля не принимаются как изменение аккаунта. Props отдельно передают `brand_timezone` и `effective_timezone`, чтобы подпись варианта по умолчанию не подменялась текущим личным выбором.

POST `/profile/avatar` принимает PNG/JPEG/WebP <=2 MiB и <=2048×2048, декодирует и заново кодирует PNG, удаляя вложенные metadata/content. Нормализованный файл <=4 MiB хранится только на private local disk под `users/{current_user_id}/profile/{random}.png`. GET отдаёт только собственный путь с no-store, nosniff и CSP. `avatar_url` включает версию от случайного storage path: повторная загрузка меняет img src и не оставляет старую картинку. При любой ошибке с неопределённым результатом транзакции новый файл сохраняется как потенциально используемый private orphan: слепое удаление после COMMIT небезопасно. Старый удаляется после commit best-effort; сбой очистки не уничтожает уже сохранённый новый файл. Остаточные старые файлы требуют отдельной эксплуатационной уборки, scheduler не создаётся.

POST `/profile/email` требует текущий пароль. Адрес нормализуется, проверяется против users и уникальных HMAC reservations активных pending changes. Старый verified email остаётся действующим. Intent хранит encrypted target/token, token hash, source-email HMAC, auth_version и срок 60 минут; повторный запрос инвалидирует предыдущий intent/link. DELETE отменяет только собственный незавершённый запрос и очищает секретные поля; повторная отмена и отмена после подтверждения не меняют итоговый статус и не создают ложный audit. Изменение и audit атомарны; неожиданная внутренняя ошибка не раскрывает её детали пользователю.

Письмо содержит relative-signed URL на canonical `config(app.url)` и случайный 256-bit token; Host header запроса не определяет адрес ссылки. GET только показывает подтверждение, отдаёт origin-relative action URL и включает шифрование Inertia history; подтверждение/отмена очищают history. POST требует того же текущего пользователя и активной сессии, валидной signature/token/TTL/source email/auth_version. Commit меняет email, сохраняет verified_at, повышает auth_version, ротирует remember token, сохраняет текущую lease и отзывает остальные версии. Старый token повторно не работает. Audit не содержит адреса или токена.

**Реальная смена email принудительно отключена даже при `PROFILE_EMAIL_CHANGE_ENABLED=true`**: прежняя ссылка содержит bearer в пути, который попадает в access log сервера. Вне тестового fake выдача и подтверждение отказывают до реализации безопасного capability flow без токена в HTTP URL, логах и Inertia history. `PROFILE_EMAIL_CHANGE_ENABLED=false` по умолчанию; log/array не объявляются доставкой. `DeliverEmailChange` кладётся в отдельную notifications queue after commit, payload содержит только ID. `profile:dispatch-email-changes --limit=100` планирует только durable pending intents после сбоя dispatch; scheduler автоматически не запускается. Sender вызывается вне транзакции, перед отправкой recheck user/version/org/brand/membership. Claim pending→sending — точка начала доставки: cancel/reissue после claim инвалидирует ссылку, но уже начатую передачу письма отменить нельзя. Sent/uncertain/sending автоматически не повторяются. Падение процесса после claim требует операторского разбора, а не blind resend.

## Локализация validation

Все новые Profile controllers и существующие MFA settings endpoints используют `ProfileValidation` и собственный `lang/ru/Shell/Profile/validation.php`. Ошибки required/type/размера/формата/пароля и подписи полей выдаются по-русски, а не как literal translation keys. `Password::min(12)`, подтверждение пароля, MIME, размеры и другие исходные правила сохранены; общий `lang/ru/validation.php` не менялся.

## Защита чувствительных Inertia props

Для выдачи временного MFA secret, Telegram capability и email confirmation capability сервер разрешает HTTPS, а для local/testing HTTP требует точный loopback host, фактические loopback REMOTE_ADDR и SERVER_ADDR и отсутствие forwarded headers. Host заголовок сам по себе не подтверждает локальность. За пределами local/testing HTTP loopback запрещён. При обратном proxy forwarded HTTPS принимается только от фактического peer из явно заданного набора IP/CIDR `trustedproxy.proxies`, с ровно одним `X-Forwarded-Proto: https` и без `Forwarded`. Универсальные сети `/0`, некорректные записи, wildcard, доверие по Host и устаревшее статическое состояние Symfony не подходят. Требуется запрет прямого доступа к backend и очистка входящих forwarding headers на доверенном proxy; HTTPS требуется для всего production кабинета. Обычный HTTP на `.local` или похожем hostname не считается безопасным. Прямой GET старой страницы `/mfa/setup` и GET/POST подтверждения email там отклоняются; основная `/profile/security` остаётся доступной, но передаёт `setup: null`. Запросы начала MFA и смены email отклоняются до создания secret/intent. Отмена и отключение уже настроенной MFA доступны.

Страницы с допустимыми чувствительными props используют `Inertia::encryptHistory()`, успешные профильные ответы получают `Cache-Control: no-store, private`, а завершение/отмена MFA и подтверждение/отмена email вызывают `clearHistory()`. Inertia само по себе может вернуть незашифрованные данные при отсутствии Web Crypto, поэтому одной настройки encryptHistory недостаточно: Profile UI дополнительно проверяет `crypto.subtle` и не начинает такие операции без него. Гарантия шифрования истории относится к поддерживающему Web Crypto браузеру в безопасном контексте; серверный guard предотвращает выдачу секрета на обычном HTTP независимо от поведения UI.

Смена email также требует безопасного canonical `APP_URL`: HTTPS либо один из перечисленных локальных адресов. Иначе intent не создаётся, `email_change_available=false`, а `email_confirmation_secure=false` позволяет UI объяснить настройку администратору. Заголовок Host не меняет canonical URL письма; непроверенный `X-Forwarded-Proto` не разрешает обход server guard.

`SecureAccountContextTest` проверяет создание/чтение MFA и email capability на HTTPS и трёх локальных адресах; отказ на HTTP до сохранения, отсутствие уже существующего MFA secret в ответе, невозможность HTTP-подтверждения email, доступность отмены/отключения и отказ для похожего hostname/поддельного forwarded proto.

## Интеграционные ограничения

1. Тихие часы и общая личная ежедневная сводка — source S-7.1 A, но сейчас отсутствует общий composable runtime hook. Единственный `notifications.router` уже принадлежит E6-07 (`SellerNotificationRouter`). Нельзя занять его повторно или изменить shared код вне scope. Controls показывают недоступность и не сохраняют неисполняемые настройки. Минимальный запрос интегратору: новый согласованный `PersonalNotificationTiming` contract/extension в `app/Shell/Notifications/Contracts/`, его композиция в `NotificationRouting::route`/`allowsImmediate` после personal opt-out и совместно с brand policy; контракт отложенного восстановления/доставки, позволяющий задержать каждого recipient/channel без блокировки всего outbox event. Потребуется отдельная задача на consumer/preferences/digest, затем включение UI. В актуальном main отдельно реализована сводка только продавца SP-E6-07: личное время на `/seller/settings/notifications/digests`, часовой пояс бренда и consumer; по умолчанию `SELLER_DIGEST_ENABLED=false`, внешняя доставка также отключена. Её наличие не реализует общие тихие часы и сводку всех модулей.
2. Generated route/translation contracts принадлежат интегратору; их нужно обновить после merge. Общий `generate.php --check` сообщает stale `translations.ts`; этот общий файл исполнитель не меняет. Новые production translations принадлежат `lang/ru/Shell/Profile/`; UI использует временный типизированный feature helper до общего generated update.
3. QR/TOTP и сессии описываются SecuritySettings/SecurityController. Резервные MFA-коды не реализованы: полноценный вход по ним требует согласованного recovery flow и расширения scope на `resources/js/pages/Shell/Auth/Mfa.tsx`, где сейчас допускается только `[0-9]{6}` при `maxLength=6`. Выдавать непригодные для входа коды нельзя. Геолокация не имитируется; IP и user agent хранятся только как данные собственной сессии.
4. Реальная SMTP/Telegram доставка и регистрация webhook не проверялись и не включались; в тестах только fake adapters/локальные requests. Общая рабочая БД и main не менялись.

## Дополнение после независимой проверки

Старые и новые маршруты настройки MFA дополнительно расходуют общий ограничитель на аккаунт: шесть попыток за минуту, проверка и увеличение под cache lock. Для нескольких процессов/узлов cache и lock должны быть общими и поддерживать атомарные блокировки. Лимит входного MFA challenge сохранён отдельно. При неопределённом результате сохранения аватара новый приватный файл сохраняется для будущей сверки, поэтому нужна безопасная эксплуатационная уборка orphan-файлов. Ошибки profile update и email query не раскрывают SQL bindings и исходное исключение.
