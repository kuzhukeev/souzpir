# E0-04: аудит и уведомления

Ядро зарегистрировано через config/features/E0-04.php. AuditWriter принимает TenantContext и AuditEntry внутри существующей транзакции; AuditedAction оборачивает мутацию и audit в одну транзакцию. AuditableModel подключает AuditObserver к модели явно. AuditLog ограничен организацией и запрещает изменение/удаление через Eloquent. Перед записью вложенные поля с именами паролей, ключей, токенов, адресов и сообщений редактируются. Для свободного текста и других чувствительных полей следует использовать явный allowlist в вызывающем коде, а не полагаться на фильтр имён.

NotificationDispatcher принимает DomainEvent с точным набором полей, перечисленным в docs/contracts/registry.json. Он записывает outbox внутри бизнес-транзакции и запускает обработку после commit. Повтор с тем же ID и теми же данными идемпотентен; разные данные с тем же ID отклоняются. NotificationProcessor под блокировкой outbox вычисляет получателей, проверяет организацию, активное членство и разрешённый бренд, учитывает личные настройки по событию и каналу и создаёт отдельную запись доставки. По умолчанию только cabinet включён; email и Telegram выключены, пока пользователь явно не настроит канал. Каталог содержит все notificationEvent из реестра, включая 7 Seller, 6 Vision и 2 общих события.

Внешняя отправка дополнительно выключена переменной NOTIFICATIONS_EXTERNAL_ENABLED. Для Telegram нужен NOTIFICATIONS_TELEGRAM_BOT_TOKEN; Telegram ID хранится шифрованным приложением. При настройке email требуется реальный сконфигурированный mailer: log/array не считаются отправкой. Тесты используют Mail::fake/Http::fake, никаких внешних вызовов не делается. Перед отправкой повторно проверяются членство, роль, бренд и настройка. Код ошибки хранится без текста исключения, URL или токена. Ошибки до начала передачи дают failed; исключение после начала SMTP/Telegram, null от Mail или ответ Telegram без подтверждения дают uncertain. Повтор допустим только для pending и явно проверенных failed: ни uncertain, ни sending автоматически не повторяются и требуют проверки оператором. notifications:drain обрабатывает неразобранный outbox и pending; ключ --retry-failed отдельно повторяет failed. Внезапное падение оставляет sending. Внешние почта и Telegram не гарантируют exactly-once.

HTTP: PATCH /notifications/settings в группе web/auth/verified/tenant, JSON event_key, channel, enabled и необязательный Telegram destination. Изменяются только предпочтения авторизованного участника текущего бренда. Неизвестное событие/канал — 422, неавторизованный — 401, чужой либо отозванный бренд — 404/403 по tenancy, каждая принятая мутация сопровождается audit в одной транзакции. ResolveTenant разрешает viewer только этот маршрут личных настроек при активном членстве и доступе к выбранному бренду; другие операции записи остаются запрещены.

Ограничения интеграции: настройки здесь личные (event × channel); D-11.4 дополнительно требует правил бренда «роль получателя / сразу или сводкой». Модель этих групповых правил и планировщика digest здесь не заявлена готовой; требуется согласовать владельца схемы и связать с SP-E6-07. Policy получателей намеренно консервативная: owner/admin и member для передачи диалога; расширение по утверждённым правилам должно проходить отдельные проверки. Внешние каналы в этой задаче предоставляют инфраструктуру, а подключение пользовательских интеграций принадлежит соответствующим последующим задачам. После внешней отправки и до сохранения sent возможна неоднозначность исхода; автоматической гарантии exactly-once у внешних API нет.
