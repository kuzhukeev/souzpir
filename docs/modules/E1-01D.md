# SP-E1-01D: отложенное подтверждение почты

Функция и SMTP отдельно выключены в `config/features/E1-01D.php`; интерфейс `VerificationTransport` по умолчанию привязан к `DisabledTransport`. Реальная почта не включается этим изменением. `SmtpVerificationTransport` реализован, но не привязан по умолчанию. Он строит временную подписанную ссылку стандартного `verification.verify`, передаёт письмо явно именованному SMTP mailer и считает отправку подтверждённой только при `Illuminate\Mail\SentMessage`. `sent` означает принятие транспортом, а не гарантированную доставку в ящик. `null` и любые исключения после входа в транспорт — `uncertain`. `KnownDeliveryFailure` допустим только когда передачи точно не было. Подтверждение адреса/ссылки или письмо не логируются этим модулем; перед live необходимо отдельно настроить redaction SMTP, query log, APM и обработчиков событий, которые находятся вне контроля модуля.

## Интеграция контроллера

`VerificationDelivery::enqueue(Request $request, string $key): array` принимает криптографически случайный стабильный ключ действия из 16–128 символов `[A-Za-z0-9_-]`; для повтора одной и той же операции клиент обязан сохранять тот же ключ. Внутри `AuthSessionRegistry::withinActive` блокируются сессия и пользователь, проверяется право и записываются intent, HMAC ключа и audit. Результат содержит `status` и непрозрачный `id` либо null: `pending`, `sending`, `transmitting`, `sent`, `failed`, `cancelled`, `uncertain`, `verified`, `disabled`, `conflict`. Не выдавайте `id` другому пользователю и не выдавайте `pending` за отправленное письмо. Для нового явного действия после известного `failed`/`cancelled` нужен новый ключ. `uncertain` блокирует повтор, требуется отдельное безопасное разрешение оператором; автоматического разрешения и повторов нет.

Повторная отправка в `VerificationController::send` сейчас напрямую вызывает Laravel notification и в scope этой задачи не меняется. Перед включением реальной почты интегратор должен заменить этот путь на enqueue и обработать статусы; сохранить защиту сессии и throttle. `RegisterController` и `InvitationController` также сейчас отдельно запускают `Registered`: для них нужно создать intent после выдачи активной сессии, убрать прямую отправку и проверить отзыв/истечение приглашения. Текущий общий `AUTH_EMAIL_DELIVERY_ENABLED` должен оставаться выключенным до закрытия всех трёх путей и проверки; прямые legacy-вызовы не защищены этим модулем.

## Интеграция очереди

После успешного commit intent передать в `Jobs\DeliverVerification` только его ID, например dispatch после commit на изолированную очередь уведомлений. Работа хранит только ID; `tries=1`, повторное исполнение также безопасно благодаря атомарному claim. Одна запись в БД переживает падение между созданием и dispatch: интегратору нужен ограниченный периодический scanner существующих `pending` и повторный dispatch на ту же очередь. Не сканировать для отправки `sending`, `transmitting` или `uncertain`. Сам модуль не запускает scheduler, worker или почту.

Создание намерения, захват и финальная проверка блокируют session → user → organization → invitation (по id) → membership → intent и проверяет действительность сессии, версию, remember fingerprint, активную организацию, участника/действующее приглашение, неподтверждённый и неизменившийся адрес. Перед транспортом эта проверка повторяется, статус атомарно меняется на `transmitting`, transaction завершается. Если logout произошёл до этой проверки, отправка отменяется. Без DB-lock во время SMTP невозможно атомарно отозвать отправку между последней проверкой и началом внешнего вызова; после начала отправка не считается отзываемой.

При аварии процесса зафиксированный `sending`/`transmitting` остаётся неоднозначным. `markUncertain(id)` только переводит его в `uncertain`, ничего не отправляет и безопасен при позднем ответе старого worker. Вызывать его может только отдельно авторизованная операторская процедура после проверки worker; публичного маршрута нет. Не выполнять повторную отправку автоматически. Проверять, что воркер не запускается внутри чужой открытой DB-транзакции.

В `verification_delivery_intents` и `verification_delivery_keys` отсутствуют raw email, session ID, idempotency key и подписанная ссылка; хранятся keyed HMAC для сверок. Capability claim остаётся в памяти процесса, не сериализуется и не передаётся очереди или клиенту. Физическая гарантия отсутствия секретов в сторонних трассах зависит от их конфигурации; такие трассы требуют отдельной проверки перед live.

Порядок блокировок должны соблюдать также все авторизованные операции отзыва и принятия приглашения. Существующий `InvitationAcceptance::accept` вне этого scope отдельно берёт organization → user; интегратор обязан привести его к согласованному порядку session → user → organization → invitation → membership, с регрессионным тестом на конкуренцию. PostgreSQL прерывает одну из транзакций при взаимной блокировке; не считать это поддержкой старого порядка. До интеграции и проверки live-почта остаётся выключенной.
