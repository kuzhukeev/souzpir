# SP-E8-02: анкета и профиль Видения

## Подключение к E8-01F

HTTP feature использует `Questionnaire` и `ProfileAccess` владельца SP-E8-01F: данные сохраняются в его `visibility_quizzes` и immutable `brand_profiles`, а не во второй схеме. Предпочтения и бренд берутся из серверного tenant/session context. Все операции проверяют действующую lease, права `vision.quiz.write`, членство и включённый модуль в транзакции. GET текущей анкеты и истории сначала выполняет авторизованное tenant-qualified чтение индексов и затем читает данные через Questionnaire; foreign ID не раскрывается. `quiz_id`/`revision` обязательны при изменении; старый revision или profile id возвращает конфликт и не затирает запись. Семь секций целиком сохраняются отдельными запросами, восьмой шаг — проверка. Submit атомарно создаёт версию профиля и audit; повтор с исходной revision идемпотентен. Редактирование создаёт новую версию; `/vision/profile/{id}` показывает конкретную историческую версию.

Конфигурация feature содержит лимиты для UI и может их уменьшить; общего жёсткого максимума E8-01F 10 конкурентов, 10 фактов, 15 вопросов она увеличить не может. Пустые факты допустимы. Сервер проверяет пределы до записи, общий сервис выполняет независимую окончательную проверку.

Чувствительные ответы не передаются логгеру даже при сбое. Контроллер перехватывает исключения до глобального exception reporter, отдаёт безопасное сообщение, для JSON различает 409/422/403. Приватные страницы и мутации доступны только через HTTPS либо loopback. До каждого ответа страницы с приватными Inertia props выполняется одноразовая проверка Web Crypto на нейтральной HTML странице: SHA-256 challenge, CSRF и grant на конкретный path/brand/user/auth.version. Ответ без поддержки crypto.subtle остаётся нейтральным, данные анкеты не отдаются. После проверки включён Inertia encrypted history, после записи — clearHistory. Mutations имеют JSON API, чтобы ошибочный ввод оставался в памяти формы без plaintext history/sessionStorage. Нужны корректный HTTPS `APP_URL` и доверенный proxy в эксплуатации. `auth.nostore`, стандартные session/auth/verified/tenant и CSRF включены.

## Дальнейшая интеграция

- E8-01F уже включает self-declared профиль в исторический snapshot замера, однако не передаёт его в AI и не подменяет опубликованный grant. Проверяется существующим fake runtime тестом. Для передачи анкеты во внешний ИИ нужны отдельные data class, policy и grant; таких вызовов в задаче нет.
- Только пользователям с `vision.settings.write` шаг названий предлагает title ранее сохранённой и audit-подтверждённой страницы текущего сайта бренда через `SiteDraftStore::read`; он проверяет свой `SiteImportAccess` и не обращается к сети. Редактору и при локальной ошибке подсказка недоступна. Для подсказок редакторам и иных полей нужен отдельный согласованный read-only контракт с фильтрацией приватных данных и tenant/permission checks; сканирование сайта из анкеты не запускается.
- Генерация кандидатов V-2 принадлежит SP-E8-03: batch в E8-01F находится в состоянии blocked, генератора/consumer нет. Интерфейс не имитирует готовность кандидатов и не отправляет запрос ИИ; полный сквозной сценарий №2 требует последующих задач вопросов/отчётов.
- Просмотр истории ограничен последними 100 версиями; pagination при большем числе требует отдельного улучшения.
- Общее меню navigation.json вне scope: отдельный пункт анкеты отсутствует, вход доступен из /vision. Интегратору требуется добавить ссылку на /vision с возможностью продолжить анкету, учитывая vision.quiz.write и ограничение числа пунктов меню; не добавлять новый общий пункт самостоятельно.

- Два одновременных начала приватного просмотра в разных вкладках одной сессии могут вытеснить одноразовую проверку друг друга: одна вкладка безопасно откажет и потребует повторного открытия. Данные при этом не передаются в нейтральную страницу.
