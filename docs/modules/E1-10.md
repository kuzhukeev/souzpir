# E1-10 — интеграции бренда (промежуточная реализация)

Полная приёмка не выполнена; блокирующие контракты перечислены в `docs/results/SP-E1-10.md`.

Маршруты настроек находятся в web/auth/verified/tenant, дополнительно используют auth.version и no-store. Для управления ключами и вебхуками требуются `integrations.write`, `brand.write` и действующий доступ к выбранному бренду. Аудит пишется в одной транзакции с изменением. Экран подключений читает статусы `channel_accounts` текущего бренда, не конфигурации другого бренда.

Ключ сохраняется как SHA-256, с маской последних четырёх символов. Секреты нового ключа или вебхука выдаёт только отдельный POST `/integrations/api/secrets`, единожды из заблокированной сессии, при совпадении организации, бренда и пользователя. Inertia получает лишь признак доступности; ответ секрета помечен no-store. Брендовый bearer guard и реальное применение abilities отсутствуют: ключи пока не работают на `/api/v1/*`.

Вебхуки включаются только операторским `INTEGRATIONS_WEBHOOK_DELIVERY_ENABLED=true`; по умолчанию внешняя отправка отключена. Независимый идемпотентный consumer читает стандартный outbox командой `integrations:webhooks-drain`; команда не запускается автоматически. Настройка защищает от запросов к частным адресам проверкой DNS, фиксацией разрешённого IP и запретом redirects. Тело подписано HMAC-SHA256, идентификатор доставки постоянен для дедупликации получателем. Каждому job доступно до пяти последовательных попыток; преждевременное падение может оставить `sending`, который не повторяется автоматически. Оператор должен проверять неопределённый исход до ручного восстановления; exactly-once не гарантируется.

Настройки и доставка корпоративного Telegram/email пока недоступны. Общие personal notification tables не используются для фиктивной реализации company-recipient.
