# E1-10 — интеграции бренда (промежуточная реализация)

Полная приёмка не выполнена; блокирующие контракты перечислены в `docs/results/SP-E1-10.md`.

Маршруты настроек находятся в web/auth/verified/tenant, дополнительно используют auth.version и no-store. Для управления ключами и вебхуками требуются `integrations.write`, `brand.write` и действующий доступ к выбранному бренду. Аудит пишется в одной транзакции с изменением. Экран подключений читает статусы `channel_accounts` текущего бренда, не конфигурации другого бренда.

Ключ сохраняется как SHA-256, с маской последних четырёх символов. Секрет нового API-ключа выдаёт только отдельный POST `/integrations/api/secrets`, единожды из заблокированной сессии, при совпадении организации, бренда и пользователя. Inertia получает лишь признак доступности; ответ секрета помечен no-store. Брендовый bearer guard поддерживает проверенный read-only `/api/v1/brand`; API диалогов и лидов пока недоступны. Настройка вебхуков и раскрытие их секретов закрыты.

Просроченные `integration_secret_receipts` удаляются отдельной командой `integrations:prune-secret-receipts`: один запуск удаляет не более 500 строк по умолчанию, допустимый `--limit` — от 1 до 1000. Заблокированные строки пропускаются и доступны для следующего запуска. При включённом общем scheduler задача регистрируется раз в пять минут; без запущенного scheduler команду требуется запускать оператору. Создание ключа не запускает очистку. Для корректного срока на разных узлах часы приложения должны быть синхронизированы.

Внешняя доставка всех вебхуков, включая ручной тест, временно недоступна независимо от `INTEGRATIONS_WEBHOOK_DELIVERY_ENABLED`: на экране показано предупреждение, а попытка ручной отправки получает 503. Обычные события не помечаются потреблёнными, новые доставки не создаются, команда `integrations:webhooks-drain` возвращает ошибку без обработки. Даже старые pending-записи не отправляются при прямом вызове сервиса. До включения нужны общий атомарный snapshot подписок в момент события, квитанция ручного теста, совместные транзакционные проверки и отдельное операторское разрешение на реальные вызовы. Исторические тесты подписи/DNS и отправки после commit приостановлены и должны быть восстановлены после внедрения контракта; exactly-once не гарантируется.

Настройки и доставка корпоративного Telegram/email пока недоступны. Общие personal notification tables не используются для фиктивной реализации company-recipient.
