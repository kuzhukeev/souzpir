## Почему исходные 74 строки нельзя запускать произвольно параллельно

1. `T-02` импортирует YAML в `knowledge_releases`, а создающая таблицы задача `E3-01` зависит от `T-02`. Формального цикла в колонке зависимостей нет, но есть фактическая обратная зависимость результата.
2. `E3-03` переносит Orchestrator и Tools с записью сообщений/задач, а модели `conversations/messages/seller_tasks` появляются в `E3-04`, поставленной после `E3-03`.
3. Фраза «можно параллельно» не отменяет зависимость: F-02 зависит от F-01, E0-03 — от E0-02, E7-03 — от E7-02. Нужен фактический merge результата зависимости в базовую ветку.
4. `E4-01` включает входящие из задач, пометок и супервизора, но зависит только от схемы знаний. UI этой части не завершить без договорённости о read-model/событиях.
5. `E1-07` собирает использование из Видения/продавца и создаёт тикет при заявке на тариф, но зависит только от планов. Нужны интерфейс UsageProvider и общий контракт тикетов.
6. `E1-10`, `E5-03` и `E6-09` затрагивают общие API-ключи, вебхуки и доставку. Общий слой имеет одного владельца; остальные используют его контракт.
7. `E4-05` и `E6-01` редактируют одни лимиты persona/Guard; `E6-04`, `E6-08`, `E5-07` пересекаются в Tools, цене, остатках и почте; `E6-03`, `E3-05` — в followup. Пересечение E1-04/E1-11 по удалению организации снято исключением этой функции пользователем.
8. Единые `routes/web.php`, `routes/api.php`, `routes/console.php`, service providers, shared props, `ru.json`, DTO-generated files, `composer.lock` и `package-lock.json` быстро становятся общей зоной конфликтов даже у разных экранов.
9. Миграции с одинаковыми временными метками и разные версии одной модели могут успешно смержиться текстом и сломать приложение логически. Каждая таблица и связь должны иметь владельца.
10. Общая БД, Redis prefix, mail/Telegram transport и порт dev-сервера делают разные worktree не независимыми. Изоляция требуется и для среды выполнения.

## Обязательный контрактный этап до основной параллельной работы

Подготовительная очередь должна начинаться с одной задачи фиксации контрактов и одной задачи создания исполняемого фундамента. Первые контракты можно разработать до установки приложения; исполняемые интерфейсы и fixtures проверяются после скелета.

Контрактный пакет фиксирует:

- ID и FK (ULID либо обоснованное согласованное решение после проверки исходников), имена таблиц/колонок, владельцев схем, правила временных меток миграций и уникальности;
- `TenantContext`, `BrandRuntime`, `KnowledgeSnapshot`, `AiGateway`, `PlanLimits`, `UsageProvider`, `ConversationRepository`, `ChannelDelivery`, аудит, уведомления, webhook delivery, tickets;
- технические роли `owner/admin/member/viewer`, флаг sales_manager, действия и permissions; tenant 404, validation 422, version conflict 409;
- envelope JSON-ошибок, пагинацию, форматы времени/денег, версионирование API, session/brand boundaries;
- полный словарь событий и minimal payload: organization/brand, aggregate ID, event ID, timestamp; идемпотентность и дедупликацию;
- shared props, DTO для независимых UI-пакетов, API fake fixtures, возможности `active/planned`, правила неизвестных лимитов;
- агрегирующие загрузчики маршрутов, переводов и конфигурации, чтобы feature-чаты добавляли собственный файл без изменения общего;
- правила imports/exports между доменами: Seller и Vision не читают таблицы друг друга напрямую для виджетов оболочки;
- согласованную точку, в которой изменения начинают влиять на активный релиз знаний, и семантику публикации/отката/оптимистического concurrency.

Изменение контракта после начала потребляющих задач оформляется как отдельная задача. Нельзя молча переделывать интерфейс под один экран.

## Исправленная последовательность и DAG

Последовательность ниже описывает логические ворота готовности, а не календарные даты.

1. **PREP:** контрактный реестр, ownership, источники и фикстуры; изолированный baseline audit прототипа. На текущей итерации допустимы только подготовительные артефакты.
2. **FOUNDATION:** E0-01 → tenancy/permissions/shared DTO. После skeleton параллельно допустимы дизайн-токены и подготовка baseline без live API.
3. **CORE:** AI, platform core, knowledge schema, conversation schema, Vision schema/core работают отдельно после общих контрактов. DESIGN последовательно доводит примитивы и каркас.
4. **BEHAVIOR:** knowledge schema → T-02 → Engine policy → orchestration → followups/evals → equivalence. Conversation persistence создаётся **до** orchestration. Vision переносится своей линией после AI. Результаты золотых сценариев обязательны до объявления эквивалентности; отсутствующие записи не заменяются фиктивной зелёной проверкой.
5. **FEATURES:** независимые Shell/Seller/Vision экраны и adapters после готовности их contracts/core/DS. Факт зависимости может быть удовлетворён интерфейсом с fixture для разработки UI, но завершение UI-задачи требует интеграционного теста с настоящим Action.
6. **INTEGRATION:** domain feature tests → cross-domain e2e → миграционный dry-run → документированный операторский запуск. Последние два шага требуют реальной среды/данных, которых нельзя объявлять существующими по ТЗ.

Критический путь: skeleton → tenancy/contracts → AI + knowledge/conversation schema → YAML equivalence → policy → orchestration/tools/guard → channels/live dialogues → replay equivalence → интеграционная приёмка. Дизайн, Shell и Vision идут параллельными линиями в пределах готовых контрактов.

XL из 10 обязательно разбить минимум так:

- E3-03: responder/tool execution, guard/fallback, orchestration/persistence integration. Orchestrator не редактируется одновременно несколькими задачами.
- E5-04: read API + actions; inbox/list/detail; suggestion/review flows. Общие DTO и query keys фиксируются до UI.
- E8-01: schema/read models; measurement runner; report preparation/metrics; SiteInspector adapter. Не объединять все сервисы в одну огромную очередь.
- E8-05: report sections; public publication page; competitors; source directories. Общие report DTO/metric definitions фиксируются раньше.

## Требования к карточке очереди и завершению задачи

У каждой runnable-задачи: стабильный ID; project key `souzpir`; цель; source IDs; screen IDs; `depends_on`; `allowed_paths`; `exclusive_resources`; запреты на чужие области; список deliverables; проверки; статус; branch/worktree; base commit; owner claim и время; результат/commit/тесты. Общая очередь должна выдавать только задачи, зависимости которых **смёржены и проверены**, а не просто «в работе» или «готов код».

Одна task branch/worktree на чат. Общий checkout `souzpir.local` — интеграционный. Изменять его параллельными чатами запрещено. Сливает один интегратор после проверки ownership и тестов; исполнители не делают force push и не перезаписывают чужие коммиты. Не создавать коммит с общей рабочей директорией, где находятся незавершённые изменения другого чата.

Для runtime каждой задачи отдельные `.env`, БД или схема, Redis prefix/queue names, session/cookie namespace, storage/cache/testing directories и порт. Реальные mail/Telegram/webhook/LLM по умолчанию заменены fake в тестах. Ветка не меняет общие локальные секреты.

Готовность feature означает реальный путь: UI → validation → Action → storage → применение → policy → аудит → тест. Skeleton UI, fixture-only backend и зелёные unit-тесты без интеграции не означают готовый экран. Для C/D достаточно честного read-only/«Скоро» поведения по утверждённому scope, без подключения несуществующего сервиса.

Минимальные проверки приёмки: тематические unit/feature, tenant isolation и матрица прав, поведение defaults vs enabled для ИИ-изменений, type generation/lint, визуальный просмотр затронутого экрана на 1440/1024/390 и a11y. Общий набор 8 e2e из 08 собирается постепенно и проверяется интегратором. Перезапись золотых fixtures или prompt snapshots ради прохождения теста — отдельное изменённое поведение с объяснением, не обычное обновление теста.

Состояние после текущей подготовки должно оставаться `planned/blocked-by-dependency`, без автоматического старта реализации. В следующей итерации пользователь сможет разрешить выдачу первой независимой волны.
