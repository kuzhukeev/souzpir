# Аудит и подготовка tasks.local к параллельным чатам

Дата проверки: 2026-10-31. Рабочая очередь: `C:/OSPanel/home/tasks.local`. Этот отчет описывает исходное состояние и подготовленный патч; факт установки и импорта фиксирует основной агент после отдельной проверки.

## Исходное состояние

- PHP 7.4 по `.osp/project.ini`, без фреймворка и SQL. Хранилище — `data/board.json`, на момент чтения 158 карточек, все `done`, `nextId=160`. Это архив выполненных задач на макеты, а не готовность кода проекта.
- `api.php` уже берет `flock(LOCK_EX)` на JSON-файл для каждого запроса. Это подходящая база для атомарного claim: проверка доступности и изменение выполняются под тем же lock.
- Исходные действия: GET `list`, GET `image`; POST `create`, `update`, `delete`, multipart `upload`. `create.legacyKey` обеспечивает идемпотентную миграцию старого localStorage/IndexedDB, но не импорт проектного плана.
- Исходные статусы: `queue`, `progress`, `done`. Нет project/taskKey/dependencies/ownership, атомарного взятия задачи или понятия проверки перед merge.
- Исходный `app.js` опрашивает API каждые три секунды. Проверка snapshot перед сохранением редактора выполняется двумя запросами, поэтому не защищает от гонки между ними; селектор статуса мог потерять чужое изменение вообще без проверки.
- В `board.json` встречаются дополнительные поля (`screen_code`, `readiness`); патч их сохраняет. Изображения и директории `completed`, `attachments` не изменяются подготовленным импортом.

## Подготовленные файлы

Патч находится в `.local/taskdesk-patch/`:

| Файл | Изменение |
|---|---|
| `api.php` | Подключает extension, делегирует новые действия, optimistic revision, запрещает обход проектного workflow через старый update/delete/upload, создает резерв предыдущего JSON перед записью |
| `queue.php` | Импорт, dependency DAG, готовность, path/resource ownership, claim/release/submit/review/resume/merge, восстановление заброшенной задачи |
| `app.js` | Колонка проверки, фильтр проекта, readiness/ownership подсказки, передача revision, запрет ручного обхода workflow селектором статуса |
| `index.html` | Фильтр `souzpir`/архив/все, статус review |
| `style.css` | Четыре колонки, адаптация и оформление метаданных |
| `test-queue.ps1` | Изолированные API-тесты, включая конкуренцию двух процессов PHP на одном JSON |

Файлы под `.local` являются локальными подготовительными артефактами. Для воспроизводимости основной агент может поместить проверенные рабочие файлы и extension в отслеживаемый каталог инструментов перед первым коммитом. Тестовые `test-run-*` не включать в Git.

## Импорт без запуска

POST `http://tasks.local/api.php?action=import`, `Content-Type: application/json`:

```json
{
  "project": "souzpir",
  "tasks": [
    {
      "taskKey": "SP-E0-01",
      "title": "Название независимого пакета работ",
      "description": "Самодостаточное задание или указание на promptPath",
      "dependsOn": [],
      "scope": ["docs/contracts/"],
      "exclusiveResources": ["api-contracts"],
      "wave": 0,
      "sourceRefs": ["docs/spec/10_backlog.md"],
      "acceptance": ["Проверяемый результат"],
      "screenIds": [],
      "promptPath": "docs/tasks/SP-E0-01.md"
    }
  ]
}
```

`taskKey` допускает латиницу, цифры, `_`, `.`, `-`, до 80 символов. Формат `SP-E0-01`, `SP-T-01`, `SP-C-01` допустим. Уникальность — пара project+taskKey. `title` ограничен 1200 байтами. `description` хранит текст целиком.

`scope` обязателен, это относительные пути файлов/каталогов в репозитории. Не поддерживаются wildcard, кроме нормализации конечного `/**` в путь каталога. `/` означает весь репозиторий. Абсолютные пути, `..`, `.`, `*`, `?`, `:` запрещены. Сравнение регистронезависимое для Windows: одинаковый путь либо родительский префикс означает конфликт. `exclusiveResources` — дополнительные именованные взаимные блокировки, например `composer-lock`, `npm-lock`, `db-schema`, `routes-shell`.

Импорт сначала валидирует весь batch и DAG, включая уже имеющиеся проектные задачи. Неизвестная зависимость, цикл, дублирование ключа, неправильный scope отменяют весь запрос до записи. Все новые задачи получают `queue`, revision=1; новый проект всегда `enabled=false`. Поле status в плане игнорируется. Идентичный повтор возвращает `created=0` и имеющиеся задачи. Изменение уже импортированного плана возвращает 409 вместо молчаливой перезаписи работы.

Пример PowerShell для подготовленного JSON:

```powershell
$body = [IO.File]::ReadAllBytes('C:\OSPanel\home\souzpir.local\docs\tasks\manifest.json')
Invoke-RestMethod -Method Post -Uri 'http://tasks.local/api.php?action=import' -ContentType 'application/json; charset=utf-8' -Body $body
```

После импорта проверить: все souzpir-задачи `queue`; `projects.souzpir.enabled=false`; исходные 158 карточек и их images неизменны. **В этой подготовительной итерации не выполнять project-mode enabled=true и не брать claim.**

## API для следующей итерации

GET `api.php?action=list` возвращает `{tasks,projects}`. Проектная задача имеет `revision`, `blockers`, `ready`; секрет claim не возвращается. GET `api.php?action=ready&project=souzpir` возвращает только доступные `queue`-задачи. Причины блокировки: `project_disabled`, `dependency:<taskKey>`, `ownership:<taskKey>`.

Все перечисленные ниже действия — POST JSON. Идентификатор задачи можно передавать как `id` либо как `project`+`taskKey`.

| action | Поля | Результат |
|---|---|---|
| `project-mode` | `project`, boolean `enabled` | Явное включение/остановка выдачи новых задач. Не прерывает имеющиеся claims |
| `claim` | идентификатор, `worker` (например ID чата) | Атомарно проверяет queue, проект, зависимости, ownership; возвращает `task` и **однократный `claimToken`**; status=progress |
| `release` | идентификатор, `claimToken`, `expectedRevision`, `reason` | Только владелец активной задачи возвращает ее в queue |
| `submit` или `complete` | идентификатор, `claimToken`, `expectedRevision`, полный `commit` SHA, `branch`, `summary`, массив `checks` | status=review, результат ветки сохранен. Ownership и token сохраняются. Зависимые задачи не разблокируются |
| `resume` | идентификатор, прежний `claimToken`, `expectedRevision`, непустой `reason` | Тот же исполнитель возвращается из review в progress для исправления замечаний, сохраняя владение |
| `merge` | идентификатор, `expectedRevision`, полный `mergeCommit` SHA | Только из review в done. Освобождает ownership и разблокирует зависимости |
| `requeue` | идентификатор, `expectedRevision`, непустой `reason` | Административный отказ в review с возвратом в queue и сбросом токена; использовать если задачу должен взять другой исполнитель |
| `recover` | идентификатор, `expectedRevision`, непустой `reason`, `confirmAbandoned:true` | Административное освобождение progress только после фактической остановки прежнего исполнителя |

Пример claim:

```json
{"project":"souzpir","taskKey":"SP-E0-01","worker":"codex-chat-id"}
```

Пример отправки результата:

```json
{
  "project":"souzpir",
  "taskKey":"SP-E0-01",
  "claimToken":"LOCAL_TOKEN_FROM_CLAIM",
  "expectedRevision":2,
  "commit":"0123456789abcdef0123456789abcdef01234567",
  "branch":"task/SP-E0-01",
  "summary":"Описание полученного результата",
  "checks":["Запущенные проверки и их результаты"]
}
```

Token хранится в локальном игнорируемом файле конкретного checkout/worktree, не в Git, не в описании карточки и не в сообщении другому исполнителю. Сервер хранит только SHA256 token; GET удаляет hash из ответа. Claims **не имеют автоматического срока истечения**. Долгий чат не должен потерять блокировку только из-за времени.

`review` продолжает удерживать scope/resources до merge. Иначе второй чат мог бы стартовать от main без еще не интегрированных изменений в тех же файлах. Независимые scope могут работать и проверяться параллельно. При `resume` используются тот же token и свежая revision.

`merge` на уровне PHP проверяет состояние, revision и синтаксис SHA, но не читает Git. Поэтому его вызывает только интегратор/CLI после проверки коммита в нужном репозитории и `git merge-base --is-ancestor <task commit> <integrated main commit>`. Простой результат в feature-ветке **не равен done**. Для squash merge нужна отдельная проверенная политика аттестации; базовый workflow использует обычный merge с сохранением ancestry.

`recover` не является автоматическим TTL и не должен вызываться чатами при случайном 409. Сначала человек/координатор удостоверяется, что прежний исполнитель остановлен и его изменения сохранены. Следующий claim получает новый token.

## Границы гарантий

- API сериализует metadata и проверяет ownership. Оно не предотвращает прямое редактирование чужих файлов в обход queue. Каждый чат обязан работать в своем Git worktree и соблюдать scope; общие lockfiles, схемы и root routes назначаются одному владельцу или эксклюзивному ресурсу.
- Проверка dependency требует `done` в том же проекте. Worktree создается только от main после фактического merge зависимостей, не от старого checkout.
- Проектные поля, зависимости и scope изменяются через новую версию подготовленного плана с явной миграцией, а не случайным перетаскиванием карточки. Обычный editor может исправлять title/description с revision, но не workflow, зависимости или ownership.
- Хранилище остается JSON под `flock`. Перед сохранением создается `board.json.bak`, проверяется кодирование и полная длина записи. Это защищает от потери предыдущей версии, но не заменяет SQL-транзакции при аварийном завершении ОС. Автоматического восстановления поврежденного файла нет: API отказывает, а оператор восстанавливает проверенный backup.
- Защита API остается рассчитанной на локальную машину (`127.*`/`::1`, проверка Origin). Это не многопользовательский сервер с внешней авторизацией; не публиковать tasks.local в Интернет.

## Проверки

Патч проверен PHP 7.4 CLI (`-n -l api.php`, `-n -l queue.php`) и Node.js (`--check app.js`). `test-queue.ps1` создает уникальный fixture внутри staged-каталога, запускает **два скрытых процесса** PHP на разных loopback-портах и завершает их в finally. Реальное хранилище tasks.local не используется.

Пройдено 30 проверок, среди них:

- 12 одновременных claim одного task через два PHP процесса: ровно один 200, остальные 409;
- параллельный claim независимых путей, блокировка пересекающихся путей и отдельного общего resource;
- запрещенный запуск disabled-проекта, dependency блокировка, сохранение ownership в review;
- resume исходным token, повторный submit, разблокирование downstream только после merge;
- отказ при неверном token, stale revision и попытке обойти workflow старым update;
- атомарный/idempotent импорт, cycle/missing-dependency/invalid-scope rejection, отказ перезаписать измененный план;
- сохранение legacy custom fields, отсутствие частичных задач после ошибочного импорта;
- явное восстановление заброшенного claim только с подтверждением.

## Установка основным агентом

1. Сделать timestamp-копию `api.php`, `app.js`, `index.html`, `style.css`, `data/board.json` в локальный backup внутри souzpir. Проверить исходные hash из `source-hashes.json`, если с начала аудита были чужие правки.
2. Скопировать только четыре измененных рабочих файла плюс новый `queue.php` в tasks.local с разрешением на запись вне workspace. `data/board.json` из тестового fixture **не копировать**.
3. Проверить GET list и открытие существующей картинки; сравнить исходные task IDs/count/metadata. Внести manifest через import, затем повторить import для проверки `created=0`.
4. Оставить проект disabled и все новые карточки queue. Не запускать новые чаты и не брать задачи в этой итерации.
