# Кандидат rollout: аргументы в трассах PHP

База `07c54de`. **Неактивное архитектурное предложение:** продуктовый guard, bootstrap, OSPanel и рабочая БД в этой ветке не менялись. Цель — не допускать запуска чувствительного продукта с `zend.exception_ignore_args=0`, не меняя настройку во время обработки данных или работы fibers. `public/.user.ini` уже добавлен в main для текущего Apache/FastCGI, но не покрывает CLI и не является полной защитой.

## Проверенное на текущей машине

- OSPanel PHP 8.4.19, `cgi-fcgi`: в отдельном временном каталоге с исходным `.user.ini` `0` ранняя проверка в начале PHP-скрипта смогла вызвать `ini_set(..., '1')` и прочитать эффективное `1` до загрузки приложения. Контрольные соседние запросы остались `0`; обрабатывались разными PID, поэтому перезапуск/изоляция состояния **одного и того же** FCGI-процесса между запросами не доказаны. Каталог был ограничен loopback и удалён, OSPanel и конфигурация сайта не менялись.
- В CLI синтетический ранний алгоритм: при исходном `0` и доступном `ini_set` получил `1`; при уже установленном `1` и отключённом `ini_set` допускает запуск; при `0` и отключённом `ini_set` завершился с кодом 78. Вызов без setter не должен сам вызывать отключённую функцию или выводить данные.
- Родительский `php -d zend.exception_ignore_args=1` запустил `PHP_BINARY` без `-d`: родитель показал `1`, потомок — `0`. `ServeCommand::serverCommand()` создаёт отдельный `php -S` без копирования `-d`. Изолированный настоящий PHP built-in server с `.user.ini` в каталоге вернул `PHP_SAPI=cli-server`, `ignore_args=0`: `.user.ini` там не действует.
- Отдельная более ранняя проверка настоящего Laravel `queue:work database --once` на временной PostgreSQL и своей очереди: обычный worker имел `0`, обнаружена захваченная synthetic closure; запуск с `php -d ...=1` дал `1`, args отсутствовали. Временные job, скрипт, таблица и база удалены. Эти пробы **не проверяют предлагаемый продуктовый guard**, которого пока нет.

## Почему сейчас только документ

1. Два основных entrypoint — `public/index.php` и `artisan`. Но рабочий `bootstrap/app.php` также подключается напрямую из `scripts/generate-types/generate.php`, `scripts/ci/assert-browser-database.php` и множества тестовых fixture/worker; существуют и неуправляемые сторонние entrypoints. Проверка только в index/artisan не обеспечивает общую гарантию для них. Перенос проверки без подготовки в bootstrap сломает запуск процессов с текущим CLI `0`, включая Composer `post-autoload-dump`, генерацию типов, CI и многочисленные `PHP_BINARY` subprocess.
2. Существующие security-тесты намеренно ставят `0`, включая `OutboxTracePrivacyTest`, `PrivateTraceTest`, `SupportRequestBoundaryTest` и Vision/AI tests. Нельзя незаметно превратить их в зелёные за счёт общего переключения или сделать небезопасный обход по одному `APP_ENV=testing`: нужны изолированные synthetic harness и неизменяемая проверка того, что такой режим никогда не используется для живого HTTP/worker и данных.
3. `ini_get_all(...)[...]['access'] = 7` допускает дальнейшее `ini_set` из PHP-кода. Стартовая проверка `1` сама по себе не доказывает, что следующий код или соседняя coroutine не понизит значение; `app/Privacy/SupportRequestBoundary.php` уже содержит условную временную смену настройки. Для долгоживущих worker, Octane/Swoole/RoadRunner и иных непроверенных runtime нет доказанного общего enforcement/изоляции. Простого списка имён окружения недостаточно, чтобы обнаружить все нестандартные bootstrap пути.
4. Laravel daemon `queue:work` вызывает Looping до очередного pop, но `queue:work --once` идёт через `runNextJob()` и не вызывает этот цикл. Hook только на Looping не покрывает once, sync/deferred workers, scheduler и пользовательские runners; отдельно проверить ошибку/десериализацию **до** передачи задания в пользовательский код. Уже работающие до rollout процессы не выполнят startup guard повторно.

## Требования к реализуемому rollout

1. Утвердить полный список поддерживаемых SAPI, server/worker entrypoints и механизмы запуска. До пользовательских обработчиков/fibers и загрузки приложения в каждом из них, а лучше в защищённой конфигурации соответствующего процесса, получить эффективное значение `1`. Раннее однократное включение допустимо только после подтверждения изоляции и совместимости выбранного SAPI. Если уже `1`, отсутствие `ini_set` допустимо; если не `1` и безопасно выставить/перепроверить не удалось, fail closed: HTTP 503 с константным ответом без request, CLI ненулевой код до выполнения команды или задания. Не выводить аргументы, секреты и конфигурацию в diagnostic.
2. Отдельно решить предотвращение снижения значения после запуска: предпочтительна неизменяемая per-pool/per-service конфигурация и доказанная политика PHP-кода; для daemon workers — контроль **перед извлечением каждого задания**, плюс защита `--once`, scheduler и subprocess. Непроверенные long-lived, coroutine и альтернативные веб-серверы блокировать до отдельного подтверждения. Корректность проверки самого отказа и отсутствия обработки job обязательна, в том числе при `ini_set` отключён и при его отказе.
3. Покрыть `artisan serve` **дочерний** cli-server, а не только родительскую команду; параметры CLI и `.user.ini` ему автоматически не наследуются. Убедиться, что прямой запуск приложения/скриптов и все subprocess получают политику. Для supervisor/systemd/Windows services/scheduler параметры передаются каждому реальному PHP процессу. Не менять общий PHP/OSPanel других проектов.
4. Изолировать тесты с `0` в контролируемых subprocess на синтетических данных и отдельной БД, не вводя production-доступный флаг обхода. Проверить существующие тесты и миграции, Composer install/autoload, сборку типов, browser CI, реальные HTTP through CGI/FastCGI и cli-server, настоящий `queue:work` в daemon и once, scheduler и spawn child при обоих значениях и отключённом setter. Проверять effective ini и отсутствие аргументов в структурированном trace после фактического старта каждого процесса.
5. Учесть `.user.ini` cache TTL текущего FCGI 300 секунд и перезапуск/замену уже живых процессов. Проверить не один случайный PID, а все экземпляры. Изменения конфигурации/перезапуск сервера делать только отдельным согласованным локальным rollout, не трогая другие сайты.

Даже успешный rollout не скрывает payload в тексте ошибки, SQL bindings, ранее сохранённых исключениях, HTTP responses и логах провайдеров; отдельные безопасные error boundaries и проверка redaction необходимы. Сроки диагностики и требования к логам согласовать до удаления полезной информации. Существующий partial fix Outbox и Seller ограничивает исходные exception chains, но не доказывает сокрытие closure caller при `0`.
