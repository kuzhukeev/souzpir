# ТЗ на UI кабинета клиента: оболочка, модуль «Видение», Диалоговый модуль (ИИ-продавец)

Версия 1.0 · 28.10.2026 · Назначение: по этому документу Codex отрисовывает все экраны кабинета клиента. Документ описывает только кабинет клиента (компания, купившая модули). Внутренняя консоль EYON (staff) в объём не входит.

## 0. Как пользоваться документом

### 0.1 Что нужно получить от Codex

Статические макеты экранов, пригодные для переноса в Blade-шаблоны существующего приложения `eyon-pilot` (Laravel 13, Blade, Tailwind CSS 4, без SPA).

Формат выдачи:

```
mockups/
  index.html                  галерея всех экранов со ссылками, фильтр по модулю и готовности
  theme.css                   CSS-переменные тем (см. раздел 1.3), подключается на каждом экране
  shell/S-0.1-login.html      один файл на экран, имя = ID экрана из этого документа + slug
  shell/S-1.1-dashboard.html
  vision/V-5.1-report-main.html
  seller/D-2.2-dialog.html
  ...
```

Правила для макетов:

- Tailwind 4 (CDN допустим для макетов), шрифт Manrope (уже есть в проекте: `public/brand/manrope-*.woff2`).
- Каждый экран рисуется в теме клиента, заданной атрибутом `<html data-theme="confectionery">` или `data-theme="pyro"`. Переключатель темы — в шапке галереи `index.html`. Макет не должен содержать захардкоженных цветов бренда, только переменные из `theme.css`.
- Моковые данные правдоподобные и соответствуют теме: в теме «Кондитерская» — торты, свадебные заказы, кафе-партнёры; в теме «Пиротехника» — салюты, петарды, оптовые точки, сезон ноябрь–декабрь. Словари значений (стадии, статусы, типы задач) — только из Приложения А, не выдумывать свои.
- Для каждого экрана обязательны три состояния, если в описании экрана не сказано иначе: основное (с данными), пустое (первый вход, данных нет), загрузка/ошибка. Пустое и ошибочное состояния можно рисовать как отдельный блок внизу того же файла под заголовком «Состояния».
- Ширина основного макета 1440 px; для экранов, помеченных «моб.», дополнительно 390 px.
- Никаких эмодзи в интерфейсе. Иконки — линейные, один набор (Lucide или аналог), размер 16/20 px.

### 0.2 Структура описания экрана

Каждый экран описан одинаково:

| Поле | Что означает |
|---|---|
| ID и название | `S-` оболочка, `V-` Видение, `D-` Диалоговый модуль. Номера совпадают со структурными картами (01/02/03 png). |
| URL | Целевой адрес в кабинете. В скобках — существующий маршрут `eyon-pilot`, если он уже есть. |
| Роли | Кто видит экран: Владелец, Администратор, Редактор (руководитель продаж / маркетолог), Менеджер, Наблюдатель. Подробно — S-3.3. |
| Готовность | A / B / C / D, см. 0.4. |
| Состав | Блоки сверху вниз, слева направо. |
| Данные | Откуда берётся содержимое (таблицы и файлы реальных репозиториев). |
| Действия | Кнопки, формы, их результат. |
| Состояния | Пустое, загрузка, ошибка, заблокировано, особые. |

Из M3 остаются: виджет, Telegram-канал, инбокс менеджеров как основа ленты диалогов, разметка «хорошо/плохо» ответа, импорт переписок и теневой прогон (`/data`).

### 0.4 Легенда готовности

| Код | Значение | Как рисовать |
|---|---|---|
| **A** | Данные и логика уже есть в одном из репозиториев. Экран — интерфейс поверх существующего. | Полноценно, это v1. |
| **B** | Логика есть, но параметры живут в YAML / `.env` / `config` прототипа и общие для всех. Нужно перенести в БД с привязкой к бренду (миграция + CRUD), **без изменения поведения агента**. | Полноценно, это v1. В макете пометка «B» в углу. |
| **C** | Требует изменения логики агента или платформы (рефакторинг кода, не только хранилища). | Рисовать, но помечать как «v2» бейджем в макете. В v1 экран показывается как «настраивается командой EYON при внедрении» с текстом текущих значений только для чтения. |
| **D** | Нет ни в одном репозитории (платёжный провайдер, VK, реальный WhatsApp, календарь). | Рисовать как заглушку «Скоро» с описанием, что будет, или не рисовать (указано у экрана). |

### 0.5 Честный ответ: можно ли править ИИ-продавца без программиста

Да, в значительной части, но не целиком. По коду прототипа граница проходит так.

**Правится через кабинет без кода (B — только перенос YAML в БД).** Всё, что сейчас лежит в `resources/knowledge/*.yaml` и читается классом `Knowledge` при каждом ходе:

| YAML | Что это | Куда в кабинете |
|---|---|---|
| `facts.yaml` | атомарные факты по темам, `must_not`, `bridge_hint`, ссылки `{cond:...}` | D-4.3 Факты, D-4.4 Факт |
| `conditions.yaml` | цифры условий: минималка, сетка скидок, предоплата, доставка, акции; `approved_by`, `max_pct_unapproved` | D-4.5 Условия |
| `intents.yaml` | темы вопросов клиента и привязка к фактам | D-4.6 Темы, D-4.7 Тема |
| `fewshot.yaml` | образцы реплик по тегам, `confidence` | D-4.8 Образцы речи |
| `closed_topics.yaml` | закрытые темы и как их закрывать | D-4.9 Запреты |
| `guard_rules.yaml` | запрещённые обещания, стилевые ограничения (регулярки, severity block/warn) | D-4.9 Запреты (вкладка «Обещания и стиль») |
| `persona.yaml` | имя, роль, представление, тон, длина, якоря, стоп-фразы, hard_bans | D-6.1, D-6.2, D-6.3 |
| `policy.yaml` | порядок вопросов по типу клиента, лимиты, стадии, tools по стадиям, триггеры по стадиям | D-5.1 (порядок и лимиты), D-5.2 Воронка, D-5.6, D-5.7 |
| `escalation.yaml` | причины передачи человеку, приоритет, что сказать клиенту, поведение после передачи | D-5.3 |
| `triggers.yaml` | приёмы продаж: когда уместен, суть, примеры, лимит на диалог | D-5.4 |

Плюс параметры из `config/agent.php` и `.env`: имя агента, модели по компонентам, температура, режим «суфлёр» (`SUGGEST_MODE`), чат менеджеров в Telegram, `fallback_reply`. Это тоже B.

**Требует программиста (C).** Жёстко зашито в PHP и в текстах промптов:

1. **Набор полей карточки клиента** — константы `LeadState::SLOTS` и `PRIORITY_SLOTS` (16 полей: city, purpose, experience, outlet_type, outlet_floor, categories, brands_interest, current_supplier, competitor_discount, budget_range, timing, legal, email, messenger, next_contact_at, name). Добавить поле «тип торта» для кондитерской сейчас нельзя без кода.
2. **Нормализация значений полей** — в промпте `extractor.blade.php` прописаны допустимые значения: `outlet_type → павильон | ТЦ | жилой дом | интернет | с машины`, `categories → салюты, петарды, мелочь, всё` и т.д. Это пиротехника, зашитая в текст промпта.
3. **Типы клиента** (`unknown / newbie / experienced / for_self / prices_only`) и правила их определения — метод `Policy::clientType()`.
4. **Машина стадий** и порядок принятия решений — `Policy::stageBySlots()`, `Policy::decide()` (жёсткие ветки: opt_out, prompt_injection, closed_topic, handoff и т.д.). Параметры из `policy.yaml` на неё влияют, но сами ветки — код.
5. **Домен в системных промптах** — «отдел оптовых продаж пиротехники (компания «Союз Пир», Москва)» в `extractor.blade.php`, «(Москва, оптовая пиротехника)» в `responder.blade.php`, ссылки на «прайс» в инструкциях.
6. **Список tools** (`send_price`, `calc_delivery`, `check_stock`, `send_requisites`…) — `ToolRunner.php`; для кондитерской нужны другие действия («отправить каталог», «проверить дату»).
7. **Регулярки Guard** проверяются в коде по паттернам из YAML — паттерны править можно (B), но новый тип проверки — код.

**Вывод для ТЗ.** В v1 кабинет позволяет клиенту полностью управлять знаниями, условиями, речью, запретами, приёмами и правилами передачи. Поля карточки, типы клиентов, нормализацию и действия бота в v1 настраивает EYON при внедрении (экраны D-5.1, D-5.7 рисуются как «только чтение + запрос изменения»). Чтобы они стали редактируемыми, нужен один рефакторинг: вынести схему карточки (поля, допустимые значения, порядок по типу клиента) и домен из промптов в конфигурацию бренда, из которой собираются промпты Extractor/Responder. Это задача на бэкенд, не на UI; UI в этом ТЗ уже спроектирован под неё.

### 0.6 Объём v1 (что рисовать в первую очередь)

Порядок отрисовки: оболочка целиком → Диалоговый модуль разделы 1, 2, 3, 4, 6, 7.1–7.3, 9 (виджет и Telegram), 11 → Видение целиком → остальное Диалогового модуля. Разделы с готовностью D рисуются последними или как заглушки.

### 0.7 Три роли в кабинете и их «дом»

- **Владелец** заходит узнать, работает ли бот и окупается ли. Дом: Главная S-1.1 и Сводка модуля D-1.1.
- **Редактор** (руководитель отдела продаж, маркетолог) учит бота говорить правильно и готовит замеры видимости. Дом: База знаний D-4, Качество D-7, Анкета и Вопросы V-1/V-2.
- **Менеджер** забирает переданные диалоги и ничего больше не читает. Дом: Диалоги D-2.3 «Мои» и D-2.4 «Очередь подсказок».

Каждый экран должен отвечать на вопрос «кто сюда пришёл и зачем» за три секунды: заголовок + одна строка подзаголовка + главное действие справа.

## 1. Дизайн-система кабинета

**Левое меню (260 px, фиксировано).**
- Верх: логотип клиента (из карточки бренда, S-2.3) + подзаголовок бренда («Оптовые поставки кондитерки»). Клик — переключатель бренда (S-0.7), если брендов больше одного; иначе ведёт на Главную.
- Пункт «Главная».
- Группа «Модули»: подключённые модули бренда раскрывающимися блоками. Внутри блока — разделы модуля (для Видения — 11 пунктов, для Продавца — 11). Неподключённый модуль показывается серым с пометкой «Подключить» → S-2.4.
- Группа «Кабинет»: Компания и бренды, Команда, Тариф и оплата, Интеграции, Журнал, Настройки, Помощь. Пункты скрываются по роли (Менеджер видит только Настройки и Помощь).
- Низ: промо-карта бренда (иллюстрация + одна фраза + стрелка; содержимое из темы, см. 1.3) и блок пользователя (аватар-инициалы, имя, роль).
- Активный пункт — заливка `--brand-primary`, белый текст, радиус 12. Бейдж-счётчик (янтарный) у «Диалоги» — число диалогов, ожидающих менеджера; у «Главная» — число пунктов «Требует действия».
- Моб.: меню скрывается за кнопкой-гамбургером, выезжает слева.

**Шапка (64 px).**
- Глобальный поиск (ширина 400 px): по клиентам, диалогам, фактам, вопросам видимости. Результаты — выпадающий список с группировкой по типу, до 5 на группу, «Показать все» ведёт на список с фильтром.
- Переключатель режима каналов: таблетка «Сайт · Автономно» с точкой-статусом (зелёная автономно, янтарная подсказки, серая выключен). Клик — выпадающий список каналов бренда с режимом каждого и ссылкой «Настроить каналы» (D-9.1). Показывается только при подключённом Диалоговом модуле.
- Колокольчик с красной точкой — выпадающий список последних 8 уведомлений (S-1.3), «Все уведомления».
- Пользователь: имя, роль, меню: Профиль (S-7.3), Сменить компанию (S-0.7), Выйти.

**Заголовок страницы.** H1 32/40 px, подзаголовок 16 px серый. Справа — селектор периода (где уместен) и одна главная кнопка. Вторичные действия — в меню «···».

### 1.2 Сетка и типографика

- Контейнер контента: максимум 1180 px, отступы 32 px. Сетка 12 колонок, межколоночный отступ 24 px.
- Карточка (`panel`): белый фон, радиус 16, тень `0 1px 2px rgba(32,27,48,.06), 0 8px 24px rgba(32,27,48,.04)`, внутренний отступ 24.
- Шрифт Manrope. Размеры: H1 32/700, H2 (заголовок карточки) 20/700, H3 16/600, текст 14/500, подпись 12/500, крупная цифра KPI 36/800.
- Таблицы: класс `data-table` из проекта — заголовки 12 px капс серые, строки 56 px, hover-подсветка, последняя колонка — действия, выравнивание чисел вправо.
- Фокус: кольцо 4 px цвета `--brand-primary-soft` (уже так в `app.css`).

### 1.3 Темы под клиента

Тема задаётся на уровне бренда (S-2.3, блок «Оформление кабинета») и хранится в `brands.settings.theme`. Кабинет не перекрашивается «в цвета сайта клиента» произвольно — клиент выбирает один из готовых пресетов отрасли и загружает логотип. Это гарантирует контраст и единый вид.

Переменные `theme.css`:

| Переменная | Назначение |
|---|---|
| `--brand-primary` | активный пункт меню, главные кнопки, линии графиков «наш» ряд |
| `--brand-primary-soft` | заливка иконок KPI, фокус-кольцо, hover |
| `--brand-accent` | второй ряд графика, акценты, бейдж «внимание» |
| `--canvas` | фон страницы |
| `--sidebar` | фон левого меню |
| `--surface` | фон карточек (всегда белый или почти) |
| `--ink` | основной текст |
| `--muted` | вторичный текст |
| `--ok / --warn / --danger` | статусы: зелёный / янтарный / красный — одинаковые во всех темах |
| `--hero-image` | иллюстрация в шапке Главной и Сводки модуля (правый верхний угол, 420×180, обрезка мягкой маской) |
| `--promo-image`, `--promo-text` | промо-карта внизу меню |

### 1.5 Правила состояний и текста

- Загрузка: скелетоны серые (не спиннеры) для таблиц и карточек; спиннер только в кнопках.
- Ошибка: красная карточка внутри контента с кодом и кнопкой «Повторить». Никаких технических стеков.
- Сохранение форм: кнопка внизу справа становится активной только при изменениях; при уходе с несохранёнными — модалка.
- Все даты в часовом поясе бренда (`brands.timezone`), формат «17 апр, 14:02»; относительное время («5 мин назад») только в лентах.
- Деньги: «12 400 ₽», пробел-разделитель тысяч; доллары расходов ИИ показываются только в Тарифе и в консоли EYON, клиенту — в рублях или в «единицах» тарифа.
- Тон текста: обращение на «вы», коротко, без канцелярита. Названия сущностей для клиента: «факт», «условие», «тема вопроса», «образец речи», «приём», «передача менеджеру», «замер», «набор вопросов». Внутренние термины (intent, slot, Guard, Extractor, prompt set) в интерфейсе не используются, кроме раздела «внутренности хода» для разборов, где они даны мелким серым.

## 3. Модуль «Видение» (V-)

Поток клиента: Анкета → Вопросы → Замер → Уточнения → Отчёт → Действия → повторный Замер. Все разделы, кроме «Старт» и «Анкета», заблокированы (компонент 1.4.12) до отправки анкеты. Разделы «Отчёт», «Конкуренты», «Источники», «Динамика» дополнительно заблокированы до первого завершённого замера.

Принцип конфиденциальности (решение зафиксировано ранее): клиент видит полные тексты ответов нейросетей только внутри кабинета (V-3.4, V-3.5). В публичной ссылке отчёта (V-5.10) сырых ответов и точных формулировок вопросов нет — только сводные выводы. Формулировки вопросов клиент видит, но не видит технику их генерации и промпты.

Готовность модуля — в основном **A**: конвейер реализован в `eyon-pilot` (`routes/visibility*.php`, таблицы `visibility_quizzes`, `question_candidates`, `prompt_sets`, `audit_runs`, `measurement_answers`, `answer_mentions`, `entities`, `answer_sources`, `snapshot_confirmations`, `report_publications`, `competitors`, `site_pages`, `action_tasks`, `monitoring_schedules`). Сейчас часть экранов сделана как рабочее место сотрудника EYON (`/visibility/workspace`, `/visibility/review`); для клиента они упрощаются по описанию ниже.

Иллюстрация темы в шапке — только на V-0.1 и V-5.1.

## 4. Диалоговый модуль «ИИ-продавец» (D-)

Движок — прототип «Союз Пир»: таблицы `leads`, `messages`, `tasks`, `review`, `evaluations`, `llm_calls`; знания — 10 YAML (переезжают в БД, **B**); виджет, Telegram и инбокс — из `eyon-pilot` (`widget_settings`, `channel_accounts`, `conversations`, `contacts`). Внутренняя модель: один `lead` = один диалог с одним клиентом в одном канале; «Клиент» (D-3) — это `contacts` из eyon, к которому привязываются лиды.

Терминология для клиента: «диалог» (lead), «карточка клиента» (LeadState), «стадия» (stage), «итог» (outcome), «задача» (task), «пометка» (review), «доклад» (evaluation), «факт / условие / тема / образец речи / приём / запрет» (знания), «передача менеджеру» (handoff/escalate), «режим канала» (autonomous / suggest / off).

### D-4 База знаний

Главный раздел редактора. Единая модель: **атом знания** с типом (факт, условие, тема, образец речи, запрет, правило Guard) — это соответствует `knowledge_atom_heads / revisions / releases` в eyon и 10 YAML в прототипе. Все правки накапливаются в черновике и публикуются версией (D-4.12); бот использует последнюю опубликованную версию. Это **B**: нужна миграция YAML → таблицы по бренду и сборка `Knowledge` из БД вместо файлов, логика агента не меняется.

**D-4.1 Обзор** · `/seller/knowledge` · Редактор и выше · **B**
- Карточки-счётчики по типам с кнопкой «Открыть»: Факты (124, из них 3 без темы), Условия (18, 2 не утверждены), Темы вопросов (36), Образцы речи (58), Запреты (14). Карточка «Входящие» с красным счётчиком (D-4.2). Карточка «Черновик»: «12 изменений с публикации v13 · 3 дня назад», кнопки «Посмотреть изменения» и «Опубликовать» (D-4.12). Карточка «Покрытие»: «За 7 дней бот не нашёл ответа в 8 % диалогов», топ-5 вопросов без ответа. Строка «Проверить в песочнице» (D-4.11).

**D-4.2 Входящие** · `/seller/knowledge/inbox` · Редактор и выше · **A/B**
- Очередь карточек из трёх источников: неизвестные вопросы бота (`tasks.type = unknown_fact`, `log_unknown_question`), пометки «Неверный факт» (D-2.5), предложения из докладов (`evaluations.report.fixes`). Карточка: вопрос клиента дословно, контекст (ссылка на диалог), сколько раз встречался, предложенный ботом вариант ответа (если есть). Действия: «Добавить факт» (открывает D-4.4 с предзаполнением), «Это условие» (→ D-4.5), «Привязать к теме», «Это запрет», «Уже есть — объединить», «Отклонить». Фильтр по источнику, сортировка по частоте.

**D-4.3 Факты** · `/seller/knowledge/facts` · **B** (из `facts.yaml`)
- Слева — дерево тем (`topics`: доставка, оплата, ассортимент, документы, …) со счётчиками; справа — таблица фактов выбранной темы: текст факта, тема, связанные условия (`{cond:...}` чипами), «нельзя говорить» (есть/нет), подсказка-мостик (есть/нет), статус (Опубликован / Изменён в черновике / Новый / Отключён), последнее изменение. Кнопка «Добавить факт». Поиск по тексту. Групповые действия: перенести в тему, отключить.

**D-4.4 Факт** · drawer / `/seller/knowledge/facts/{id}` · **B**
- Поля: Текст факта (многострочный, счётчик знаков, подсказка «одно утверждение — один факт»), Тема (селект), Подставлять условия (мультивыбор условий; в тексте показываются как чипы вместо `{cond:...}`), «Чего нельзя говорить рядом» (`must_not`, список строк), «Мостик к продаже» (`bridge_hint`, одна строка — как от этого факта перейти к следующему вопросу), Темы вопросов, где факт используется (чипы, из `intents.yaml`), Включён (переключатель). Справа: «Как бот это скажет» — живой пример ответа в песочнице на один типовой вопрос темы (кнопка «Обновить пример»), история изменений (диф).

**D-4.5 Условия** · `/seller/knowledge/terms` · Редактор и выше; утверждать — Владелец/Админ · **B** (из `conditions.yaml`)
- Группы карточек: Минимальный заказ, Скидки (сетка: таблица «от суммы → %»), Оплата (предоплата %, отсрочка — да/нет и кому), Доставка (по городу, по стране, бесплатно от), Акции (с датами), Прочее. Каждое условие: значение, единица, «Утверждено: Иван Петров, 12 окт» или янтарный бейдж «Не утверждено» (`approved_by`), «Максимум без утверждения: 5 %» (`max_pct_unapproved`), где используется (факты). Правая панель: «Что бот скажет, если спросят про скидку» — пример. Кнопка «Утвердить все» для Владельца. Опасность: изменение условий — модалка «Изменение вступит в силу после публикации версии».

**D-4.6 Темы вопросов** · `/seller/knowledge/topics` · **B** (из `intents.yaml`)
- Таблица: тема (русское имя), системный код (мелко), примеры вопросов клиентов (чипы), привязанные факты (счётчик), частота за 30 дней (столбик), доля ответов «не знаю» по теме (красным, если > 10 %). Кнопка «Добавить тему». Темы с нулём фактов — предупреждение.

**D-4.7 Тема** · drawer · **B**
- Название, описание для бота («когда клиент спрашивает о…»), примеры формулировок (список), привязанные факты (мультивыбор с поиском), «Ответ по умолчанию, если фактов нет» (текст), «Что бот должен сделать после ответа» (вопрос-мостик или tool из разрешённых). Статистика: топ реальных вопросов клиентов, попавших в тему (из `messages.meta.intent`), с кнопкой «Добавить как пример».

**D-4.8 Образцы речи** · `/seller/knowledge/phrases` · **B** (из `fewshot.yaml`)
- Фильтр по тегу (`tag`: приветствие, возражение по цене, уточнение города, напоминание, прощание, …) — таблетки. Карточка образца: ситуация (вопрос клиента или контекст), текст ответа, тег, уверенность (`confidence`: ползунок 0–1 с подписью «насколько строго копировать»), источник (ручной / из пометки / из диалога #), включён. Кнопка «Добавить из диалога» — выбор реплики менеджера из ленты. Предупреждение, если текст длиннее лимита персонажа (D-6.1).

**D-4.9 Запреты** · `/seller/knowledge/limits` · **B** (из `closed_topics.yaml` + `guard_rules.yaml`)
- Вкладка *Закрытые темы*: тема (например, «политика», «конкуренты по именам», «написать стих/лендинг»), как бот её закрывает (фраза), что делать дальше (вернуть к делу / передать менеджеру). Вкладка *Запрещённые обещания*: правило (человеческая формулировка: «обещать отсрочку платежа»), что ловим (паттерн — показывать как текст с подсветкой, редактирование паттерна — за «Расширенно»), строгость (Блокировать — ответ заменяется / Предупреждать — только в доклад), сработок за 30 дней. Вкладка *Стиль*: максимум вопросов в реплике, запрет канцелярита (список слов), длина. Кнопка «Проверить фразу»: поле текста → показывает, какие правила сработают.

**D-4.10 Документы и импорт** · `/seller/knowledge/documents` (есть `/knowledge` в eyon с `knowledge_documents`) · **A/B**

### D-11 Настройки модуля

**D-11.1 Режим работы и расписание бота** · `/seller/settings` · Админ и выше · **B**

### А.7 Качество

Критерии судьи (1–5): `naturalness` Естественность · `goal` Движение к цели · `facts` Факты · `objections` Работа с возражениями · `brevity` Краткость.
Слои проблем (`by_layer`): `extractor` Понимание · `policy` Логика · `responder` Речь · `knowledge` Знания · `guard` Проверка.
Типы проблем (`Supervisor::ISSUE_TYPES`): `invented_fact` Выдумал факт · `stale_or_conflicting_fact` Устаревший или противоречивый факт · `forbidden_promise` Запрещённое обещание · `false_action_claim` Сказал, что сделал, но не сделал · `lied_about_bot` Солгал, что не бот · `false_refusal` Отказал без причины · `misunderstood_intent` Не понял вопрос · `ignored_client_question` Проигнорировал вопрос · `repeated_question` Повторил вопрос · `two_questions` Два вопроса в одной реплике · `missed_signal` Пропустил сигнал клиента · `missed_personal_hook` Не использовал личную зацепку · `missed_escalation` Не передал менеджеру, когда надо · `needless_escalation` Передал без причины · `no_followup` Не поставил напоминание · `bad_objection_handling` Слабо отработал возражение · `off_topic_fulfilled` Выполнил просьбу не по теме · `pushy_sales` Навязчивость · `too_long` Слишком длинно · `bureaucratic` Канцелярит · `unnatural` Неестественно · `guard_fallback` Ответ заменён запасной фразой · `other` Другое.
Серьёзность: `high` Блокирующая (красный) · `medium` Важная (янтарный) · `low` Мелкая (серый).

### А.8 Видение

## Приложение Г. Критерии приёмки макетов

1. Каждый экран из Приложения В существует как отдельный файл с указанным ID в имени и заголовком `<title>` вида «D-2.2 Диалог · EYON».
2. Переключение `data-theme` между `confectionery` и `pyro` меняет цвета, логотип, иллюстрации и моковые данные (тексты фактов, названия клиентов, вопросы) без правки разметки. Контраст текста на фоне не ниже 4.5:1 в обеих темах.
3. Ни одного захардкоженного hex-цвета бренда в файлах экранов; статусные цвета — только из Приложения Б.
4. Все подписи стадий, итогов, типов, ролей — только из Приложения А. Внутренние термины (intent, slot, extractor, prompt) видны лишь в блоках «внутренности хода» и в песочнице мелким серым.
5. На экранах с готовностью C есть бейдж «v2» и текст-заглушка «настраивается командой EYON при внедрении»; на экранах D — состояние «Скоро» с описанием.
6. У каждого экрана есть хлебная крошка / активный пункт меню, H1, подзаголовок и одно главное действие справа.
7. Пустые состояния присутствуют там, где отмечено «П»; заблокированные — где «Б» (компонент 1.4.12 с ссылкой на разблокирующий шаг).
8. Мобильные версии (390 px) есть для D-2.2, D-2.3, D-2.4, V-5.P и экранов входа.
9. `index.html` содержит галерею с фильтрами по модулю (оболочка / Видение / Продавец) и по готовности (A/B/C/D), а также раздел «Компоненты» со всеми элементами 1.4 в обеих темах.
10. Макеты не содержат эмодзи, восклицательных знаков в интерфейсных текстах и обращения на «ты».
