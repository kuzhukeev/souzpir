# 01. Общий документ проекта «Кабинет клиента EYON»

## 1. Назначение
Новый самостоятельный кабинет клиента EYON: оболочка (регистрация, вход, организации, бренды, пользователи, роли, настройки), модуль «Видение» (видимость бренда в ИИ-ответах) и диалоговый модуль «ИИ-продавец». Бэкенд — Laravel 13, фронтенд — React 19 + TypeScript + Vite 8 + Tailwind 4 через Inertia 3. Исходные проекты (прототип продавца «Союз Пир» и eyon-pilot 6.4) — источники логики, а не фундамент для копирования.

## 3. Границы v1
- Готовность по ТЗ §0.4: A (есть в коде, переносится), B (новое, реализуется), C (только чтение/отложено), D («Скоро» — экран-заглушка). Статусы не повышаются по факту наличия экрана.
- В v1 нет: WhatsApp, amoCRM, Bitrix24, 1С, Google Sheets, внешний URL (D); редактирования промптов клиентом; WebSocket; английского интерфейса; головной админки (только контракты).
- Один монолит Laravel + один Inertia-фронтенд + отдельная лёгкая сборка виджета сайта.

## 4. Приоритет источников и как он применён
1. Указания пользователя (React/TS/Vite/Tailwind, SPA вместо Blade, не упрощать продавца, папка 13 — визуальный эталон).
2. ТЗ `src/tz.md` — содержание экранов, словари Приложения А, бейджи Б, чек-лист В, приёмка Г.
3. Код — фактическое поведение (прототип для продавца, eyon-pilot для оболочки/Видения/каналов/ИИ-шлюза).
4. Макеты — визуальный характер и состав элементов; 70 расхождений зафиксированы в `02c` с решениями, где ТЗ побеждает (3 темы, 11 пунктов меню, 16 слотов, стадии А.1, честные статусы интеграций, никаких вымышленных цен и лимитов).

## 5. Ключевые решения (подробно — 09 §3)
- Движок продавца — дословный перенос классов прототипа в `App\Seller\Engine`; знания из YAML — в версионируемые таблицы с `KnowledgeSnapshot`, воспроизводящим массив `Knowledge::all()`; эквивалентность доказывается золотыми сценариями, записанными до переноса.
- Любое изменение поведения — настройка с дефолтом «как в прототипе».
- Мультитенантность: организация → бренды → данные; технические роли `owner/admin/member/viewer` (А.12, как в eyon) с подписями интерфейса по S-3.3 (Редактор/Менеджер — флаг); 404 для чужого tenant.
- Inertia 3 как база; TanStack Query для живых данных; Redux не нужен (05 §3.1).
- Тарифы — модель без значений до ответа заказчика (Q-01).

## 6. Главные риски
1. Поведение продавца при переносе (митигируется T-01/E3-07 и теневым запуском E9-03).
2. Неясные тарифные лимиты и единицы стоимости (Q-01, Q-02) — влияют на 6 экранов.
3. Переработка анкеты и размера набора Видения (R-V-01…05) — регресс метрик отчёта; нужен снапшот отчёта до/после.
4. Объём: 160 экранов; критический путь — движок продавца, его нельзя сдвигать ради интерфейсов.
