# Параллельная работа Codex с очередью souzpir

Пользователь 31.10.2026 разрешил продолжить разработку всего кабинета после первого просмотра: docs/checkpoints/first-preview.md. Авторитетная готовность задачи определяется очередью: зависимости находятся в `done`, нет пересечения ownership с `progress`/`review`, проект включён. Список `ready` — подсказка; право владения выдаёт только атомарный `claim`.

## Роли и рабочие каталоги

- Сначала интегратор проверяет и объединяет готовые результаты с учётом зависимостей. Одновременно допускается до двух исполнительских направлений с отдельным владельцем и конкретной приёмкой. Общие блокеры имеют одного владельца; зависимые части можно готовить изолированно, но нельзя включать или сдавать как готовые до выполнения их зависимостей.
- Примерно каждые 30 минут исполнитель сообщает интегратору: готовый результат и SHA либо точный блокер и следующий шаг. Не прерывать из-за времени операцию в небезопасном состоянии; при необходимости сначала завершить её безопасный этап.
- Останавливая работу, исполнитель сохраняет коммит в своей ветке и фиксирует в карточке или отчёте SHA, сделанное и оставшееся. Парковка сама по себе не переводит задачу в `review` или `done` и не освобождает claim.
- Исполнитель запускает адресные проверки своей задачи. Интегратор выбирает и один раз перед merge запускает необходимую интеграционную регрессию; полный набор нужен, когда это оправдано изменениями и приёмкой.
- Основной checkout `C:/OSPanel/home/souzpir.local`, ветка `main` — только интегратор.
- Один чат исполнителя = одна задача = ветка `codex/<task-key-в-нижнем-регистре>` = каталог `.worktrees/<task-key-в-нижнем-регистре>`.
- Исходники в `.local/references/` только для чтения и выборочного переноса. Они доступны в основном checkout и не копируются Git в worktree.
- Перечень задач и ownership: `planning/tasks.json`. Полный prompt: путь `promptPath` соответствующей задачи.
- Claim token хранится только в основном checkout `.local/claims/<task-key>.json`; не вставлять этот файл или token в чат, коммит, PR, лог или screenshots. CLI не выводит token.

Для каждой ветки нужны отдельные DB/schema, Redis/cache/queue prefix, private storage и порты. До выполнения конкретных задач контракты bootstrap должны описать точные env names. Worker не запускает scheduler/real messaging автоматически; внешние adapters в разработке используют fake/sandbox режим. Общая `.env`, production database и общая очередь между чатами недопустимы.

## CLI

Скрипт `scripts/task.py` использует Python standard library и Git. Ни Composer, ни Node для него не нужны. На текущем компьютере доступен Python:

```powershell
$taskPython = 'C:\Users\eralash\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
$taskCli = 'C:\OSPanel\home\souzpir.local\scripts\task.py'
& $taskPython $taskCli --help
& $taskPython $taskCli ready
```

Команды ниже выполняются только в пределах активного разрешённого этапа. В примере взята задача `SP-C-01`; перед выполнением сверить её состояние и зависимости в `planning/tasks.json` и очереди.

```powershell
& $taskPython $taskCli claim SP-C-01 --worker 'codex:<chat-id>'
```

`claim` требует чистый основной checkout на `main`, сверяет project, scope и зависимости локального плана с сервером, проверяет отсутствие прежних claim/worktree/branch. Каждая зависимость должна быть `done`, иметь полный `mergeCommit`, уже находящийся в истории выбранного локального `main`. Если очередь обновлена, а Git ещё нет, сначала синхронизировать main; одного статуса `done` недостаточно.

После проверок CLI получает атомарный token, сохраняет исходный SHA `main` вместе с SHA зависимостей, повторно сверяет план из ответа claim и создаёт worktree от фиксированного проверенного commit. Изменение main во время HTTP-запроса не меняет эту базу. Scope сравнивается без учёта регистра в соответствии с Windows и очередью. Результат содержит безопасные поля branch/worktree/baseCommit/promptPath. Передать последующие Git/редактор/тест-команды именно в выданный worktree. Скрипт не открывает новый чат и не начинает выполнение задачи.

Git вызывается с `-c safe.directory=<конкретный рабочий каталог>` только для одной команды. Глобальные настройки доверенных каталогов не меняются.

Если создание worktree не удалось, CLI пытается вернуть задачу в очередь и сохраняет локальное состояние для разбора. Он не удаляет каталоги, ветки или незакоммиченные изменения. При сетевом timeout сначала проверить статус задачи: HTTP-запрос мог завершиться на сервере. Не повторять mutation вслепую.

## Сдача результата

Работать только в `scope` задачи; общие lockfiles, bootstrap registries и контракты изменяет их выделенный владелец. Если обнаружена необходимость вне scope — описать её интегратору; не расширять ownership самостоятельно. Коммитить только собственные изменения, выполнить acceptance и сохранить честные результаты проверок.

```powershell
& $taskPython $taskCli submit SP-C-01 --summary 'Что реализовано и какой результат' --check 'Фактически выполненная проверка и её результат'
```

`--check` можно повторять. CLI проверяет clean worktree, ожидаемую ветку, ancestry сохранённого base SHA, наличие task commit и все изменённые/удалённые пути в diff. Rename рассматривается как удаление + добавление, поэтому перенос чужого файла также не проходит scope. `submit` передаёт SHA, branch, summary и checks и переводит задачу в `review`; зависимости ещё не разблокируются.

Для исправлений после review тот же исполнитель сохраняет ownership:

```powershell
& $taskPython $taskCli resume SP-C-01 --reason 'Конкретное замечание проверки'
```

После исправлений — новый commit, нужные проверки и повторный `submit`. Пока задача в review, её ownership блокирует конфликтующие задачи.

Если работа прекращена до review:

```powershell
& $taskPython $taskCli release SP-C-01 --reason 'Причина остановки и где сохранена работа'
```

Release сохраняет branch/worktree, удаляет token из локальной записи и возвращает задачу в queue. Перед новым claim интегратор должен разобрать остатки прежней попытки и безопасно архивировать/удалить её worktree/branch/claim record; CLI намеренно не перезаписывает их. Если потерян token или чат недоступен, интегратор может использовать серверный `recover` только после проверки, что прежний исполнитель остановлен; нужен reason и `confirmAbandoned=true`. Время само по себе не освобождает ownership.

## Интеграция и готовность зависимостей

Интегратор читает diff и проверки, последовательно вносит принятую ветку в `main`, выполняет проверки совмещённого результата и синхронизирует Git remote по правилам проекта. Одновременно интегрирует только один процесс. Обычный merge/fast-forward должен сохранять reviewed commit в истории; squash/cherry-pick не удовлетворяет ancestry gate CLI.

После настоящего merge:

```powershell
& $taskPython $taskCli mark-merged SP-C-01
```

Эта команда сама **не делает merge**. Она требует clean main checkout, проверяет, что `result.commit` задачи существует и является предком текущего `main`, и передаёт фактический полный SHA main в очередь. Только затем сервер переводит задачу в `done`, а зависимые задачи могут стать ready. Сам API не читает Git: гарантия связи `done` с merge обеспечивается CLI и интегратором. Не отмечать done вручную обходным HTTP-запросом.

## Проверка инструментов подготовки

```powershell
& $taskPython -m unittest discover -s tests/preparation -p 'test_task_cli.py' -v
```

Тесты создают временные Git-репозитории и подменённый API, не обращаются к tasks.local и не берут рабочие задачи. Они проверяют token storage, readiness, collision guards, rollback после сбоя worktree, scope/dirty gates, review/resume, ancestry merge gate и отказ при отсутствующих в main commit зависимостей.
